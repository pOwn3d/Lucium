# API matérielles du web : WebHID, WebUSB, Web Serial

Réglage `webHardware` (« API matérielles du web », **désactivé par défaut**), fonction `web-hardware` du registre (`src/shared/features.ts`, `docs/fonctions.md`). Ce document dit ce qui est livré, ce que le moteur permet réellement (vérifié dans les définitions d'Electron 45.0.0) et le modèle de menace.

## Ce que fait la fonction

Un site peut, **après un clic dans son onglet**, demander à utiliser un appareil : manette ou carte à interface HID propre (`navigator.hid`), appareil USB à interface vendeur (`navigator.usb`), port série (`navigator.serial` : cartes Arduino, adaptateurs, imprimantes 3D). Ce sont les usages qui justifient ces API : configurateurs de claviers (VIA, Vial), outils de flash de microcontrôleurs, consoles série dans le navigateur, portefeuilles matériels.

- Le **sélecteur** est un menu natif (celui des sélecteurs d'écran, `display-media`) posé sur la fenêtre de l'onglet. Ses **deux premières lignes sont du texte** : « « exemple.org » veut se connecter à un appareil USB », puis « Choisissez l'appareil à lui confier ». Aucun appareil n'est sous le pointeur à l'ouverture, et le menu étant natif, la page ne peut ni le dessiner ni cliquer dedans. Suivent les appareils (nom nettoyé, identifiants `vendeur:produit`, fin du numéro de série pour distinguer deux exemplaires), puis « Annuler ».
- Le nom du site est celui de l'origine (`host` et port ; en punycode pour un nom internationalisé, donc un site qui imite un autre avec des lettres voisines ne passe pas pour lui ; un nom trop long est coupé au début, la fin étant ce qui distingue les sites).
- **Refusé sans rien montrer** : un site qui n'est pas en `https` ou sur ce poste (`localhost`, `127.0.0.0/8`, `::1`) ; une origine opaque (iframe `sandbox`, `file:`, `data:`) ; tout ce qui n'est pas le **cadre principal d'une page du navigateur** (onglet, aperçu, volet web) : une iframe, y compris celle que la page a autorisée avec `allow="usb"`, une fenêtre surgissante, la page d'un flux de connexion, une page d'extension ; une demande sans clic ni touche dans l'onglet depuis cinq secondes ; une seconde demande pendant qu'une liste est ouverte.
- **Jamais proposés** (ni listés, ni acceptés par le gestionnaire d'appareils) : les clés de sécurité FIDO (page d'usage `0xF1D0`, même imbriquée), les constructeurs de clés (Yubico, Feitian), les cartes à puce et la sécurité de contenu USB, les claviers, pavés numériques, souris et pointeurs HID, les appareils USB dont aucune interface n'est utilisable par une page (HID, stockage, audio, vidéo, sans-fil), et tout appareil dont le descripteur ne se laisse pas lire jusqu'au bout. Le menu dit combien d'appareils ont été écartés, pour qu'une clé absente s'explique.
- **Jamais en fenêtre privée ni dans un onglet privé** : voir plus bas.
- Les appareils autorisés se lisent et se retirent dans **Réglages › Vie privée et sécurité › Plus de réglages › API matérielles du web** : une ligne par appareil (nom, type, site) avec « Retirer », et « Tout retirer ».

## Ce que le moteur permet (vérifié dans `node_modules/electron/electron.d.ts`, version 45.0.0)

| Fait | Source | Conséquence |
|---|---|---|
| `select-hid-device`, `select-usb-device` : `{ deviceList, frame }`, `frame` est un `WebFrameMain` ou `null`. `select-serial-port` : `(portList, webContents, callback)`, **sans cadre**. | `Session` | Pour HID et USB on sait quel cadre demande (`frame.parent === null` = cadre principal) ; pour le port série seul l'onglet est connu, le cadre est jugé en amont par le contrôle de permission (`isMainFrame`). |
| Il faut appeler `event.preventDefault()`, sinon Electron annule la demande ; `callback()` (HID, USB) ou `callback('')` (série) annule. | Doc des trois événements | Le service réclame l'événement dans tous les cas et appelle `callback` exactement une fois. |
| `setDevicePermissionHandler` reçoit `{ deviceType, origin, device }` : **ni le cadre ni l'onglet**. | `DevicePermissionHandlerHandlerDetails` | Le gestionnaire ne peut juger que le type, l'origine et l'appareil. Le cadre et l'onglet sont jugés au moment du choix (événement `select-*`) ; la durée de vie d'une autorisation est suivie à part (voir plus bas). |
| « Si ce gestionnaire n'est pas défini, les permissions accordées par la sélection (`requestDevice`) sont utilisées ». Par défaut Electron garde les autorisations **en mémoire**. Aucun appel pour en retirer une (`hid-device-revoked` n'a lieu que si la page appelle `forget()`). | Doc de `setDevicePermissionHandler` | Avec un gestionnaire défini, la mémoire d'Electron n'est plus consultée : **le registre de Lucium est la seule source**, et retirer une autorisation du registre la révoque au contrôle suivant. |
| `setPermissionCheckHandler` : `securityOrigin`, `isMainFrame`, `embeddingOrigin` (sous-cadre inter-origine seulement), `webContents` éventuellement `null`. | `PermissionCheckHandlerHandlerDetails` | Contrôle en amont, session par session : origine sécurisée ; pas de sous-cadre inter-origine ; cadre principal quand l'onglet est connu (série). |

**Non vérifiable sans moteur ni appareil** (à rejouer, voir « Vérifications ») : que `isMainFrame` soit renseigné pour `serial` ; que le gestionnaire soit bien appelé à la place de la mémoire d'Electron pour `getDevices()` et pour l'ouverture d'un appareil ; que les trois événements partent même quand la liste est vide.

## Le registre et la révocation

`DeviceGrants` (`src/shared/web-hardware.ts`) est la seule mémoire que lit le gestionnaire d'appareils du moteur. Une entrée = un profil (session), une origine sécurisée, **un appareil précis** (type, vendeur, produit, numéro de série, interface HID ou nom de port) et les onglets qui la portent.

- **Retirer** supprime l'entrée : au contrôle suivant le gestionnaire répond non. `getDevices()` ne rend plus l'appareil, `open()` échoue.
- **Elle se termine avec son onglet** : l'onglet qui a reçu l'appareil est surveillé (`did-navigate`, `destroyed`, des écouteurs posés seulement tant qu'une autorisation existe). Il ferme ou change de site : l'autorisation tombe. Un rechargement ou un changement de page dans le même site la conserve (c'est le cas d'usage de `getDevices()` au chargement). Si plusieurs onglets ont reçu le même appareil, elle tient jusqu'au dernier. **On ne peut pas faire mieux** : le gestionnaire ne sait pas quel onglet l'interroge, donc un autre onglet du même site profite d'une autorisation donnée à un frère.
- **Rien n'est écrit sur le disque** : pas de persistance entre deux lancements (un numéro de série n'est pas une donnée à garder). Une autorisation ne survit donc pas à la fermeture de Lucium, ce qui est le choix prudent.
- Au plus 64 autorisations ; la plus ancienne part.
- **Coupure du réglage** : les écouteurs `select-*` sont retirés, toutes les autorisations tombent, la coupure dit si des onglets avaient une connexion. Dans un profil où un appareil a été choisi, un gestionnaire qui refuse tout reste posé : sans lui la mémoire d'Electron répondrait de nouveau. Dans un profil où rien n'a été choisi, rien ne reste.

**Limite que le moteur impose, et qu'on ne contourne pas** : retirer une autorisation (ou couper le réglage) **ne ferme pas une connexion déjà ouverte** par la page (`HIDDevice.open()`, port ouvert). Electron n'offre aucun appel pour la fermer de l'extérieur. Elle dure jusqu'au rechargement ou à la fermeture de l'onglet. L'interface le dit après chaque retrait (« Une connexion déjà ouverte à l'appareil reste active jusqu'au rechargement ou à la fermeture de l'onglet ») ; recharger l'onglet n'est jamais fait de force, car cela peut interrompre l'écriture d'un microcontrôleur. L'alternative aurait été de recharger les onglets concernés au retrait : écartée pour cette raison.

## Modèle de menace

| Menace | Réponse | Où |
|---|---|---|
| **Page hostile** qui appelle `requestDevice` sans clic. | Blink exige un geste ; le moteur le revérifie (un clic ou une touche dans l'onglet depuis 5 s, non consommé), car Electron ne l'impose pas pour d'autres API (partage d'écran). | `userActed`, `GestureLedger.fresh` |
| Page hostile qui **lance les demandes en rafale** pour lasser l'utilisateur ou empiler des menus. | Une liste à la fois ; le reste est refusé et journalisé. | `picking` |
| Page hostile qui **usurpe l'interface** (fausse boîte qui ressemble au menu, ou menu qui apparaît sous un clic que la page a provoqué). | Le menu est natif (la page ne peut pas le dessiner) ; ses deux premières lignes sont du texte désactivé (aucun appareil sous le pointeur à l'ouverture) ; le site est nommé en tête. | `pickerMenu` |
| **Iframe** (la page, ou une publicité) qui demande un appareil ou profite d'un autre cadre. | Refus de tout cadre dont `parent` n'est pas `null` (HID, USB) ; refus d'un sous-cadre inter-origine et de tout cadre non principal au contrôle de permission (série) ; l'origine du cadre doit être celle de l'onglet. Les autorisations sont par origine : une iframe d'un autre site n'a rien. | `offer`, `mayRequest` |
| **Appareil sensible** : clé de sécurité FIDO, clavier, souris, carte à puce. | Jamais listés, jamais acceptés par le gestionnaire d'appareils, même si une entrée du registre y ressemblait (verrou propre à Lucium : on ne suppose pas que le sélecteur d'Electron applique la liste d'exclusion de Chromium, ce qui n'a pas été vérifié). Un descripteur trop grand ou trop profond pour être lu est refusé, pas supposé inoffensif. | `sensitiveReason` |
| **Appareil hostile** (un nom qui ment, des caractères de contrôle ou bidirectionnels, un nom de 10 Mo). | Les noms sont nettoyés (contrôles, formats, retours à la ligne), coupés, et jamais interprétés ; les identifiants rendus à Electron sont ceux qu'il a donnés, vérifiés contre la liste affichée. | `cleanLabel`, `pickerChoices` |
| Réponse **falsifiée** (un identifiant qui n'était pas dans la liste). | La réponse est cherchée dans la liste proposée, sinon refusée. | `choices.find` |
| **Page qui change de site** pendant que la liste est ouverte, ou onglet fermé. | La réponse est refusée si l'onglet n'est plus sur l'origine qui a demandé. | `offer` |
| **Autorisation résiduelle** : l'appareil reste accordé après la fermeture ou la navigation. | Voir « Le registre ». | `watch` |
| Autorisation **oubliée dans une base** : un état importé ou ancien contenant `hid: allow`. | `hid`, `usb`, `serial` ne passent jamais par les réponses mémorisées (`routePermission` → `hardware`), ni par l'invite générique, ni pour une page d'extension. | `shared/permissions.ts` |
| **Identifiant matériel** : le numéro de série d'un appareil est stable et relie une visite privée à une visite normale. | Aucune fonction matérielle en fenêtre privée ni en onglet privé : aucun écouteur sur leurs sessions, contrôle de permission qui refuse. La liste des Réglages d'une fenêtre privée est vide et ne montre rien des fenêtres normales. | `ensureProfile` seulement, `hardware-ipc.ts` |
| **Appareil connecté par un tiers** (un site autorisé est compromis : XSS). | Le risque est celui de l'autorisation : le site a l'appareil. La durée est bornée à l'onglet, la liste le montre, « Retirer » le coupe pour les nouveaux accès. | — |
| **Extension** qui demande un appareil. | Une page d'extension n'obtient pas `hid`/`usb`/`serial` sur la foi de son manifeste. | `routePermission` |
| Coût quand c'est **désactivé**. | Aucun écouteur, aucun gestionnaire, aucune autorisation (sauf le gestionnaire qui refuse tout d'un profil où un appareil a déjà été choisi). Toute demande est refusée. | `gateWebHardware` |

**Hors périmètre de cette fonction** : WebBluetooth et WebNFC ne sont pas touchés (toujours refusés) ; la liste n'est pas mise à jour si un appareil est branché pendant qu'elle est ouverte (le menu est un instantané) ; la persistance entre lancements n'est pas offerte ; le « Retirer » ne ferme pas les connexions ouvertes (voir plus haut) ; un même modèle sans numéro de série en deux exemplaires est indiscernable (l'autorisation vaut pour les deux).

## Vérifications

- Règles pures : `src/shared/web-hardware.test.ts`, `src/shared/permissions.test.ts`, `src/shared/external-links.test.ts`. Service du moteur avec une session et des onglets simulés : `src/main/engine/web-hardware.test.ts`. IPC et portail : `src/main/shell/hardware-ipc.test.ts`, `hardware-gate.test.ts`. Chaque garde est couverte : la retirer fait échouer un test.
- Moteur : `LUCIUM_SMOKE_ONLY=webhardware node_modules/.bin/electron . --smoke --user-data-dir=<dossier jetable>` (`src/main/smoke-webhardware.ts`). Aucun appareil n'est touché : les listes sont simulées en émettant les événements `select-*` sur la session avec un vrai cadre et un vrai onglet, le menu natif est remplacé par un enregistreur, les appels réels de la page (`requestDevice`, `requestPort`) vérifient que rien ne passe sans choix.
- **À rejouer avec un vrai appareil** (aucun test ne peut le faire) : choisir un appareil dans une page de test, constater `getDevices()` ; « Retirer » dans les Réglages ; constater que `getDevices()` rend `[]` et que `open()` échoue (c'est la preuve que la mémoire d'Electron n'est plus consultée) ; vérifier qu'une clé de sécurité branchée n'est pas dans la liste ; vérifier qu'un cadre `allow="serial"` n'ouvre pas de liste.
