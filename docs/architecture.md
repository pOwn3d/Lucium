# Architecture de Lucium

## Objectifs (par ordre de priorité)

1. **Mettre à jour le cœur Chromium sans tout casser.**
2. **Améliorer les performances** avec les modules déjà écrits en extensions de navigateur (Chrome Toolkit : mise en veille d'onglets, blocage de pubs/traqueurs, consentement cookies…).
3. Offrir les fonctions qui comptent, puis en ajouter.

Carte blanche sur la stack : une application native (Swift/AppKit) n'est pas un objectif.

## Décision : Electron, sans aucun patch de Chromium

| Option | Mise à jour de Chromium | Extensions MV3 | Effort solo | Verdict |
|---|---|---|---|---|
| **Electron** (retenu) | Monter la version d'`electron` ; Chromium suit | Partielles, mesurées (voir plus bas) | Faible | **Retenu** |
| Fork de Chromium (patchs maintenus en propre) | Rebase de tous les patchs à chaque version, build de 100 Go+ | Complètes | Très élevé | Rejeté : contredit l'objectif n°1 |
| CEF + coque native | Binaires CEF suivent Chromium | Limitées en mode Alloy | Élevé (C++/Swift) | Gain mémoire marginal, maintenance plus lourde |
| Navigateur existant basé sur Chromium + extension (side panel) | Automatique | Complètes | Faible | Impossible de masquer la barre d'onglets : ce n'est plus « mon navigateur » |
| WebView système (Tauri, WKWebView) | Dépend de l'OS | Aucune | — | Pas Chromium |

Fait vérifié : **Electron 45.0.0 embarque Chromium 156.0.8078.48.** Le `package.json` épingle Electron 45.2.1 ; la seule référence présente, `compat/baseline-electron-45.0.0.json`, a été produite avec Electron 45.0.0 et ne contient que la suite principale d'alors. Celle de la version épinglée reste à écrire : `pnpm test:engine` sur un Mac libre, lecture de `pnpm compat:compare`, puis `pnpm compat:baseline`.

Autres choix, tous réversibles : TypeScript (strict), React 19 + Vite pour l'interface (le coût mémoire est dominé par Chromium, pas par le framework), pnpm, Vitest.

## Comment mettre à jour Chromium sans casse

Principe : tout ce qui pilote le contenu web et les extensions passe par **un seul port**, `src/main/engine/types.ts` (`Engine`, `Page`). Son implémentation sur Electron est dans `src/main/engine/` : `electron-engine.ts` et ses couches `electron-engine-*.ts`, `electron-page.ts` et leurs auxiliaires (vues, fenêtres surgissantes, mode lecture, Web Store…). Chaque fichier qui importe Electron y est listé, avec sa raison, dans `src/main/engine-port.test.ts`, qui refuse tout nouveau fichier qui importerait Electron dans `src/main/engine/` ou `src/shared/`. `src/shared/` (état, barre de commandes, import, logique pure) n'importe jamais Electron. Le shell (`src/main/shell/`), les préchargements et la racine de `src/main/` l'importent encore pour les fenêtres, les menus et le réseau de l'application.

Procédure de montée de version :

```bash
pnpm up electron@<version>            # Electron fixe la version de Chromium
pnpm typecheck                         # une API retirée apparaît ici
pnpm test                              # logique pure : doit rester vert
pnpm test:engine                       # contrat moteur dans un vrai Electron
pnpm perf                              # mémoire et processeur de l'arbre de processus contre perf-budget.json (docs/performance.md)
pnpm compat:compare                    # le rapport du passage contre la référence du moteur : ce que la montée a fait perdre
pnpm compat:baseline                   # une fois les écarts lus et acceptés : écrit compat/baseline-electron-<version>.json
```

Quatre scripts hors `pnpm test`, à lancer à la main : `pnpm icons:probe` redessine l'icône de l'extension de sonde `compat/surface-probe` (Node seul, sans navigateur ; le test `scripts/probe-icon/probe-icon.test.ts`, lui, tourne avec `pnpm test` et compare le fichier au dessin), `pnpm icons:menu` régénère `src/main/shell/menu-icons-data.ts` (icônes des menus contextuels, rendues par un navigateur basé sur Chromium installé sur le Mac ; `CHROME=/chemin` pour en désigner un autre que celui du script), `pnpm icons:logo` régénère les icônes de l'application depuis le dessin du logo (`scripts/logo/`, voir son `README.md` : `build/icon.icns`, les huit PNG de `resources/app-icons/`, et les fichiers du site dans `out-icons/`) et `pnpm census:textes` liste les textes écrits en dur dans les réglages. Le test lourd du script de comparaison des navigateurs (environ 30 s) tourne avec `pnpm test:bench-script`.

`pnpm test:engine` lance un vrai Electron en mode `--smoke` et vérifie : chargement de page, remontée du titre, épinglage, mise en veille, refus des URL non web, chargement des extensions, **API `chrome.*` réellement disponibles** (sonde `compat/api-probe`) ; il **mesure** aussi si une règle `declarativeNetRequest` de blocage est appliquée (avec groupe témoin) : la valeur part dans le rapport. La suite `probes-ext` vérifie une à une les règles réseau et les événements `chrome.webRequest` des extensions, que Lucium applique lui-même (voir `docs/extensions-compatibilite.md`), puis l'accès qu'un clic donne avec `activeTab`, et une permission facultative demandée, accordée sur la feuille puis retirée (sonde `compat/optional-permission-probe` ; cette dernière partie est écrite et n'a pas encore été lancée). La suite `activetab-origin` (sonde `compat/active-tab-origin-probe`) envoie l'onglet prêté par un clic vers une autre origine puis demande aussitôt un script ou une feuille de style : aucune instruction ne doit s'exécuter, aucune feuille s'appliquer ni rien se lire dans l'origine non remise (les fonctions déclarées au plus haut niveau d'un script du monde principal sont créées avant le garde : `docs/compat-extension-claude.md`) (monde isolé ou principal, fonction ou fichier, feuille de l'auteur ou de l'utilisateur, onglet envoyé par l'extension, une redirection ou la page), et la même origine comme une extension qui a la permission d'hôte doivent continuer à fonctionner (passage du 14 novembre : rouge sur l'ancien code pour le monde isolé, 26 contrôles sur 26 après le correctif ; voir `docs/compat-extension-claude.md`). La suite `mv2-blocking` (sonde `compat/mv2-blocking-probe`) vérifie que Lucium applique ce que répondent les écouteurs bloquants d'une extension Manifest V2 (annulation, redirection, en-têtes de la requête et de la réponse) et refuse ce qu'il doit refuser (redirection vers un fichier local, réponse arrivée après le délai) ; son premier passage, le 13 novembre, a échoué (la page d'arrière-plan, sans isolation de contexte, ne recevait pas les relais de Lucium) ; corrigée, elle est verte au passage suivant (13 novembre, 10 contrôles sur 10). La suite `client-hints` (hors chaîne : `LUCIUM_SMOKE_ONLY=client-hints`, sans extension chargée) relève les Client Hints que les pages envoient à un site (`Sec-CH-UA`, `Sec-CH-UA-Mobile`, `Sec-CH-UA-Platform`, puis les quatre qu'une page demande par `Accept-CH`, sur la navigation, une image, un script et une image de l'autre site) et ce qu'elles lisent d'elles-mêmes (`navigator.userAgent`, `navigator.userAgentData`, `getHighEntropyValues`), dans un onglet du profil normal (protection Standard, puis Renforcée), dans une fenêtre privée et dans une fenêtre d'un second profil, et écrit une ligne `LUCIUM_SMOKE_CLIENT_HINTS {…}` avec tout ce qu'elle a vu. Son premier passage, le 13 novembre, n'était qu'une mesure (24 contrôles sur 24 ; aucun indice sur la navigation, les trois sur le reste, voir « Indices du client » plus bas). Depuis la décision du même jour, elle vérifie aussi que chaque navigation porte les trois indices, avec les valeurs des autres requêtes et les marques, le système et l'indicateur mobile de `navigator.userAgentData`, et qu'aucun indice détaillé ni aucune marque de produit ne part. Premier passage de ces contrôles le 13 novembre : 41 sur 44, les trois échecs étant la toute première navigation du lancement, partie avant la lecture des marques ; corrigé depuis par une attente bornée (voir « Indices du client »), pas encore repassé. Chaque passage écrit son rapport dans `out-engine/report.json` (les suites, leurs vérifications avec leur résultat, la réponse de la sonde d'API, l'application de `declarativeNetRequest`). `pnpm compat:compare` (`scripts/compat-compare.mjs`, règles dans `src/shared/compat-report.ts`) le compare à la référence de la version la plus haute de `compat/` et sort en échec dès que le passage a perdu quelque chose : une vérification qui passait et échoue, est sautée ou n'est plus faite, une suite qui n'a pas tourné, une API `chrome.*` disparue, un appel qui ne répond plus, une règle de requête qui n'est plus appliquée. Une vérification en échec dans la référence et toujours en échec est un échec connu, pas une perte. Les noms se comparent sans le port des serveurs locaux, que le système choisit à chaque passage (`127.0.0.1:<port> finished filling its storage`), et un nom qu'une suite écrit plusieurs fois se compte : le passage perd la différence quand il le fait moins de fois que la référence. Une vérification retirée ou renommée exprès s'explique dans un fichier `{ "<nom de la vérification>": "<raison>" }` donné par `--explained <fichier>` : elle est listée avec sa raison au lieu d'être perdue ; une vérification encore faite qui échoue ou est sautée n'est jamais expliquée ainsi. `pnpm compat:baseline` écrit le rapport du passage tel quel : la nouvelle référence ne garde rien de l'ancienne, et avec `--explained` elle n'est écrite que si chaque perte a sa raison. Après une montée, la référence est celle de la version d'avant ; une fois les écarts acceptés, `pnpm compat:baseline` écrit celle de la nouvelle version.

Le test moteur ne dépend pas de la machine qui le lance : `smoke-run.ts` fixe d'abord, dans le profil jetable, la taille des fenêtres et des panneaux à 100 % pour chaque écran (« Automatique » dépend de l'écran), la langue de l'interface à français (les vérifications lisent des menus et des titres en français, « auto » suivrait la langue du Mac ou du runner) et l'apparence de Lucium à sombre (les couleurs attendues sont celles de l'apparence sombre, « Automatique » suivrait le Mac) : ce sont les réglages de `PINNED_SETTINGS` (`smoke-kit.ts`) ; une vérification qui lit une page des Réglages ouvre d'abord son « Plus de réglages » (`OPEN_MORE_SETTINGS`) ; `index.ts` lui donne un trousseau factice (`--use-mock-keychain` : sans lui, la première lecture de `safeStorage` ouvre une fenêtre du trousseau macOS à laquelle personne ne répond, et la fenêtre qui reste devant empêche toute autre de prendre le focus). Les suites sont déclarées dans une seule table, `smoke-suites.ts` (nom, place dans la chaîne, raison de cette place ou de son absence) ; ce que le passage en fait est dans `smoke-kit.ts`, que les tests unitaires exécutent. Une suite qui lève une exception, qui ne rend pas la main dans son délai (10 minutes par défaut, `LUCIUM_SMOKE_SUITE_TIMEOUT_MS` pour le changer), qui se termine sans une seule vérification ou dont la sonde d'extension n'est pas chargée compte comme une suite en échec, nommée dans le journal, et les suivantes tournent (`runSuite`). Une suite dont le délai est passé n'est pas arrêtée pour autant : ce qu'elle fait encore peut gêner les suivantes, et le résumé dit laquelle c'était. Le passage s'arrête, échoue et dit pourquoi quand les écrans du Mac se mettent en veille, que sa session est verrouillée, qu'il se met en veille, que le processus principal n'a pas tourné pendant une minute ou que l'application est priée de quitter (`watchRun`, `RunStop`) : la suite en cours est coupée, aucune autre ne démarre et le rapport garde les suites faites. Les vérifications pilotent de vraies fenêtres et lisent ce qui est dessiné : après un écran verrouillé, toutes échouaient pour une raison étrangère à l'application, et une demande de quitter finissait le passage avec le code 0 sans rapport. Chaque vérification est écrite au moment où elle est faite ; une vérification qui n'a pas pu être faite s'écrit `skip` avec sa raison et se compte à part. Un nom de suite inconnu dans `LUCIUM_SMOKE_ONLY` est refusé. Pour boucler sur un morceau : `LUCIUM_SMOKE_ONLY=parts LUCIUM_SMOKE_PARTS=settings,pages` ne lance que ces morceaux de la suite principale (`runMainParts` de `smoke.ts`), `LUCIUM_SMOKE_STOP_AFTER=<mots d'une vérification>` arrête la suite principale juste après elle.

**Les suites `smoke-iso-*.ts` ne mesurent plus Lucium contre Arc.** Leur préfixe `iso` est historique (l'époque où l'interface était comparée à celle d'Arc au pixel près, avec des relevés de mesures et de couleurs). Cette comparaison est abandonnée : aucune suite ne contient plus de taille, de position, de rayon, de graisse de police, de couleur ou de courbe d'animation prise d'Arc, aucune image ni donnée de référence n'est conservée pour cela, et les variables d'environnement qui écrivaient les mesures relevées (`LUCIUM_ISOP_DUMP`, `LUCIUM_ISO_DUMP`, `LUCIUM_ISO_PLUS_DUMP`) ou des captures des panneaux, de la barre d'outils et du lecteur (`LUCIUM_ISOP_SHOTS`, `LUCIUM_ISO_SHOTS`, `LUCIUM_ISO_MEDIA_OUT`) n'existent plus (`LUCIUM_ISO_SB_OUT` et `LUCIUM_ISO_PLUS_SHOTS` écrivent encore des images, pour les regarder et jamais pour les comparer). Ces suites (`iso-menus`, `iso-sidebar`, `iso-settings`, `iso-toolbar`, `iso-plus`, `iso-media`, `iso-panels`) vérifient ce que fait l'interface : un panneau s'ouvre, un bouton agit, un élément est atteignable au clavier et à la souris, les noms accessibles, les délais voulus (bulle après environ 1,5 s, repli du lecteur) et des **relations** de mise en page (rien de masqué, de coupé ni de chevauché ; un élément dans sa carte, dans la fenêtre ; l'un sous l'autre, dans cet ordre). Les couleurs ne sont plus comparées qu'aux jetons de l'interface (`--surface-3`, `--tb-icon`, `--focus`) pour vérifier que le thème est suivi. Les chiffres du design (par exemple en tête de `sidebar.css`) restent le dessin de Lucium, plus un contrat vérifié par ces suites.

Ce que le port ne garantit pas : un changement de comportement *interne* de Chromium (rendu, réseau) n'est vu que par ces tests moteur, pas par le typage. `pnpm test:engine` tourne en CI dans le workflow « Smoke (macOS) » (`.github/workflows/smoke-macos.yml`) : à la main, sur un tag et chaque semaine, avec `pnpm compat:compare`, `pnpm test:engine:webstore` et `pnpm test:engine:extwindows`. Le runner GitHub est une machine virtuelle dont l'écran fait 1024 × 768 points en échelle 1, soit une fenêtre de 674 points de haut (les vérifications ont été écrites et lancées sur un écran Retina) : les suites qui ne peuvent pas y passer sont nommées, chacune avec sa raison, dans `compat/runner-limits.json` ; ce workflow-là seul ne s'arrête pas sur elles (`scripts/smoke-runner-verdict.mjs`, `--limits` de `compat:compare`) et s'arrête sur toute autre. Aucune commande du Mac ne lit cette liste : elles jugent toutes les suites.

**Ce que le mode `--smoke` débranche, et que les suites moteur ne voient donc pas.** Pour ne pas agir sur la machine qui lance la passe, l'application coupe ou remplace, sous `--smoke` (`src/main/engine-test-cuts.test.ts` rattache chaque ligne du code qui lit le commutateur à l'un des points ci-dessous, et échoue sur une lecture nouvelle tant qu'elle n'est pas écrite ici) :

- l'ouverture réelle d'une application externe, d'un fichier ou du Finder (`shell.openExternal`, `openPath`, `showItemInFolder` : remplacés par une ligne de journal), et le trousseau de macOS (trousseau de remplacement en mémoire) ;
- Touch ID (pour le verrou et pour le coffre des mots de passe), l'installation de Widevine et le verrou d'instance unique (le second lancement ; sans un dossier de données à elle, `--user-data-dir`, la passe refuse de démarrer) ;
- la question avant de quitter, l'effacement des sites à la fermeture, la restauration des fenêtres au lancement, la feuille d'accueil ou de nouveautés, les notices de persistance ;
- les tâches de fond du lancement : copies de la session (et la copie à la fermeture), mise à jour automatique, seuil mémoire des fenêtres, balayage des fonds d'espace inutilisés, effacement à la fermeture rejoué ; la suite `perf` les démarre, puisqu'elle les mesure ;
- le raccourci global de la mini-fenêtre, le glissement de la barre latérale, le suivi de l'écran de la fenêtre (le facteur du panneau ouvert sur un autre écran, et la notice sur la taille des panneaux d'un écran très large ou très petit), le téléchargement des listes du bloqueur (toute liste échoue aussitôt, avec sa raison) ;
- le journal des rejets et des exceptions non capturés du processus principal (la passe a le sien).

Ce qu'il remplace : les téléchargements vont dans le dossier de données de la passe (`downloads/`), jamais dans Téléchargements ; ils se font en un seul flux, comme lorsque la reprise après un redémarrage est allumée ; l'historique est écrit d'un bloc, le processus attendant la fin de l'écriture, au lieu d'être écrit à côté puis mis en place.

De même, `smoke-run.ts` fixe l'apparence sombre et la taille à 100 % (les vérifications des Réglages ouvrent « Plus de réglages » de la page qu'elles lisent) : le thème clair, « Automatique » et les tailles par écran ne sont éprouvés que par leurs propres vérifications. Une partie est reprise par les tests E2E (question avant de quitter, restauration des fenêtres, premier lancement, mise à jour) ; le reste (Touch ID, Widevine, ouverture d'une autre application, second lancement) se vérifie à la main avant une publication.

Moteur de secours : si une compatibilité complète avec les extensions devient indispensable, le même port permet d'écrire un second moteur (Chromium patché ou CEF) sans toucher au reste.

Garde du port : `src/main/engine-port.test.ts` échoue si un nouveau fichier de `src/main/engine/` ou de `src/shared/` importe `electron` (ou une bibliothèque faite pour lui), et si un fichier de sa liste figée n'en importe plus (la liste ne fait que rétrécir).

## Extensions et performance : deux pistes

Mesure faite sur Electron 45 + `electron-chrome-extensions` 4.9.0, avec **Chrome Toolkit chargé tel quel** (21 modules, service worker module) :

- Service worker démarré, **aucune erreur console**.
- 73 API présentes et appels réels réussis : `storage.local/session/sync`, `alarms`, `tabs.query/create/remove/update/sendMessage`, `windows`, `scripting` (dont `registerContentScripts`), `contextMenus`, `offscreen`, `cookies`, `system.memory`.
- **`declarativeNetRequest` était appliqué par Electron lors de cette mesure** (le script demandé avant la règle, témoin, n'arrivait plus au serveur après) : aucune session ne portait alors d'écouteur `session.webRequest`. Depuis le 5 novembre 2026 chaque session de pages en porte un (garde des fichiers locaux, bloqueur intégré), et Electron saute alors les règles des extensions. Lucium les applique donc lui-même, dans ces mêmes relais (`src/shared/net-rules.ts`, `src/main/engine/extension-net.ts`) : le module `ad-blocker` bloque de nouveau. Les écouteurs bloquants d'une extension Manifest V2 (`webRequestBlocking`) sont interrogés dans les mêmes relais, après les règles déclaratives, et leurs réponses appliquées : une requête les attend une seconde au plus, et seulement quand le filtre d'un tel écouteur la couvre (`src/shared/web-request-blocking.ts` ; ordre, fusion et limites dans `docs/extensions-compatibilite.md`, « Écouteurs bloquants (Manifest V2) »).
- **Absentes dans Electron seul** (la couche ci-dessous en fournit une partie) : `tabs.discard`, `tabs.group/ungroup`, `tabGroups`, `debugger`, `sidePanel`. **Toujours absentes** : `sessions`, `management.getAll` ; `tabs.duplicate`, `tabs.move` (accepté, sans effet) et `tabs.highlight` (le premier onglet seulement) sont fournies par la couche ci-dessous, avec les écarts de `docs/extensions-compatibilite.md` (`history`, `bookmarks` et `browsingData` sont fournies par la couche ci-dessous ; `captureVisibleTab` aussi).

D'où la stratégie :

1. **Piste A, compatibilité** : charger les extensions MV3 telles quelles (menu *Extensions › Ajouter une extension…*, bouton « Charger une extension… » des Réglages, ou `LUCIUM_EXTENSIONS=chemin1:chemin2`). Couvre l'essentiel de Chrome Toolkit.
2. **Piste A+, couche de compatibilité** (`src/preload/extension-shims.ts`, `src/main/shell/extension-shims.ts`, `src/main/engine/ece-router.ts`) : un script de précharge, enregistré deux fois (avant et après celui de la bibliothèque d'extensions), ajoute ce que Electron ne fournit pas et corrige ce que `electron-chrome-extensions` fait mal. Une API n'existe que pour l'extension qui a déclaré sa permission, et le processus principal le revérifie à chaque appel et à chaque événement, avec le manifeste de l'appelante (`shimAllowed` et `shimEventAllowed` pour ce que Lucium fournit, `restrictLibraryApis` et `src/shared/extension-access.ts` pour ce que fournit la bibliothèque). **Qui appelle** : la bibliothèque déduit l'extension appelante de l'identifiant que le message annonce et ne le compare jamais à l'expéditeur, et son objet `window.electron` reste lisible dans la page (la propriété n'est pas supprimable) ; `restrictLibraryApis` sert donc chaque appel, tous les gestionnaires, au nom de l'extension dont l'expéditeur est réellement la page ou le worker (hôte de `chrome-extension://…` de `sender.getURL()` ou de `scope`, `extensionOfSender`), et réserve `browserAction.activate`, `getState`, `addObserver` et `removeObserver` à l'interface de l'application (session par défaut). L'écoute d'un événement passe par un autre canal (`addExtensionListener`, message `crx-add-listener`), où la bibliothèque inscrit la page sous l'extension que le message nomme : une page d'une extension recevait ainsi les événements d'une autre, dans la version de celle-ci (adresses et titres des onglets, cookies, clics sur ses menus). `restrictLibraryApis` n'inscrit une page que pour sa propre extension ; l'écoute d'un worker reste acceptée telle quelle, car la bibliothèque n'en envoie les événements qu'au worker de l'extension nommée (`ece-router.test.ts`, et `ece-listeners.test.ts` sur la vraie bibliothèque, qui échoue aussi si une version de la bibliothèque ajoute une fonction à `window.electron` ou un canal). Un cadre d'extension inséré dans une page web n'est pas jugé par son propre cadre (la bibliothèque ne transmet que le contenu web) : ses appels à ces gestionnaires sont refusés. Une adresse d'hôte écrite dans `permissions` ne vaut accès que pour un manifeste V2 (`hostPatternsOf`) : en V3 Chromium l'ignore, donc l'accès, la capture d'onglet et la feuille de revue aussi. Sont couverts : `cookies` (permission **et** permission d'hôte pour l'adresse ; `getAll` ne rend que les cookies des sites autorisés), `webNavigation`, `contextMenus`, `notifications`, `topSites`, `privacy`, `webRequest`, `downloads` (espace de noms absent sans la permission, appel et événements refusés), `tabs.insertCSS` (hôte ou onglet « remis » à l'extension), `tabs.captureVisibleTab` (`<all_urls>`, ou `activeTab` **et** un onglet remis par un clic sur l'icône ou le raccourci, valable jusqu'à ce que l'onglet change de site ou se ferme), `debugger`, `tabGroups`, `sidePanel`, `identity`, `nativeMessaging`. `tabs` et `windows` existent pour tous, mais l'adresse, le titre et l'icône d'un onglet (résultats et événements, fenêtres comprises) ne sont montrés qu'avec `tabs`, une permission d'hôte pour la page ou `activeTab` sur cet onglet ; un filtre `tabs.query({ title, url })` ne retrouve pas ce qu'on ne peut pas lire. Une permission facultative (`optional_permissions`, `optional_host_permissions`) n'est accordée que par l'utilisateur : `permissions.request`, après un clic ou une touche, ouvre la feuille de revue réduite à ce qui est demandé ; la réponse est gardée par profil (`src/main/engine/optional-grants.ts`, règles pures dans `src/shared/optional-permissions.ts`), jamais au-delà de ce que le manifeste liste comme facultatif, listée et retirable dans la page Extensions. Ce qui est accordé est ajouté au manifeste que lisent ces règles (`ElectronEngine.manifests`, `withGranted`), et `permissions.contains`, `getAll`, `remove`, `onAdded` et `onRemoved` répondent d'après lui ; Chromium, lui, ne connaît que le manifeste des fichiers (limites dans `docs/extensions-compatibilite.md`). Chaque appel porte le profil du contexte qui l'a fait : une extension n'atteint que les onglets, groupes et téléchargements de son profil, et ce qu'elle ouvre (`tabs.create`, `windows.create`, fenêtre `popup`) naît dans un espace de ce profil. Un onglet ou une fenêtre ouverts par une extension ne chargent qu'une page web, `about:blank` ou une page de **cette** extension (jamais `file:`, `data:`, `blob:`, `view-source:`, la page d'une autre extension ni celles du navigateur).
   - **`chrome.sidePanel`** : un vrai **panneau docké à droite**, qui se ferme avec `window.close()` et que `chrome.runtime.getContexts` annonce comme contexte `SIDE_PANEL`.
   - **`chrome.debugger`** : `attach`, `detach`, `sendCommand`, `getTargets`, `onEvent`, `onDetach`, sur le débogueur DevTools d'Electron. ## Extensions du Chrome Web Store et extensions par profil

Parcours : l'utilisateur ouvre une page du Chrome Web Store dans un onglet (menu *Extensions › Ouvrir le Chrome Web Store*, barre de commandes, Réglages › Extensions et outils › Plus de réglages › Extensions), clique le bouton d'installation de la fiche, lit la **feuille de revue** (ce que le paquet demande, en français, permissions larges en tête, avertissement et focus sur « Annuler » quand l'accès est étendu), accepte : l'extension s'installe dans **le profil de l'espace de l'onglet** et son icône apparaît dans la barre d'actions de ce profil seulement. Une fenêtre privée n'a ni pont ni extension. Un autre profil ne l'exécute pas ; chaque profil a sa case (Réglages › Extensions et outils › Extensions) et le menu de l'icône (clic droit) propose « Désactiver dans ce profil » et « Désinstaller… » (la désinstallation demande une confirmation). La rangée « Extensions » d'Infos et réglages du site a le même pouvoir sur les extensions du profil de l'onglet, par le menu de chaque tuile (« Désactiver » ou « Activer », « Recharger », « Gérer… », « Retirer… ») : la question de « Retirer… » est posée dans le panneau, et la requête `uninstall` qui suit porte `asked: true` pour que la boîte du processus principal ne la repose pas (`docs/fonctions.md`).

**Bibliothèque** : `electron-chrome-web-store` 0.13.0 (MIT, du même auteur que `electron-chrome-extensions`), chargée **à la demande** (jamais si le réglage est désactivé). Lue dans `node_modules` : API `installChromeWebStore({ session, extensionsPath, autoUpdate, loadExtensions, beforeInstall, … })`, `downloadExtension`, `installExtension`, `uninstallExtension`, `updateExtensions` ; un script de page (`electron-chrome-web-store/preload`) fournit `chrome.webstorePrivate` à la page du Store, et dix-neuf canaux IPC répondent à la page. Compatible avec Electron 45 et avec un moteur d'extensions par profil (un appel par session). **Réseau** : `https://clients2.google.com/service/update2/crx` (paquet, redirigé vers `clients2.googleusercontent.com`), `https://update.googleapis.com/service/update2/json` (mises à jour) et l'adresse d'icône que **la page** donne (images de `googleusercontent.com`) ; rien d'autre, aucune télémétrie. Ces requêtes partent de la pile réseau d'Electron, dans la session par défaut de l'application (`web-store-transport.ts`, bâti sur `net.request` comme le `requestFetch` des icônes), et non du `fetch` de Node que la bibliothèque préfère (« until net.fetch crash is fixed », bogue antérieur à Electron 45) : le proxy de l'utilisateur et le DNS chiffré s'appliquent comme pour le reste de l'application ; `net.fetch` n'est pas utilisé parce que son mode `redirect: 'manual'` échoue, alors que le garde juge lui-même chaque redirection. **Exigences** : la page doit être sur `https://chromewebstore.google.com` ; le script de page doit être lisible par Chromium (hors `app.asar` : `asarUnpack` dans `electron-builder.yml`, chemin réécrit dans `web-store.ts` ; non vérifié sur un `.app` empaqueté) ; Manifest V3.

**Ce que la bibliothèque fait mal, et ce que Lucium met autour** (`src/main/engine/web-store.ts`, `web-store-network.ts`, `crx-scan.ts`) :
1. Elle contrôle l'origine de la page avec `startsWith`, côté page et côté processus principal : `https://chromewebstore.google.com.evil.example` passe. Ses canaux IPC sont enregistrés **à travers une barrière** (`gate`) : origine exacte (`isStoreOrigin`), image principale de la page, un onglet à nous, réglage activé, profil attaché, et pour l'installation et la désinstallation un clic ou une touche de l'utilisateur à l'instant. Si elle n'enregistrait plus ses canaux par `ipcMain.handle`, l'installation est refusée avec une erreur explicite.
2. Le manifeste que montrerait la feuille vient de **la page**. La feuille est faite avec le manifeste du **paquet téléchargé** (dossier d'attente `WebStoreStaging/`, déplacé dans `WebStoreExtensions/<profil>/<id>/` seulement si l'utilisateur accepte ; la bibliothèque trouve alors l'extension installée et ne fait que la charger : pas de second téléchargement).
3. Elle appelle `fetch` avec l'adresse d'icône donnée par la page (SSRF), sans limite de taille ni de durée, et suit les redirections sans contrôle. Pendant son chargement son `fetch` est remplacé par un **garde** : https seulement, domaines du Store seulement (`google.com`, `googleapis.com`, `googleusercontent.com`, `gstatic.com`), chaque redirection rejugée, réponses bornées (paquet 128 Mio, mises à jour 1 Mio, image 2 Mio), délais, et un paquet est lu avant d'être décompressé (`crx-scan.ts` : taille, nombre d'entrées, chemins qui sortent du dossier, doublons même à la casse près, archive chiffrée ou ZIP64, bombe de décompression, y compris une entrée qui annonce une taille nulle mais contient des données, manifeste borné). **Les signatures** de l'en-tête CRX3 sont vérifiées (`crypto`, `sha256_with_rsa` et `sha256_with_ecdsa` sur `"CRX3 SignedData\0" + longueur + données signées + archive`) : la bibliothèque ne fait que comparer le hachage d'une clé à l'identifiant demandé, si bien que l'archive n'était garantie que par TLS ; un paquet sans signature, altéré, ou dont aucune signature ne vient de la clé de l'identifiant qu'il déclare est refusé avant d'être déballé. Comme Chromium, Lucium exige aussi la preuve « éditeur » du Store : une signature valide par la clé avec laquelle le Chrome Web Store signe chaque paquet qu'il publie (`STORE_PUBLISHER_KEY_SHA256`, l'empreinte que Chromium écrit dans `components/crx_file/crx_verifier.cc`, `kPublisherKeyHash`). Sans elle, le paquet est refusé (`not-from-store`) : la clé de l'extension seule établit que l'archive est celle de son propriétaire, pas qu'elle a passé par le Store. Un paquet que Lucium fait lui-même (Empaqueter une extension, `crx-pack.ts`) n'en demande pas. Le contrôle moteur `webstore` sert des paquets signés par une clé d'éditeur de test, qu'il nomme au garde (`useTestNetwork`) ; le Store réel n'est lu que par `webstore-live`. Les dossiers d'attente d'une installation interrompue sont effacés une fois, au premier envoi des réglages (`WebStore.configure`).
4. Elle lance des vérifications de mise à jour seule (au démarrage et toutes les cinq heures) : désactivé (`autoUpdate: false`). Les mises à jour se font **à la demande** (Réglages › Extensions et outils › Plus de réglages › Extensions, « Rechercher maintenant ») ou à un rythme choisi (réglage `webStoreUpdates` : à la demande par défaut, chaque jour, chaque semaine). Une mise à jour qui demande **plus** de permissions que la version installée (`addedAccess`) n'est jamais appliquée seule : le garde la refuse, Réglages la liste (« Examiner la mise à jour… ») et la feuille ne montre que ce qui est nouveau.
5. Elle désinstalle sans demander : la désinstallation demandée par la page du Store est transformée en demande de confirmation par le shell.
6. Elle charge les extensions elle-même, sans passer par le moteur : ici le moteur charge (`loadExtensions: false`) et enregistre tout ce que la session charge, quel que soit l'auteur du chargement (événement `extension-loaded`).

**Être reconnu par le Store comme un navigateur compatible** (sur la fiche d'une extension, le Store affichait une bannière invitant à changer de navigateur pour installer des extensions et des thèmes, et un bouton grisé). Constaté sur la vraie fiche (Dashlane, lecture seule, `LUCIUM_SMOKE_ONLY=webstore-live`, Internet nécessaire, jamais dans la chaîne) et dans le code public de la page : (1) le **bouton « Ajouter à … »** dépend du pont `chrome.webstorePrivate` (`chrome.management` et `beginInstallWithManifest3` doivent exister) : la bibliothèque le fournit, il est actif ; sans elle il est grisé. (2) La **bannière** vient d'un état de la page (« navigateur non reconnu ») décidé par `JS(Kk)` : à partir de la version **142.0.7430.0** (version lue par `getFullChromeVersion`, donc fournie par notre pont), la page ne croit plus son propre test du *user agent* mais un **verdict du serveur** (un drapeau dans les données de la page) que le serveur ne donne qu'aux navigateurs qu'il reconnaît ; en dessous, elle fait son propre test (la forme du *user agent*, que le nôtre passe). Essayés **sans effet** sur la bannière : une marque de navigateur ajoutée dans `Sec-CH-UA` (en-têtes ajoutés à la requête de la page, sur laquelle Chromium dans Electron n'en met aucun ; il en met sur les autres requêtes, voir « Indices du client » ; essai non gardé), la même marque dans `navigator.userAgentData.brands`, les objets `chrome.loadTimes`, `chrome.csi`, `chrome.app`. Seul levier trouvé : le pont annonce à la page de la boutique **la dernière version avant le seuil** (`141.0.7389.0`, `versionForStore` dans `src/shared/web-store.ts`) au lieu de `156.0.8078.48` ; la page revient à son test du *user agent* : **la bannière disparaît** et le bouton « Ajouter à … » reste actif (vérifié en chargeant la fiche réelle, lecture seule, sans installation). Effet : une réponse, à l'origine exacte du Web Store seulement (la barrière IPC refuse les autres), jamais pour un autre site ; aucune en-tête ni propriété `navigator` n'est modifiée, donc rien ne change pour les autres sites (le *user agent* « Chrome/156 » des pages est celui qui existait déjà). Inconvénient : la boutique croit à une version 141, ce qui peut lui faire refuser une extension qui exige une version plus récente (message d'incompatibilité de version) ; le seuil est une valeur de la page, que l'éditeur du Store peut changer : c'est alors la vérification en direct qui le dit.

**Réglages** (Extensions et outils › Plus de réglages › Extensions) : `webStoreInstall` (défaut **activé** : aucune requête vers le Store n'a lieu sans une action de l'utilisateur ; le réglage permet de s'en retirer, voir la réserve ci-dessous) et `webStoreUpdates` (défaut **à la demande**). Une sauvegarde restaurée ne change ni l'un ni l'autre. Les extensions déjà installées continuent de fonctionner quand l'installation est désactivée. L'état « désactivée dans ce profil » est dans `settings.profiles[profil].disabledExtensions` (normalisé par `state-clean.ts` / `cleanProfileOverrides`, appliqué au chargement : une extension désactivée n'est pas chargée dans le profil).

**Réserve sur les conditions d'utilisation du Web Store** : les conditions d'utilisation du Chrome Web Store (<https://developer.chrome.com/docs/webstore/terms>, version lue en octobre 2026) ne restreignent pas explicitement les autres navigateurs, mais définissent les produits comme créés pour le navigateur de l'éditeur du Store (§ 5.2, licence) et interdisent l'accès au Store par un autre moyen que l'interface fournie par son éditeur, sauf accord séparé (§ 4.4.2). Plusieurs autres navigateurs, basés sur Chromium ou non, installent des extensions du Chrome Web Store. Lecture prudente : usage courant, sans interdiction expresse, mais une zone grise contractuelle que l'éditeur du Store peut resserrer ; ce n'est pas un avis juridique. Mesures prises : le Store s'ouvre dans un onglet (interface fournie par son éditeur), son catalogue n'est pas aspiré, aucun écran du Store n'est contourné, le chargement d'une extension non empaquetée reste possible, et le réglage « Autoriser l'installation d'extensions depuis le Chrome Web Store » permet de s'en retirer d'un geste.

**Vérification** : unitaires (feuille de permissions, état par profil, garde, paquets, ledger, actions) ; moteur `LUCIUM_SMOKE_ONLY=webstore` (`src/main/smoke-webstore.ts`) avec un faux Store entièrement local : une page servie pour l'origine du Store par la session du profil, un serveur qui joue le service de mise à jour et l'hôte de paquets, des paquets fabriqués par le test. **Jamais d'extension réelle installée depuis Internet pendant les essais.** L'installation de bout en bout depuis le vrai Web Store est une vérification manuelle : ouvrir *Extensions › Ouvrir le Chrome Web Store*, choisir une extension Manifest V3 (par exemple Vimium), « Ajouter à Lucium », lire la feuille, accepter, vérifier l'icône dans la barre d'actions, changer d'espace de profil (l'icône n'y est pas), désactiver puis réactiver dans Réglages, désinstaller par le clic droit sur l'icône ; si un téléchargement échoue, le journal dit quel hôte le garde a refusé.

## La page Extensions en onglet (`lucium-ui:`)

La page Extensions (`chrome://extensions`) est un onglet de la fenêtre, pas une fenêtre à part. Ce qui suit est le résumé ; les décisions, les écarts et ce qui reste à voir dans un vrai Electron sont dans `docs/design/extensions-en-onglet.md`.

**Le bogue qu'on ne refait pas : `startsWith`.** La bibliothèque du Chrome Web Store (section précédente) jugeait l'origine d'une page avec `startsWith` : `https://chromewebstore.google.com.evil.example` passait. Un onglet qui reçoit une API privilégiée a le même risque, aggravé : la page de l'onglet peut changer, avoir des cadres, être redirigée. Donc : l'adresse de la page, `lucium-ui://extensions/`, est reconnue sur **le texte brut**, dans une seule écriture canonique (`internalPageParts`, `src/shared/internal-page.ts` : ASCII, schéma et hôte en minuscules, ni identifiants, ni port, ni barre oblique inverse, puis `/` ou `/shortcuts`) ; l'origine est comparée à l'**égalité** (`isInternalOrigin`) ; aucune comparaison de préfixe nulle part. Les tests d'adversaire (`lucium-ui://extensions@evil`, `lucium-ui://extensions.evil.com`, `LUCIUM-UI://EXTENSIONS`, `lucium-ui:extensions`, un port, des identifiants, des barres obliques inverses, des encodages) sont dans `internal-page.test.ts` et `internal-page-model.test.ts`.

**Quatre barrières, aucune n'est la seule.**
1. *La requête* (`src/shared/internal-serve.ts`, `src/main/engine/internal-pages.ts`) : chaque session de profil sert le schéma `lucium-ui:` avec `protocol.handle`, à partir de la liste des fichiers que le document de la page nomme ; une session de fenêtre privée ou de conteneur refuse tout. La règle ne repose pas sur des en-têtes qu'Electron peut ne pas donner au gestionnaire (`Sec-Fetch-*`, `Referer` d'une page en `no-referrer`) : deux secrets de la session, faits au hasard et jamais écrits. *La clé* : un fichier n'est servi que sous `lucium-ui://extensions/<clé>/assets/…`, et seul le document, servi avec ses références réécrites sous la clé (`internalDocumentOf`), les nomme ; une page du web ne peut charger aucun fichier, donc `onload` ne lui apprend ni que Lucium est là ni sa version. *Le secret du chargement* : le document n'est servi qu'à une requête qui porte `x-lucium-page-load`, que `loadURL` du moteur ajoute à son propre chargement et à aucun autre (un rechargement de la page en est un). Les en-têtes (`Sec-Fetch-*`, `Origin`, `Referer`, `Referrer-Policy: same-origin` du document) seraient une seconde couche si le moteur les donnait : **Vérifié le 13 novembre 2026, Electron 45.2.1 (macOS) : le gestionnaire de `protocol.handle` ne reçoit ni `Sec-Fetch-*`, ni `Origin`, ni `Referer` ; la clé de session (128 bits aléatoires, jamais écrite) et le secret du chargement du shell sont les seuls murs ; la clé n'est révélée qu'au document que le shell charge.** Une page du web qui saurait la clé chargerait un fichier public du bundle, jamais le document ni l'API ; le contrôle moteur l'enregistre et signale (sans échouer) toute version d'Electron qui donnerait ces en-têtes. La réponse porte `frame-ancestors 'none'`, `X-Frame-Options`, `Cross-Origin-Resource-Policy`.
2. *Le préchargement* (`src/preload/internal-extensions.ts`) : enregistré pour `lucium-ui://extensions/*` seulement (pas du tout si cette limite est refusée), et qui ne donne `window.lucium` qu'à l'origine exacte, dans l'image principale ; huit appels, canaux `lucium-ui:*`.
3. *La porte du processus principal* (`src/shared/internal-gate.ts`, `src/main/shell/internal-page-ipc.ts`) : pour chaque message, origine exacte, image principale, document de la page, onglet de cette fenêtre que l'état tient toujours sur la page, ni privé ni en conteneur, fenêtre ordinaire, session de profil, application déverrouillée. Toute autre source est refusée avec une ligne au journal. Elle reçoit un instantané réduit (`internal-snapshot.ts`) : les extensions et les réglages que la page lit.
4. *La navigation* (`src/main/engine/electron-page.ts`) : `isNavigable` ne connaît pas le schéma ; seul `loadURL` du shell l'accepte (`isShellNavigable`). Aucune page du web n'y envoie l'onglet (lien, `will-redirect`, `will-frame-navigate`, `window.open`), et la page ne va nulle part. Le moteur suit aussi la navigation **en cours** vers la page (`HeadingNavigation`) : `chrome.debugger` ne s'attache ni à une page qui est sur elle, ni à une page qui y va, et la session déjà attachée est coupée quand le shell demande la page, pas quand elle valide. Un onglet qui revient à la page par Précédent est de nouveau sur elle dans l'état (`tab/update` avec `allowInternalPages`, que seul le processus principal envoie), et un document refusé (403) est redemandé une fois par la voie du shell.

**Le modèle.** L'onglet s'ouvre par `tab/open` avec `allowInternalPages` (que l'interface ne peut pas envoyer), jamais en onglet privé ni en conteneur ; il survit à une restauration de session, n'entre ni dans l'historique, ni dans l'archive, ni dans les sessions, ni dans les favoris, et n'a pas d'hôte. `Browser.openExtensionsTab` est le seul chemin d'ouverture. L'adresse que l'on voit, copie comprise, est `chrome://extensions` (`displayAddress`). Pour les extensions, c'est une page du navigateur : aucun motif d'hôte, aucun `activeTab`, aucune capture ; une extension qui a `tabs` lit `chrome://extensions/` (dans `chrome.tabs`, `chrome.webNavigation` et `chrome.debugger.getTargets` ; une autre n'est pas dite que l'onglet est là), et les entrées de `contextMenus` ne sont pas dans le menu de la page. L'adresse de la page n'est l'ancre d'un onglet épinglé que pour l'onglet qui est sur elle, et ne renvoie jamais un onglet privé ou en conteneur vers elle (`anchorOf`). L'instantané réduit est envoyé par `Page.sendToDocument` (le port du moteur).

**Risques restants** (détail dans `docs/design/extensions-en-onglet.md`). Tout ce qui ferait sortir la clé du document : une page compromise (la politique de contenu, l'absence de lien et les gardes de navigation lui ferment tout canal, sauf l'adresse de son onglet, dont la requête n'est pas bornée aux profils connus), les journaux (le gestionnaire n'écrit jamais la clé ; les lignes `[ui]` de la page restent dans sa console, le relais n'étant branché que pour les surfaces de l'interface), les extensions (elles ne lisent que `chrome://extensions/`) et un `Referer` sortant (la page n'a aucun lien ni aucune lecture de l'adresse de ses fichiers, le document est servi en `Referrer-Policy: same-origin`, et l'adresse de la page ne contient jamais la clé : tout cela est testé).

**Vérification.** Unitaires (adresse et adversaires, requêtes, liste de fichiers, porte, instantané, préchargement, gestionnaire par type de session, gardes du moteur, ouverture) et un contrôle moteur écrit, `src/main/smoke-extensions-page.ts` (suite `extensions-page`, hors chaîne), qui n'a pas été lancé pour cette version : il journalise les en-têtes que le gestionnaire reçoit, tente de charger le document et les fichiers depuis une page du web (référent par défaut et `no-referrer`, `<script>`, `<img>`, `<link>`, `<iframe>`) et vérifie le rechargement et le Précédent.

### Découpage des gros fichiers

Les gros fichiers sont découpés par responsabilité ; chaque module garde son API (ré-exports).

- **`shell/browser.ts`** : la classe `Browser` est une chaîne de classes abstraites, une par responsabilité ; chacune étend la précédente et n'ajoute que des méthodes. `browser-base.ts` porte tous les champs, le constructeur, et les déclarations `abstract` des méthodes qu'une couche basse appelle plus haut. Ordre : base → dialogs (questions des pages et des extensions) → contexts (cookies, contexte privé, conteneurs) → sleep (veille : gel, libération, balayage) → reload (« Actualiser tous les onglets », onglets qui ne répondent plus, rechargement automatique, réveil au lancement) → capture (captures, historique, ouvreurs des surfaces) → site (Retouches, Gomme, données de site, sombre, look) → overlay (calques, ⌃Tab, glisser de vue partagée) → commands (commandes de page et d'onglet) → resources (listes du gestionnaire de tâches et du panneau des ressources) → translate (résumé, traduction) → panels (Coup d'œil, panneau latéral, volets web) → downloads (téléchargements, PDF, PiP) → annotation (annotation, verrou) → publish (snapshots) → network (moteur, bloqueur, réseau) → actions (actions sur l'état, profils) → media (son et médias) → tools (économiseur de batterie, dossiers en direct, surveillance d'une page, outils dans la page) → pages (cycle de vie des pages) → layout (mise en page) → `Browser` (`browser.ts` : groupe de fenêtres, `start`/`stop`, snapshot). Un membre lu par une autre couche est `protected`. Les tests qui lisent le source de la classe passent par `browserSource()` (`browser-source.test-support.ts`). Les onglets vides sont dans `shell/blank-tab-watch.ts` (classe `BlankTabWatch`) ; les messages non lus des titres d'onglets, tenus à travers les titres qui clignotent, dans `shell/unread-watch.ts` (classe `UnreadWatch`, règles pures dans `shared/tab-messages.ts`).
- **`engine/electron-engine.ts`** : `ElectronPage` est dans `engine/electron-page.ts` (ré-exportée par `electron-engine.ts`), `EphemeralScope` dans `engine/ephemeral-scope.ts`. Le port (`engine/types.ts`) ne change pas ; `electron-page.ts` est la moitié Page de l'implémentation. `ElectronPage` est elle aussi une chaîne de classes abstraites, une par responsabilité : `electron-page-base.ts` (les champs, ce que la page dit d'elle-même, ses cadres, ses feuilles de style, la place de sa vue) → `-navigation` (chargement, historique, touches, impression, mode lecture, export Markdown, lecteur PDF, outils de développement, zoom, recherche) → `-content` (scripts et mondes isolés, formulaires, captures, WebRTC, apparence demandée, session de débogage d'une extension, `prompt()`, mots de passe) → `-media` (outils dans la page, lecture à voix haute, image dans l'image, vidéo flottante, volume) → `-lifecycle` (veille, gel, vue prêtée ou déplacée, fin) → `ElectronPage` (`electron-page.ts` : le constructeur, qui branche tous les écouteurs, les liens vers d'autres applications et le menu contextuel). Une seule méthode est déclarée `abstract` pour être appelée d'une couche plus basse (`releaseHeld`). Les scripts injectés, les mondes isolés et les bornes sont dans `electron-page-scripts.ts`. C'est un découpage en fichiers : l'objet reste un seul à l'exécution, avec les mêmes champs partagés.
- **`index.ts`** : l'aiguillage des tests moteur (`--smoke`, `LUCIUM_SMOKE_ONLY`) est dans `smoke-run.ts`, chargé par `import()` seulement avec `--smoke` (morceau `smoke*.js`, exclu du paquet comme les suites et leurs aides `*test-support*`). `--smoke` n'existe que depuis les sources : l'application construite ne le lit pas (`isSmokeRun`, `runtime.ts`) et refuse de démarrer avec lui, comme avec le protocole DevTools (`--remote-debugging-port`, `--remote-debugging-pipe`) et les commutateurs qui affaiblissent TLS, la résolution des noms, le trousseau ou le bac à sable (`REFUSED_SWITCHES`) : une ligne `[launch] refused` sur la sortie d'erreur, code de sortie 1. Elle retire aussi de son environnement `LUCIUM_E2E` et les `LUCIUM_SMOKE_*`.
- **`shared/sidebar.ts`** : le type `Action` (et `Ctx`) est dans `sidebar-actions.ts`, la création, le chargement et le nettoyage de l'état dans `sidebar-state.ts`, les sélecteurs dans `sidebar-selectors.ts` ; `@shared/sidebar` les ré-exporte.
- Utilitaires partagés : `shared/record.ts` (`isRecord`), `shared/clamp.ts` (`clamp`, `clamp01`, `clampOr`), `shared/versions.ts` (`compareVersions`), `urlHostname` dans `shared/url.ts`.
- **Le port (`engine/types.ts`)** est écrit par capacité dans les fichiers `engine/port-*.ts`, que `types.ts` ré-exporte (`export *`) : le reste de Lucium n'importe que `types.ts`. `Page` (`port-page.ts`) joint par `extends` une interface par capacité : `PageNavigation` (chargement, historique, échec, recherche, zoom), `PageDocument` (impression, PDF, enregistrement, mode lecture, Markdown, images, captures), `PageScripts` (feuilles de style, scripts, mondes isolés, formulaires, outils dans la page), `PageDevTools` (outils de développement, protocole de `chrome.debugger`), `PageInput` (focus, touches), `PageMedia` (`port-media.ts` : son, lecture à voix haute, image dans l'image, vidéo flottante), `PageView` (`port-windows.ts` : place dans les fenêtres, vue prêtée), `PageLifecycle` (processus, veille, fin). `Engine` (`port-engine.ts`) joint de même `EnginePages` (les pages et ce qu'elles peuvent faire : permissions, fenêtres surgissantes, lecture automatique, matériel), `EngineExtensionRuntime` (`port-extensions.ts` : shims, événements, onglets, workers), `EngineExtensionTools` (`port-extension-tools.ts` : chargement, liste, Web Store, page Extensions), `EngineNetwork` (`port-network.ts`), `EngineDownloads` (`port-downloads.ts`) et `EngineStorage` (`port-storage.ts` : données de site, cookies, cache, dossiers des profils et des conteneurs) ; `openEphemeral`, `openContainer` et `EphemeralEngine` restent dans `port-engine.ts`. `PageEvents` est dans `port-page-events.ts`. Aucun type n'a changé : seuls les fichiers et les noms des interfaces de capacité sont nouveaux.
- **Menus** : `shell/menu.ts` (`buildMenu`) assemble la barre des menus dans son ordre fixe ; ce que tous les menus lisent est calculé une fois par `menuBarKit` (`shell/menu-bar-kit.ts`, avec `MenuActions` et `MenuOptions`, ré-exportés par `menu.ts`), et chaque menu est construit dans son module : `menu-bar-app.ts` (Lucium, Extensions, Fenêtre, Aide), `menu-bar-file.ts`, `menu-bar-edit.ts`, `menu-bar-view.ts`, `menu-bar-tabs.ts` (Espaces, Onglets, Archive). `shell/context-menus.ts` (`showMenu`, `menuItems`) aiguille vers un module par sorte de menu contextuel : `context-menu-tab.ts` (onglet et sélection multiple), `-favorite`, `-toolbar` (pages derrière Précédent et Suivant, extensions du bouton «, contraste de la page), `-download`, `-split`, `-space`, `-folder` ; ce qu'ils partagent (icônes, blocs, presse-papiers, `moveTabsToSpace`, ré-exporté) est dans `context-menu-kit.ts`. `menu-templates.test.ts` garde la trace de chaque menu tel qu'il est construit, pour plusieurs états (le gabarit entier, entrée par entrée) : elle a été prise avant ce découpage et prouve qu'il ne change aucune entrée ; un changement voulu d'un menu se relit dans sa différence, puis la trace est reprise (`-u`).
- **Composition de `Browser` et `ElectronPage` : plan pour un lot après la 1.1.0** (non fait : les chaînes de classes partagent tous leurs champs, et une couche ne devient un objet à part que si aucun champ partagé ne change de propriétaire). Une couche par commit, dans cet ordre ; chacune garde ses méthodes publiques sur la classe, en délégations d'une ligne, pour que les appelants (IPC, menus, tests) ne changent pas, et la chaîne perd la couche (la suivante étend la précédente).
  1. **`BrowserResources`** (`browser-resources.ts`, listes du gestionnaire de tâches et du panneau des ressources) devient un objet `ResourceLists` tenu par `Browser`. Aucune autre couche n'appelle ses méthodes, et elle ne possède aucun champ : elle lit `store`, `engine`, `group`, `leader`, `ownerOf`, `isShown`, et pour chaque fenêtre du groupe `win`, `store`, `pages`, `frozen`, `windowNames`, `isTabLocked`, `sleepNow`, `dispatch`. Ce qu'elle lit d'une autre fenêtre est `protected` aujourd'hui : l'hôte qu'on lui donne l'expose en lecture (une interface `ResourceHost`), sans déplacer un champ.
  2. **`ElectronPageContent`** (`electron-page-content.ts`, scripts, mondes isolés, formulaires, `prompt()`, session de débogage d'une extension) devient un objet `PageContent` tenu par la page. Aucune autre couche ne l'appelle. Deux champs ne servent qu'à elle et passent dans l'objet : `debugAllowUrl` et `extensionDebug`. Les autres restent à la base et lui sont prêtés : `colorScheme` (créé par le constructeur d'`ElectronPage`, rafraîchi à chaque navigation), `dialogGuard` (remis à zéro par le constructeur à chaque document), `errors`, `gone`, `webContents` (lus seulement).
  3. Ensuite seulement, couche par couche après relecture de leurs champs : `BrowserTranslate` (son champ `summaryTabs` est aussi lu par `browser-base.ts` et nettoyé par `browser-layout.ts` : il reste à la base), puis `BrowserDownloads` (appelée par `browser-dialogs.ts` et `browser.ts`). Les couches qui lisent plus de 40 membres des autres (`BrowserPages`, `BrowserLayout`, `BrowserOverlay`, `Browser` lui-même, et `ElectronPage`, qui branche tous les écouteurs) restent des couches.
  Preuve de chaque pas : `pnpm typecheck`, le `npx vitest run` complet (les tests des couches tournent sur `fakeBrowser`, `browser-fake.test-support.ts`, et sur `engineForPages`, `electron-page.test-support.ts`), `browserSource()` et `engineSource()` suivant les fichiers, et les suites moteur `pnpm test:engine` (qui font tourner les vraies pages) sur un Mac libre.
- **`ElectronEngine`** est, comme `Browser`, une chaîne de classes abstraites qui n'ajoutent que des méthodes : `electron-engine-base.ts` (tous les champs, le constructeur, les aides partagées et les déclarations `abstract`) → `-bridge` (extensions ↔ onglets : fenêtre suivie, presse-papiers, shims, relais) → `-preloads` (pont média, `prompt()`, `window.chrome.app`, mots de passe, shims et correctifs de la bibliothèque) → `-network` (bloqueur, politique des réponses, substituts, garde de page, WebRTC, en-têtes, proxys, DNS, cookies) → `-extensions` (chargement, liste, mises à jour, workers, console) → `-profile` (câblage d'un profil et de sa bibliothèque) → `-permissions` (permissions, partage d'écran, matériel) → `-downloads` (téléchargements, reprise) → `ElectronEngine` (`electron-engine.ts` : pages, contextes privés, conteneurs).

Quatre autres blocs sont sortis tels quels, chacun appelé à l'endroit où ses lignes étaient : les fenêtres à part (mini-fenêtres, vidéo flottante, Réglages, Extensions, gestionnaire de tâches, À propos) dans `shell/own-windows-wiring.ts`, le coffre des mots de passe dans `shell/password-wiring.ts` (son `will-quit` garde sa place parmi les autres), le service d'import dans `shell/import-wiring.ts`, l'aide de débogage `LUCIUM_DEBUG_PANEL` dans `shell/dev-aids.ts`. Ce qui n'existe pas encore quand un bloc est appelé (le gestionnaire de fenêtres, le menu) lui est passé par une fonction lue au besoin. `main()` fait encore environ 410 lignes : le reste (le verrou, les copies de la session, les portails, la mise à jour, la sortie) tient à l'ordre des gestionnaires de `will-quit` et aux branches du test moteur (`if (!smoke)`), que des tests lisent dans `index.ts` (`engine-test-cuts.test.ts`, `launch-wiring.test.ts`, `main-wiring.test.ts`) ; il reste en place.
- **Filet d'erreurs** : hors test moteur (qui doit échouer dessus), une promesse rejetée sans gestionnaire et une exception non rattrapée du processus principal sont écrites dans le journal d'« État de Lucium » (pile, rang, temps depuis le lancement, 100 lignes au plus) et l'application continue (`rejection-log.ts`). Politique : Electron, après sa boîte d'alerte, continue de toute façon ; le filet retire la boîte (modale, répétée à chaque tic d'une minuterie qui lève). Continuer ne peut pas écrire un état abîmé sur un bon : le reducer est pur et le store ne prend son résultat qu'une fois rendu, chaque fichier est écrit à côté puis renommé, un fichier illisible au lancement est mis de côté. Rien n'est masqué : la première exception d'une session est dite par une notice (« Voir le journal »), les échecs d'écriture gardent leurs propres avis. Un écouteur du store qui lève est journalisé et n'empêche ni les suivants ni l'appelant (`StateStore.tell`), et chacun reçoit l'état du moment (pas un état plus ancien après un plus récent sous un dispatch réentrant). Côté interface, chaque surface est montée sous une frontière racine (`renderer/root.tsx`, `mountRoot`) : un rendu qui lève laisse l'écran « Quelque chose s'est mal passé » avec « Recharger l'interface » (la page de l'interface seule ; onglets et pages sont au processus principal) ; ses erreurs, `error` et `unhandledrejection` sont écrits en lignes `[ui]` de sa console, que `load()` relaie au journal (`shell/ui-error-relay.ts`, rien d'autre de la console, aucun canal IPC de plus). **Rédaction du journal** : une ligne est réduite quand elle y entre (`ErrorLog.add`, `shared/log-redaction.ts`), avant la coupe à 300 caractères : un chemin sous `/Users/<nom>/` ou `~/` ne garde que son nom de fichier, une adresse (`https://…`, `ws://…`, `chrome-extension://…`) que son hôte (ni identifiants, ni chemin, ni requête, ni fragment), une adresse `file://` que son nom de fichier ; tout le reste de la ligne est inchangé. La console, elle, écrit toujours la ligne en entier (sur un terminal local).

- Aides en un seul exemplaire : `smoke-kit.ts` (`sleep`, `pollUntil`, `waiterOf`) pour les suites smoke, une table des suites lancées seules dans `smoke-run.ts`, `shared/fold.ts` (trois variantes nommées, chacune gardant ce que sa recherche trouvait), `shared/html-escape.ts`, `shared/bounded-stream.ts`, le `crc32` de `shared/zip.ts`.
- Les tests de contrat qui lisent le source passent par `engineSource()`, `mainSource()` et `browserSource()` (`*-source.test-support.ts`) : un déplacement entre fichiers n'en casse aucun. Les autres lectures du source sont des inventaires (coût nul, clés de traduction, textes, accessibilité, port moteur).

Historique de navigation par profil (`src/main/history.ts`) : un profil est une session isolée **et** un historique. Une page n'entre que dans l'historique du profil de l'espace de l'onglet (`Browser.onPageUpdate`), ou de l'espace d'où vient un Coup d'œil (`openPeek`) ou une mini-fenêtre (`LittleArc.startPage`), avec les mêmes règles : une page ouverte dans l'aperçu d'un onglet privé ou d'un conteneur n'y entre pas, ni un chargement qui n'aboutit à aucune page (cadre, téléchargement, page d'erreur), et le panneau Historique (⌘Y), les suggestions et la complétion en ligne de la barre de commandes, l'oubli d'une page, « Effacer les données du site » et « Effacer l'historique de navigation… » ne voient et n'effacent que celui du profil de l'espace affiché ; deux espaces d'un même profil partagent le leur. Fichiers : `history.json` (tableau de pages, format inchangé) est l'historique du profil `default` ; les autres profils ont `history-<id>.json` (une majuscule de l'identifiant s'écrit `~` et sa minuscule, car le système de fichiers d'un Mac ne distingue pas la casse). **Migration** : il n'y en a pas à faire, c'est le choix : le fichier des versions précédentes, qui mêlait toutes les pages, *est* l'historique du profil par défaut, sans être déplacé ni réécrit (une page n'est écrite que si son profil a changé) ; la version précédente relit `history.json` (elle ne voit que le profil par défaut, et ses nouvelles pages y entrent), donc revenir en arrière ou relancer deux fois ne perd rien. Un fichier illisible n'écarte que le fichier de son profil (`.corrupt-<heure>`, avis à l'utilisateur) ; chaque entrée est reconstruite (`cleanHistory`), un profil nommé dans une entrée n'est pas cru, un identifiant qui n'en est pas un est le profil par défaut, au plus 20 000 pages par profil. « Effacer les données du profil » (Réglages › Profils) et « Supprimer les profils inutilisés » effacent aussi l'historique (fichier et copies mises de côté compris) et le disent s'ils n'y arrivent pas ; la fenêtre privée utilise `NO_HISTORY` et n'écrit rien. Un import d'un autre navigateur ajoute ses pages à l'historique du profil de l'espace d'où il est lancé (`importers/history-target.ts`). Restent communs à tous les profils (état partagé, hors historique, non traités ici) : la liste des « sites récents » de l'effacement de données (`siteDataRecents`), les onglets, l'archive, la liste « à lire plus tard » et les sessions que la barre de commandes propose, les autorisations de sites mémorisées (`sitePermissions`), la liste des téléchargements, le zoom par site, et la barre de commandes d'une mini-fenêtre, qui interroge l'historique du profil de l'espace affiché dans la fenêtre principale. Les icônes de sites (une session en mémoire, sans cookie), les vignettes (mémoire, par onglet) et les suggestions de recherche (rien n'est gardé, `SUGGEST_FETCH_INIT`) ne gardent rien par profil. Le classement de la barre de commandes (`commandBarUsage`, `shared/command-bar-usage.ts`), lui, est tenu par profil : un espace lit et nourrit celui de son profil, effacer l'historique d'un profil ne vide que le sien, un onglet privé n'y écrit rien, et le classement commun d'un fichier plus ancien n'est pas repris (rien ne dit dans quel profil une adresse a été choisie). ⇧⌫ sur une ligne d'historique de la barre oublie la page et la garde de côté en mémoire dix secondes (`HistoryStore.removeKept`), le temps d'« Annuler » (cinq secondes à l'écran, ou ⌘Z) : le canal `putBackHistory` ne reçoit qu'une adresse et un profil, et seule la page que cet historique vient d'oublier revient, telle qu'elle était ; un effacement plus large entre-temps l'emporte pour de bon. Une page oubliée dans l'historique (⇧⌫, le panneau Historique, « Oublier ce jour ») quitte aussi le classement de son profil (`commandbar/forget`) ; avec ⇧⌫, son compte attend en mémoire le même temps (`shell/forgotten-ranking.ts`) et ne revient (`commandbar/put-back`) que si l'historique rend la page. L'historique n'est pas dans « Exporter les données » (l'état seul y est).

**La bibliothèque : signets, dossiers en direct, sites en fenêtre d'application** (trois réglages booléens, désactivés par défaut, inscrits au registre : `bookmarkManager` / `bookmarks`, `liveFolders` / `live-folders`, `webAppWindows` / `pwa`). *Signets* (`shared/bookmarks.ts`, `shell/bookmarks-library.ts`, `renderer/Bookmarks.tsx`) : `SidebarState.bookmarks` (5 000 au plus, chacun une fois par adresse normalisée, 12 étiquettes de 40 caractères au plus), distincts des favoris et des épinglés qu'ils ne touchent jamais ; toutes les actions `bookmark/*` ne changent rien tant que le réglage est désactivé (les données restent dans le fichier), `bookmarks/import` est réservée au processus principal (`MAIN_ONLY_ACTIONS`), une fenêtre privée n'en garde aucun (`scrubPrivateState`, `privateAction`) et l'écran verrouillé les masque (`redactForLock`). L'import lit un fichier Netscape par `parseNetscapeBookmarks(html, { details: true })` (le même lecteur borné que l'import de la barre latérale, qui ignore `TAGS`, `ADD_DATE` et `<DD>` par défaut), le nom du dossier d'un lien devient une étiquette ; l'export écrit `TAGS` et `<DD>` et se relit. Les boîtes de dialogue sont celles du processus principal (`Channel.bookmarksTransfer` : `{ op: 'import' | 'export' }`, aucun chemin ne vient de l'interface). *Dossiers en direct* (`shared/live-folders.ts`, `shared/feed.ts`, `shell/live-folders.ts`, `shell/live-fetch.ts`) : `Folder.live` (source, 15 éléments au plus, date et phrase de la dernière lecture), 20 dossiers en direct au plus. Un `LiveFolderService` (modèle : `PageWatcher`) est créé par la fenêtre principale seulement (jamais une fenêtre privée ou secondaire) quand le réglage est vrai (`gates.gate('live-folders', …)`), arme **une seule** minuterie pour l'échéance du prochain dossier (aucune sans dossier en direct), lit un dossier à la fois, au moins 20 s entre deux lectures, après un délai au lancement ; la requête passe par `requestFetch` (session en mémoire, ni cookie ni référent) et `lookAt` (hôtes publics seulement, redirections jugées une à une, 512 Ko, 15 s). Le XML est lu à la main (`parseFeed`) : un DOCTYPE est sauté, aucune entité n'est développée, profondeur, nombre de balises et longueur de chaque champ sont bornés ; GitHub passe par son API publique (adresses contrôlées : elles doivent être sous `github.com/<dépôt>/`). Le résultat revient par l'action `livefolder/result` (principal seulement), ignorée si la source a changé entre-temps. Réglage désactivé, la barre latérale ne dessine rien de plus (`Sidebar.tsx` : un enfant conditionnel) : un dossier en direct est un dossier ordinaire vide. *Sites en fenêtre d'application* (`shared/web-apps.ts`, `shell/web-apps.ts`) : un `WebAppWindows` créé par une porte (`gates.gate('pwa', …)` dans `index.ts`), une fenêtre par site (8 au plus) dont l'interface est la page de la mini-fenêtre en mode `app` (`WebAppHeader` : icône, nom, précédent, suivant, actualiser, « Ouvrir dans un onglet ») et dont la page vient de `engine.createPage` avec le profil de l'espace d'origine ; un lien vers un autre site va au navigateur, en onglet. Pas de réécriture des navigations de la page elle-même (le moteur n'a pas de crochet de portée) ; pas d'icône de Dock propre au site. **Migration** : aucune, `bookmarks` et `Folder.live` sont facultatifs, `STATE_VERSION` reste 1.

**Barre latérale à droite, image d'espace, volets web** (réglages booléens désactivés par défaut : `sidebarRight` dans Réglages › Apparence, `webPanels` dans Réglages › Fonctions en option ; `spaceImages` ne commande plus rien, l'image d'un espace se choisit dans « Personnaliser l'espace » ; `src/shared/frame-layout.ts`, `shell/space-images*.ts`, `shared/web-panels.ts`). *Miroir* : `Browser.frame()` calcule la carte de la page et le panneau docké avec `frameLayout`, l'interface (`App.tsx`, `sidebar-right.css`) pose ses marges avec les mêmes nombres ; la barre latérale, le volet, la barre flottante, la poignée, le bouton de la barre d'outils, la carte de survol, l'éditeur de thème et les popovers de la barre d'outils et des téléchargements passent de l'autre côté. macOS garde les feux tricolores à gauche de la fenêtre : en miroir ils appartiennent à la fenêtre (toujours visibles), la barre d'outils leur laisse `LIGHTS_CLEARANCE` px (et une bande vide de la hauteur de la barre quand elle est masquée). Réglages par défaut, la fonction rend exactement les nombres d'avant (test de `frameLayout` ; les suites `smoke-iso-*.ts` vérifient les relations de mise en page, pas des nombres). *Fenêtre par fenêtre* (« Barre de cette fenêtre », `shared/window-sidebar.ts`) : `sidebarRight` est le côté des nouvelles fenêtres et de celles qui n'ont rien choisi ; chaque fenêtre peut prendre l'autre côté pour elle seule, ou **coller** sa barre en une colonne de `DOCK_WIDTH` (56 px) d'icônes de sites (`renderer/DockedSidebar.tsx`, contenu `shared/docked-sidebar.ts`). Le choix vit dans le `Browser` de la fenêtre (`sidebarChoice`, hors de l'état partagé : le changer ne touche ni `state.json` ni les autres fenêtres) ; toute la mise en page de la fenêtre lit `Browser.placement()` (`sidebarPlacement` : son côté, sinon le réglage ; la colonne seulement tant que la barre est affichée), jamais `settings.sidebarRight` directement, et l'instantané de la fenêtre porte `windowSidebar` pour l'interface (`App.tsx`, `Sidebar.tsx`, `OverlayHost.tsx`). La fenêtre des Réglages, qui reçoit l'instantané de la fenêtre principale, continue de montrer le réglage. Colonne affichée, les feux restent en haut à gauche de la fenêtre, de quelque côté qu'elle soit (une colonne est une barre affichée : `trafficLightsAt` les montre déjà) ; la carte commence au bord de la colonne, la barre d'outils leur laisse la place (`toolbarLeading`, `cardLeftUnderLights`) et, masquée, une bande vide les garde hors de la page (`stageTop`, `docked`). Les changements passent par un seul canal (`Channel.windowSidebar`, `parseWindowSidebarChange` refuse toute autre forme) ou par les menus du processus principal (clic droit sur la barre : `MenuTarget` `space` avec `sidebar: true` ; Affichage ; ⌃⌘S, commande `dockSidebar`). Le bord de la fenêtre n'ouvre la barre flottante que sans barre à l'écran (`edgeOpensFloatingSidebar`, lu par `hotEdge`) ; la vue flottante dit « dedans » tant que le pointeur est sur sa vue entière, marge transparente comprise (`App.tsx`, `floating-shell`), et non sur son seul panneau : le panneau, décalé de 5 px du bord, glisse sous un pointeur arrêté au bord et le cache puis le rouvre en boucle. `main/shell/sidebar-trace.ts` écrit dans le journal que porte « Signaler un problème » (celui de `console.error`) une ligne `[sidebar] <fenêtre> : <forme> <côté> own=<choix> (<cause>)` à chaque changement de place de la barre d'une fenêtre (`layout`, avec l'action ou le geste qui l'a causé : `toggleSidebar`, `window-sidebar …`, `settings/update …`, `compact/toggle`, sinon `state`) et une ligne `edge opened|closing|gone|ignored` à chaque contact du bord, espacée (1 s, puis le double, 32 s au plus) pour ne pas chasser les vraies erreurs des 50 lignes ; ni adresse ni titre dans ces lignes : la colonne est une barre affichée, la survoler n'ouvre rien, que `compactMode` soit activé ou non (`isCompact` exige la barre masquée : la colonne affichée l'emporte, le mode compact ne devient actif qu'une fois les deux barres masquées). `windows.json` garde le choix avec chaque fenêtre (`SavedWindow.sidebar`, `SavedSession.mainSidebar`, nettoyés par `cleanWindowSidebar`) ; une fenêtre restaurée le reçoit avant de démarrer, une fenêtre fermée l'emporte avec elle. *Image d'espace* : le fichier choisi dans la boîte de dialogue du processus principal n'est lu qu'après un contrôle de taille et d'en-tête (PNG, JPEG, WebP, 5 Mo, 8 000 px, 40 millions de pixels) ; `nativeImage` ne lit pas le WebP (Electron 45), donc le rognage carré et la réduction à 128 px se font dans une page sandboxée, sans préchargement ni réseau, dont la réponse est contrôlée à nouveau ; seule la copie est gardée (`space-images/<24 hex>.png`, droits 0700 / 0600), l'état n'en retient que le nom (`Space.image`) et l'action `space/image` est réservée au processus principal. Une copie illisible est écartée à la lecture (l'espace retrouve son émoji, le fichier est supprimé) ; les copies que plus rien ne référence (espace supprimé, image remplacée ou retirée, session supprimée) sont balayées, espaces mis de côté compris, sauf celles que nomme encore une copie de la session ou une copie de l'état faite avant une restauration (`shell/space-image-sweep.ts` : remettre la copie ramène l'image ; si une de ces copies est illisible, aucune image n'est supprimée) ; rien n'est écrit depuis une fenêtre privée. *Volets web* : `Space.webPanels` (12 adresses http(s) au plus, sans identifiant dans l'adresse), un seul volet à la fois dans le dock du volet d'extension (largeur `sidePanelWidth`), une vue native créée par `engine.createPage` avec le profil de l'espace (mêmes crochets que les onglets : pages d'erreur et de certificat, HTTPS d'abord, bloqueur, vérifications de navigation) ; il se ferme avec l'espace affiché, avec le site retiré de la liste ou avec le réglage. **Migration** : aucune, c'est le choix : les deux champs sont facultatifs (un état sans eux est un état sans volets ni images), `STATE_VERSION` reste 1 et la version précédente relit le fichier (elle ignore les champs).

Navigation entre onglets (`smoke-navigation.ts`, `LUCIUM_SMOKE_ONLY=navigation`) :
- **Retour qui ferme** : `TabItem.openerId` (posé par `Browser.pageEvents.openWindow` seulement si `backClosesOpenedTab`) est oublié à la première navigation (`canGoBack`) et quand l'onglet cité disparaît (`pruneOrigins`, après chaque action, et au chargement). `Browser.nav('back')` appelle `tab/back-to-origin` (archive l'onglet, affiche l'origine) quand l'onglet a une origine et sa page rien derrière (`backCloses`) ; le bouton, le menu et `runtime.backCloses` restent activés dans ce cas.
- **⌃Tab** : aucune touche n'est écoutée tant que `tabCycleRecent` est faux. Allumé, `Page.watchKeys` (le port moteur : un écouteur `before-input-event` par page) et `win.webContents` envoient les touches à `Browser.cycleKey`, qui garde le panneau tant que le modificateur de l'accélérateur (⌃) est enfoncé ; l'ordre vient de `createdAt`/`lastActiveAt` et du moment où cette fenêtre a quitté chaque onglet (`usedAt`, mémoire seulement) ; les vignettes sont celles de la carte de survol (`Thumbnails`). Le panneau est une vue du calque transparent, sans prise du focus (les touches restent à la page).
- **Voile du glisser** : la rangée de la barre latérale dit `splitDrag('start')` ; le moteur prend une image de la page, la met de côté et ouvre le calque `splitdrop` aux bornes de la page ; le voile (`SplitDrop.tsx`) calcule les zones à partir des `dragover` (seul un glisser d'onglet est accepté), anime la page réduite et la boîte, et répond `splitDrop(zone)` ; `Browser.dropOnPage` fait `split/create` (ordre, orientation ou case de la grille, volet affiché) ou ouvre la barre de commandes pour l'autre volet (onglet glissé sur lui-même). Au repos, rien n'existe.

**Arbre d'onglets et mode compact** (`tab-tree.ts`, `compact.ts`, `smoke-tabsui.ts`, `LUCIUM_SMOKE_ONLY=tabsui` ; deux réglages booléens désactivés par défaut : `tabTree` dans Réglages › Fonctions en option, `compactMode` dans Réglages › Apparence). *Arbre* : `TabItem.parentId` n'est pas `openerId` (celui-ci est oublié à la première navigation et n'existe que si `backClosesOpenedTab` est vrai) ; `Browser` ajoute `parentId` à `tab/open` quand `tabTree` est vrai. Un seul invariant porte tout : dans `SidebarState.tabs`, les onglets du jour d'un espace sont dans l'ordre de l'arbre (un onglet, puis sa branche), donc `sidebarOrder`, `stepTab`, la sélection par plage et les déplacements par position ne connaissent pas l'arbre. `settleTree(prev, next)` le rétablit à la fin de `reduce` et dans `normalize` : réglage coupé = champs retirés (la liste garde son ordre), parent absent, épinglé, d'un autre espace ou en boucle = remplacé par le plus proche ancêtre resté valide (d'après `prev`), branche regroupée derrière son parent, repli gardé seulement s'il y a des enfants, branche ouverte quand son onglet est sélectionné. `tab/move` et `tabs/move` portent un `parentId` optionnel et emmènent la branche vers le jour ; `planDrop` calcule la place (`treeDropSlot` : avant, après, dans une rangée ; le quart haut, le milieu et le quart bas d'une rangée du jour, `locateRow(rows, y, tree)`). *Compact* : pas d'état propre, une fenêtre est compacte quand `compactMode` est vrai et que `sidebarVisible` et `showToolbar` sont faux ; l'action `compact/toggle` écrit ces deux réglages (propres à la fenêtre, voir `WindowView`) ; la barre latérale volante montre l'adresse à la place de l'onglet actif.

Fonctions optionnelles (`src/shared/features.ts`, `src/main/shell/feature-gate.ts`, `docs/fonctions.md`) : règle de conception, **une fonction désactivée ne coûte rien** (ni minuterie, ni écouteur, ni requête, ni mémoire, ni code exécuté pour elle). Le réglage de `Settings` reste la seule clé ; le registre le décrit, le portail démarre ce qui coûte quelque chose quand il est vrai et le défait quand il devient faux. Un réglage booléen ajouté sans inscription fait échouer `features.test.ts`. Il n'y a pas de volet « Fonctions » : chaque interrupteur est dans la catégorie de son réglage, avec le repère de son coût (docs/fonctions.md).

Modèle d'écran : la fenêtre (`BrowserWindow`, sans cadre, feux tricolores intégrés) affiche l'interface ; chaque onglet actif est une `WebContentsView` posée par-dessus, aux coins arrondis ; la barre de commandes est une vue transparente ajoutée au-dessus, uniquement quand elle est ouverte.

## Export chiffré, verrouillage, historique d'un onglet rouvert

Trois fonctions de sécurité et de données ; chacune ne coûte **rien** tant qu'elle n'est pas utilisée ou activée.

**Export chiffré** (`src/main/export-crypto.ts`, `export-file.ts`). « Exporter les données » écrit toujours le JSON de l'état, en clair si aucune phrase n'est donnée. Ce JSON est l'état entier, réglages compris (seuls ceux du verrouillage sont remis à zéro, `exportableState`) : un export en clair nomme donc aussi les sites que les réglages retiennent (zoom, exceptions et modes du bloqueur, mode développeur, traduction, gestes exclus, moteurs de recherche découverts, routes des liens, recherches dans un site), même quand leurs onglets sont fermés. N'y sont pas : l'historique, les scripts utilisateur, les règles des listes de filtres, les images et les fonds des espaces, la mémoire des fenêtres, le coffre de mots de passe (export séparé) ; les notes n'y vont que si leur fonction est activée. Avec une phrase : une enveloppe JSON versionnée (`format: "lucium-export"`, `version: 1`) : clé de 64 octets dérivée par `scrypt` (module `crypto` de Node, aucune dépendance) de la phrase normalisée NFKC et d'un sel aléatoire de 16 octets, soit 32 octets pour AES-256-GCM (nonce aléatoire de 12 octets, étiquette de 16) et 32 pour un HMAC-SHA256 de l'en-tête (`check`), qui distingue une phrase fausse d'un contenu altéré avant tout déchiffrement. L'en-tête (paramètres, sel, nonce) est donnée à GCM comme données authentifiées. Le contenu est rempli de zéros jusqu'à une taille arrondie (pas de 4 Kio au moins, au plus 1/8 de la taille) : le fichier ne révèle pas la taille exacte. Coût d'une nouvelle exportation : `N = 2^17, r = 8, p = 1` (128 Mio, environ un tiers de seconde, la valeur que donne l'OWASP). **Un fichier est hostile** : à la lecture, `N` doit être une puissance de deux entre 2^14 et 2^18, `r ≤ 16`, `p ≤ 4`, mémoire `128·N·r ≤ 256 Mio` et travail `N·r·p ≤ 2^22` (au plus quatre fois le coût par défaut), contrôlés **avant** de demander la phrase ou de dériver quoi que ce soit ; chaque champ est en base64 strict de longueur exacte ; le fichier ne dépasse pas 64 Mio. La phrase (8 caractères au moins) n'est ni enregistrée ni journalisée (les erreurs ne portent que leur sorte) ; elle passe de la case des Réglages à la requête IPC, puis le champ est vidé. « Restaurer les données… » ouvre un panneau (`panel: 'passphrase'`, réservé au processus principal comme `auth`) ; cinq essais au plus. L'état exporté ne contient ni `lock.json` ni les réglages du verrou (`exportableState`) ; `exportableState` ne masque que le verrou : l'export en clair garde les chemins personnels (`extensionPaths`, `translateModelsDir`) et les adresses réglées (Ollama, `proxy.address`, `dohCustomUrl`, `updateFeedUrl`), les autorisations des sites et les Retouches, et le texte de la feuille d'export (Réglages › Téléchargements et fichiers › Plus de réglages, sous « Copies automatiques ») le dit. Pas de réglage persistant : c'est une case de l'exportation.

**Verrou** (`src/shared/lock.ts` règles pures ; `src/main/lock-service.ts` état ; `lock-store.ts` fichier `lock.json`). Réglages `lockEnabled` (interrupteur), `lockApp`, `lockedSpaces`, `lockTouchId`, que seul le gestionnaire du verrou modifie (`ipc-policy.ts` les refuse à l'interface ; `state/restore` garde ceux de l'installation). **Ce que c'est** : un verrou de l'interface. Verrouillé, l'espace (ou l'application) n'a plus de page (`Browser.onLockChange` détruit les vues web, `visibleIds` n'en fait aucune), l'interface reçoit un état réduit (`redactForLock` : espaces sans nom, aucun onglet, dossier, favori, hôte), la fenêtre affiche l'écran de verrouillage, le menu se réduit à Quitter et aux commandes d'édition, et le canal IPC refuse tout sauf lire cet état, déverrouiller et fermer un panneau (`OPEN_WHILE_LOCKED`). Les surfaces qui ont leur propre canal (mini-fenêtres, fenêtres d'application, vidéo flottante, barre d'annotation, fenêtres du partage) sont fermées au verrouillage et, si l'une restait, ses messages sont refusés (`shell/lock-gate.ts`). Un canal nouveau ne peut pas l'oublier : `src/main/ipc-lock-coverage.test.ts` lit chaque enregistrement sur `ipcMain` et échoue sur un gestionnaire qui ne passe ni par la garde de `registerIpc` ni par `shutByLock`, sauf pour les canaux des pages web, listés avec leur raison (le verrou détruit les pages des onglets). **Ce que ce n'est pas** : un chiffrement. Les cookies, les profils Chromium, `state.json` et l'historique restent lisibles sur le disque par quiconque lit le disque ; les extensions déjà lancées et les téléchargements en cours continuent. La phrase n'est jamais enregistrée : `lock.json` (droits 0600, hors de l'état, des exportations et des copies automatiques) contient un sel et une empreinte `scrypt` ; oublier la phrase se règle en supprimant ce fichier. Touch ID passe par `systemPreferences.promptTouchID` (macOS) quand `canPromptTouchID()` ; sinon, ou s'il échoue, la phrase. Trois mauvaises phrases de suite, puis une attente qui double (1 s à 30 s) ; un seul essai à la fois. Deux niveaux : l'application (au lancement, à `suspend`, `resume`, `lock-screen`) et chaque espace (déverrouillé jusqu'à la prochaine de ces occasions ou « Verrouiller maintenant »). Désactivé : aucun écouteur, aucun fichier lu, aucun champ dans l'instantané.

**Pages précédentes d'un onglet rouvert** (`src/shared/closed-history.ts`). Réglage `reopenHistory`. Activé, l'archivage d'un onglet (⌘W, archivage auto, « Vider les onglets du jour »…) garde avec l'entrée d'archive jusqu'à 20 adresses http(s) de sa liste Précédent/Suivant (`Ctx.closedHistory`, lue dans la page avant sa destruction), et rouvrir l'entrée les rejoue par `webContents.navigationHistory.restore` (vérifié sur Electron 45 par `smoke-security2.ts`) ; une adresse qui n'est pas web est écartée, et un historique qui ne finit pas sur l'adresse de l'entrée n'est pas gardé. Coût mesuré (500 entrées d'archive) : 146 Ko d'état sans les pages, 375 Ko avec 3 pages par onglet, 728 Ko avec 8, 3,2 Mo au plafond (20 pages, adresses de 200 caractères) ; l'état entier part à chaque fenêtre à chaque changement, d'où un défaut **désactivé** ; le désactiver supprime les listes déjà gardées. Les listes sont de l'historique : effacer l'historique d'un profil, ou celui d'un site, les retire de l'archive (action `archive/forget-pages`, réservée au processus principal) et des copies automatiques de `session-backups/` réécrites en place (`copyAfterForgetting`) ; limites dans `docs/fonctions.md` (`reopen-history`).

## Apparence de la fenêtre et contraste de la page

Deux réglages de **Réglages › Apparence**, désactivés par défaut (la fenêtre et les sites gardent leur apparence par défaut tant qu'on n'y touche pas).

**Deux apparences, deux réglages** (`interfaceAppearance`, `websiteAppearance`). Avant 0.2.15 un seul réglage (`websiteAppearance`, « Clair ou sombre ») donnait les deux, par `nativeTheme.themeSource`, qui est **global** dans Electron : choisir Sombre pour les sites rendait aussi sombres les Réglages, la barre latérale et tous les panneaux, quelle que soit l'apparence de macOS (et « Clair » dans macOS n'y changeait rien). Maintenant :
- **Apparence de Lucium** (`interfaceAppearance`, Automatique = celle du Mac) : l'apparence des fenêtres de l'application, et **le seul réglage qui bouge `nativeTheme.themeSource`** (`shell/appearance.ts` `followAppearance`, `shared/theme.ts` `themeSourceOf` ; appelé au démarrage de `main()` et à chaque changement de l'état ; `themeSource` n'est écrit que s'il change). Un espace dont le thème est réglé sur Clair ou Sombre garde le sien dans la barre latérale (`resolveAppearance`, inchangé). Les feuilles du premier lancement et de bienvenue, le guide des réglages et les prises d'écran du site écrivent ce réglage.
- **Apparence demandée aux sites** (`websiteAppearance`, Automatique = les sites suivent Lucium) : ce que les pages lisent de `prefers-color-scheme`, et rien d'autre. Electron n'a pas de moyen de donner à **une** page sa préférence de couleur ; c'est fait comme le fait DevTools (`src/main/engine/color-scheme.ts`) : une session du protocole sur la page, `Emulation.setEmulatedMedia({ features: [{ name: 'prefers-color-scheme', value }] })`. Relevé sur Chrome sans fenêtre, par le protocole brut : l'émulation de la cible de la page vaut aussi pour ses cadres (même d'un autre site), garde la page à travers les navigations (même site ou non), un cadre chargé plus tard la prend, et elle part avec la session quand celle-ci se détache. Donc : **aucune session n'est jamais attachée tant que le réglage est sur Automatique** (le défaut), et la session est détachée quand il y revient ; `ElectronEngine.setPageColorScheme` donne le réglage à toutes les pages que le moteur fait (`ColorSchemePages` : fenêtres privées et conteneurs compris, une page faite plus tard le lit dès son premier document, la page d'une extension n'en reçoit pas), et chaque page le redemande à son `dom-ready`.
- **Ce que coûte une session du protocole, et ce qui l'empêche de gêner** : (1) elle compte comme un débogueur : les clics et les touches qui arrivent à une page pendant qu'un débogueur y est attaché ne comptent pas comme ceux de l'utilisateur (`countsAsGesture`, ce qui empêche une extension qui déboguerait une page d'appuyer à sa place sur un bouton) ; la session du réglage est **la nôtre** et ne compte pas comme un débogueur (`holdsEmulation`, `user-input.ts`), une session d'extension (`chrome.debugger`) si ; (2) elle laisse la page à une extension qui s'attache (`ColorSchemeEmulation.stepAside` avant `debugAttach`) et revient à la fin de la session de l'extension, donc l'API `chrome.debugger` voit la page libre comme avant (`isDebugAttached`, `debugSend` et `debugDetach` ne parlent que de la session de l'extension) ; (3) elle ne prend pas une session que quelqu'un d'autre tient (capture, gel, extension) : elle réessaie au document suivant ; (4) un échec (attache, commande, détache) est journalisé avec ce qu'on faisait. Limite connue : DevTools ouvert sur la page et son onglet « Rendu » peuvent écraser l'émulation tant qu'ils y touchent.
- **Migration** : aucune. `interfaceAppearance` vaut Automatique dans un fichier d'avant (un champ nouveau n'a besoin que de son défaut) ; `websiteAppearance` garde ce que le réglage unique disait. Quelqu'un qui avait forcé Clair ou Sombre pour toute l'application doit le choisir de nouveau dans « Apparence de Lucium » ; ses sites gardent leur choix.
- **Où on le choisit** : Réglages › Apparence › Affichage › « Apparence de Lucium » et Réglages › Apparence › Apparence des sites › « Apparence demandée aux sites » ; Affichage › Apparence dans la barre de menus, deux groupes de choix sous leurs titres (« Apparence de Lucium : », « Apparence demandée aux sites : »).

**Contraste de la page** (`readableMode`, `siteReadableMode` ; `src/shared/readable-mode.ts` pour le choix, `src/shared/dark-sites.ts` pour le moteur). Chaque site est en **Original** (rien ne change : le défaut), **Sombre** (une page claire est assombrie) ou **Clair** (une page sombre est éclaircie). `readableMode` est le mode de tous les sites qui n'ont pas de choix à eux ; il vaut Original, Sombre, Clair ou **Automatique** (Sombre tant que l'apparence de l'interface est sombre, Original sinon : une page sombre n'est pas éclaircie par l'apparence claire). `siteReadableMode` associe un hôte à Original, Sombre ou Clair : il couvre les sous-domaines, le choix le plus précis l'emporte, un site d'un mode Original garde ses couleurs sous un défaut Sombre. Un choix de site n'est jamais Automatique et ne suit pas l'apparence. Nettoyage comme les autres listes de sites (hôte sans `www.`, mode inconnu écarté, 500 sites au plus, aucune clé de prototype). Le choix se fait dans le centre de contrôle du site (⌘I, rangée « Contraste de la page » : un clic passe au choix suivant, défaut, Sombre, Clair, Original), dans Affichage › Apparence › Contraste de la page pour ce site, dans le bouton « Contraste de la page » de la barre d'outils (`readableToolbarButton` ; `readableButtonMode` donne son icône ; chaque clic passe au mode suivant, Original, Sombre, Clair puis Original (`READABLE_NEXT`), décidé dans le processus principal par `readableToggle` et `toggleReadableSite`, canal `toggleReadable` ; un clic droit ouvre le menu natif `{ kind: 'readable', id }` de `context-menus.ts`, qui utilise le même constructeur d'entrées que le menu Affichage, `readableSiteItems`), dans la barre de commandes (« Contraste de la page : sombre / clair / original pour ce site », « …comme les autres sites ») et dans Réglages › Apparence (le défaut et la liste des sites, qui se modifient et se retirent). Ni un onglet privé, ni une fenêtre privée n'écrit un site dans les réglages (l'action `readable/site` ignore l'onglet privé qui la demande).

**Migration.** Un fichier d'état de révision 1 ou sans révision porte l'ancien mode sombre forcé : `forceDarkSites` devient `readableMode` Sombre, ou Automatique quand `forceDarkOnlyWhenSystemDark` l'accompagnait (même comportement qu'avant : sombre quand l'apparence est sombre, rien sinon) ; Original quand l'interrupteur était coupé ; chaque `forceDarkExceptions` devient un site à Original. La migration se fait une fois, au chargement (`migrateSettings`, `readableFromForcedDark`), la révision du format passe à 2, et les trois anciens réglages ne sont ni gardés ni réécrits (`MIGRATED_SETTINGS`).

**Ce que reçoit une page.** À l'ouverture d'un document d'un site qui n'est pas à Original, la page répond à une sonde (`DARK_PROBE_SCRIPT`, la luminance du fond derrière cinq points de la fenêtre) ; **`readablePlan(mode, apparence)`** (`dark-sites.ts`) en tire ce que la page reçoit : Sombre ne recolore qu'une page claire, Clair qu'une page sombre ; une page déjà du bon côté, un PDF ou une page illisible n'ont rien. **`applyReadable`** le lui donne (ou le lui reprend) : c'est le seul endroit qui sait ce qu'un mode fait à une page ; le choix par site, les réglages, la migration et les menus ne changent pas. La sonde et le moteur (`src/shared/readable-engine.ts`) tournent dans un **monde isolé** de la page (`READABLE_WORLD`, `Page.runReadable`) : la page ne les voit pas, ne lit pas leur état et ne peut pas changer les fonctions qu'ils appellent (une page qui remplace `document.elementFromPoint` dans son propre monde ne trompe plus la sonde). Avant de lire, la sonde suspend le moteur s'il tourne déjà (ses feuilles coupées puis remises dans la même tâche : rien n'est peint entre les deux), pour juger la page sur ses propres couleurs.

**Le moteur de recoloration** (phase 2 ; il remplace l'inversion, qui reste son repli) :

1. **Recolorer, pas inverser.** Chaque feuille de style lisible (feuilles de la page, `@import`, feuilles adoptées, racines fantômes ouvertes) est copiée avec les mêmes sélecteurs, le même ordre, la même importance et les mêmes regroupements (`@media`, `@supports`, `@layer`, `@container`, imbrication CSS, `@keyframes`), en ne gardant que les déclarations de couleur, converties ; les copies sont adoptées après les feuilles de la page (`adoptedStyleSheets`), si bien que la cascade de la page (survol, focus, requêtes média, couches) est conservée. Chaque couleur garde sa teinte et autant de chroma que la gamme sRGB le permet (OKLCH) ; seule sa luminosité change, selon son rôle. En Sombre : un fond plus clair que L 0,45 passe entre 0,20 et 0,42 dans l'ordre inverse (le blanc devient 0,20 ; une couleur très saturée garde jusqu'à 0,08 de plus, pour qu'une barre de marque reste de sa couleur), un fond plus sombre reste tel quel ; un texte plus sombre que 0,65 passe entre 0,68 et 0,93 (le noir devient 0,93) ; une bordure est mise en miroir (0,20 à 0,80) pour garder son contraste avec le fond ; une ombre sombre reste ; un fond léger (alpha < 0,25 : survol, rayure) est traité comme de l'encre, un voile plus opaque (fond de fenêtre modale) comme un fond. Clair est le miroir, ancré sur le fond de la page sombre (qui devient presque blanc). Les propriétés personnalisées ne sont jamais modifiées : une propriété de couleur qui lit `var(--x)` lit d'abord un jumeau de `--x` pour son rôle, fait seulement pour les propriétés qu'une couleur lit (à travers les chaînes de `var()`), y compris les canaux `255, 255, 255` ou `0 0% 100%` qu'un système de conception passe à `rgb(var(--x))` ou `hsl(var(--x))`. Une déclaration que le CSSOM ne rend pas (un raccourci qui contient `var()` suivi, dans le même bloc, d'une propriété détaillée de ce raccourci : Chromium ne sérialise alors ni l'un ni l'autre) est reprise du style calculé d'un élément que le sélecteur désigne (pseudo-élément compris), quand il y en a un. `color-scheme` est posé sur la racine : barres de défilement, contrôles natifs et canevas d'une page sans fond suivent.
2. **Garantir le contraste.** Chaque élément est ensuite lu (style calculé, sans mise en page), par tranches de temps. Un fond, un texte ou une bordure que les copies n'ont pas atteints (style en ligne, attribut `bgcolor` ou `color`, feuille d'une autre origine) est converti par une règle propre à l'élément, sélectionnée par un attribut dont le nom est tiré au hasard pour le document (rien n'y nomme le navigateur). Un texte encore sous **4,5 : 1** contre ce qui est derrière lui (**3 : 1** pour un grand texte : 24 px, ou 18,66 px en gras ; critère RGAA 3.2, WCAG 1.4.3) voit sa luminosité poussée, même teinte, jusqu'au seuil. Ce qui est derrière un texte tient compte des ancêtres transparents ou translucides, de l'opacité (un texte effacé presque à 0 n'est pas vérifié) et des dégradés (le pire de leurs arrêts) ; une image de fond le rend inconnu jusqu'au prochain fond opaque (le texte est alors laissé tel quel et compté). La bordure d'un champ de formulaire qui ne se détache pas de ce qui l'entoure et une petite icône SVG d'une seule couleur reçoivent le **3 : 1** des composants d'interface (RGAA 3.3, WCAG 1.4.11).
3. **Suivre la page.** Un `MutationObserver` voit les nœuds ajoutés, les changements de `class`, de `style` (seulement quand l'attribut porte une couleur, avant ou après : une animation qui déplace un élément soixante fois par seconde n'est pas relue) et des attributs de couleur ; les feuilles ajoutées ensuite (`<style>`, `<link>` à son chargement) et les règles insérées par script sans changement du DOM (bibliothèques CSS-in-JS : le nombre de règles est relu à chaque tranche) sont recopiées ; les racines fantômes ouvertes reçoivent leurs copies ; des feuilles adoptées que la page retire sont remises. Le travail passe par `requestIdleCallback`.
4. **Laisser les médias.** Images, vidéos, canevas, cadres d'autres sites, émojis et images de fond gardent leurs couleurs. Aucune atténuation des grandes images claires : ce sont des contenus dont la couleur compte (photos, graphiques, produits), les seuils RGAA ne s'appliquent pas à elles, et un réglage de plus ne valait pas ce gain. Seule exception : une image d'une seule couleur sombre sur fond transparent (logo, formule, dessin au trait) disparaîtrait sur le fond sombre ; elle est éclaircie (`invert(1) hue-rotate(180deg)`), le miroir en Clair. Elle est lue dans un canevas à partir de l'image déjà chargée (aucune requête) ; une image d'une autre origine ne peut pas être lue et garde ses couleurs.

**Repli.** Si le moteur échoue au démarrage (exception, feuilles plus longues que **1,5 s** à copier, réponse qui n'est pas un `ok: true`), le shell donne à la page l'**inversion de la phase 1** (`invertCss` : le filtre de la Retouche « inverser » adouci à 90 %, images, vidéos et canevas remis à l'endroit, emplacement `dark` de `Page.applyCss`) et l'écrit au journal (`[dark-sites] the recolouring failed on tab … : the page is inverted instead`). S'il échoue après son démarrage (en suivant la page), il retire sa recoloration et pose lui-même cette inversion dans la page (ligne `[readable]` de la console de la page). Une page trop occupée (plus de **1,5 s** de travail du moteur en 10 s) garde ses copies de feuilles, mais ses éléments ne sont plus lus. Une page qui ne répond pas à la sonde est laissée telle quelle et la raison est journalisée. Une page sans aucun fond reçoit, pour l'inversion, la couleur du canevas du navigateur (blanc, ou `#121212` quand un schéma de couleurs sombre le rend sombre) : sans cela le filtre ne touche pas ce fond.

**Coût.** À Original partout : aucun (`readableInUse` est faux : rien n'est injecté, rien n'est lu, aucun minuteur, aucun écouteur). Sinon, par document d'un site qui n'est pas à Original : une sonde (cinq points) ; pour une page à recolorer, le démarrage (copie des feuilles, puis une première tranche de 12 ms d'éléments, de façon synchrone : la première image peinte ensuite est déjà recolorée, au même moment que l'ancienne feuille d'inversion, à `dom-ready`), puis des tranches de 8 ms au plus pendant les moments d'inactivité, 60 000 éléments au plus pour la première lecture ; ensuite seulement ce que la page change. Le moteur ne fait aucune requête réseau. Mesures : `scripts/readable-bench.mjs` (Chrome sans fenêtre, voir `docs/accessibilite.md`, « “Contraste de la page” et les contrastes des sites ») : démarrage de 4 à 183 ms selon la page (copie des feuilles et première tranche), première image recolorée 13 à 206 ms après le début du démarrage, travail total du moteur sur le fil principal de 4 à 236 ms par page, changements d'une page dynamique (200 éléments ajoutés, règles insérées par script, classe basculée) relus en 56 ms pour 9 ms de travail. Le plus lourd est la copie des feuilles d'un très gros site (7 600 règles, 1 250 propriétés de couleur : environ 150 ms, et 2 Mo de texte de copies en mémoire).

**Limites.** Les feuilles d'une autre origine servies sans CORS ne sont pas lues (aucune nouvelle requête, par choix) : leurs couleurs sont corrigées élément par élément, sans leurs états (survol, focus) ni leurs pseudo-éléments, et une copie d'une feuille lisible peut l'emporter sur une de leurs règles de même spécificité. Le texte posé sur une image (image de fond, texte dans une image) n'est pas vérifié. Les cadres du même site (`iframe`) ne sont pas recolorés (le monde isolé est celui du cadre principal) ; les cadres d'autres sites gardent leurs couleurs sur un fond opaque (Chromium peint le canevas d'un cadre dont le schéma de couleurs diffère de celui de la page). Les racines fantômes fermées sont inatteignables. Un élément corrigé par sa règle propre (`!important`) perd ses couleurs de survol. Une déclaration perdue par le CSSOM n'est reprise que si un élément la porte au moment de la copie. Un logo sombre d'une autre origine reste sombre. Pas de fichiers `.pdf`, ni de pages hors http(s) ; les onglets et fenêtres privés suivent les mêmes règles qu'en phase 1.

**Fenêtre** (`windowVibrancy`, `sidebarOpacity`, `windowBorder`, `cardOutline` ; `src/shared/window-look.ts`). Ce qui est possible avec Electron 45 : une matière macOS derrière l'interface (`BrowserWindow.setVibrancy` : barre latérale, sous la fenêtre, verre sombre), un fond d'interface translucide (la fenêtre et son contenu deviennent transparents, la couche de couleurs de l'espace est dessinée à l'opacité choisie), la bordure autour de la carte de page (0 à 20 px ; 10 px par défaut, `PAGE_MARGIN`) et un filet d'un pixel autour de la carte. L'opacité ne compte qu'avec une matière : sans matière elle ne ferait qu'assombrir. La bordure déplace la vue native de la page (`Browser.stageRect`) et l'interface (`--window-border`) du même nombre. **Ce qui reste impossible** : un flou réel derrière la barre de commandes ou la page, car les cartes de page sont des vues natives opaques posées au-dessus de la fenêtre, et `backdrop-filter` ne floute que ce que la même vue web dessine ; l'intensité du flou de la matière n'est pas réglable (seulement le choix de la matière et l'opacité de la couche de couleurs). Le test moteur ne voit pas le rendu de la matière derrière l'interface (la capture d'écran demande une autorisation de macOS) : il vérifie que les pixels de la barre latérale sont translucides et que la fenêtre a reçu la matière, pas le dessin du verre.

## Captures annotées et commandes par adresse

Deux fonctions **désactivées par défaut** (`annotateCapture` et `urlAutomation` dans Réglages › Fonctions en option), qui ne coûtent rien tant qu'elles ne sont pas activées.

**Annoter les captures** (`annotateCapture`, id `annotate-capture`). Désactivé, une capture (zone ⇧⌘2, partie visible, page entière, portrait) est enregistrée dans Images/Lucium et copiée tout de suite, comme avant : ce flux n'est pas touché. Activé, `deliverCapture` (`src/main/shell/capture.ts`) garde la capture en mémoire dans le navigateur de la fenêtre (`CaptureShelf`, `capture-shelf.ts` : une seule à la fois, remplacée par la suivante, libérée à la fermeture de la feuille ou quand un autre panneau la remplace) et ouvre le panneau `annotate`, que seul le processus principal peut demander (`validOverlay` le refuse à l'interface ; la fenêtre privée l'accepte, comme la capture). La feuille (`src/renderer/AnnotateSheet.tsx`) demande l'image par son identifiant (`annotateImage`, rendue seulement tant que la feuille de cet identifiant est le panneau affiché), la dessine sur un canvas **à la taille de la capture** (outils : trait, flèche, rectangle, texte, flou ; sept couleurs, blanc et noir compris ; trois épaisseurs ; annuler et rétablir ; Échap demande confirmation s'il y a des annotations) et renvoie le PNG avec le choix de l'utilisateur (`annotateDone`) : **Copier** (presse-papiers seul), **Enregistrer** (fichier `capture-…-annote.png` seul), **Partager…** (enregistre d'abord, car le menu de partage du système veut un fichier, puis l'ouvre dessus). **Rien n'est écrit ni copié avant ce choix** ; abandonner jette la capture. Le processus principal revérifie tout (`parseAnnotateDone`) : identifiant de la capture tenue, action de la liste, PNG de la taille exacte de la capture, 64 Mo au plus. Une capture que le canvas ne sait pas porter (plus de 16 384 pixels d'un côté ou 30 millions de pixels) suit l'ancien chemin. Le « flou » est une **mosaïque** calculée sur les pixels de la capture (réduction par moitiés jusqu'à un pixel par cellule, puis agrandissement sans lissage) : le texte dessous ne peut pas être relu, ce qu'un vrai flou ne garantit pas. Si le panneau ne peut pas s'ouvrir (une boîte de page attend une réponse), la capture est enregistrée comme avant et le journal le dit. La logique est pure et testée (`src/shared/annotate.ts`, `annotate-draw.ts`) ; la feuille n'a pas de test unitaire, `src/main/smoke-capture.ts` la pilote avec de vrais événements de souris.

**Position de la barre d'annotation de la page** (`annotateBar`, sans interrupteur : ce n'est pas une fonction). La barre est une fenêtre à part (`src/main/shell/page-annotate.ts`, page `src/renderer/page-annotate-command.html`), que seul le processus principal peut déplacer. Le réglage `Settings.annotateBar` (`BarPosition`, `src/shared/annotate-bar-position.ts`) est l'unique endroit où la position vit : un bord (`right`, `left`, `top`, `bottom`) ou `floating` avec `x` et `y` comptés depuis le coin de la fenêtre (ou du volet) et une disposition (`column` ou `row`) ; il est nettoyé au chargement et à chaque `settings/update` par `cleanBarPosition` (appelé par `clampSettings`), qui rend la position par défaut (le bord gauche) pour tout ce qui n'est pas lisible, et le contrôleur le lit à chaque placement (`deps.position()`), sans copie. Le glissement de la poignée est un flux de positions du pointeur sur l'écran (canal `page-annotate:drag`, `ipcMain.on`, phases `start`, `move`, `end`, `cancel`, validées par `isBarDrag` et refusées d'un autre expéditeur que la fenêtre de la barre) ; `PageAnnotate` déplace la fenêtre (`dragBounds`), décide du bord par le pointeur (`snapEdge`, 24 points, égalités gauche, droite, haut, bas) et montre, tant que le glissement dure, **les quatre zones de dépôt** et le contour de l'endroit où la barre se posera, par `BarGhost` (`annotate-bar-ghost.ts` : **une** fenêtre transparente, de la taille de la fenêtre où l'on glisse, que le pointeur traverse et qui ne prend jamais le focus, **créée au début du glissement** — pas pour un simple clic — et détruite au lâcher ; sa page n'a ni script ni préchargement, le processus principal n'y exécute que `ghostCall`, faite de nombres et du nom d'un des quatre bords ; elle est amenée devant la fenêtre de la barre puis la barre est remontée par `moveTop`). Les zones sont les bandes de `BAR_SNAP_DISTANCE` le long des quatre bords (`dropZones`, qu'un test compare à `snapEdge` en tout point de la fenêtre) : faibles au repos, celle où se trouve le pointeur est allumée avec le contour pointillé. Le menu « Position de la barre » est un `Menu` natif (`barMenuEntries`, canal `menu`), ouvert par le clic droit sur la poignée, par le clavier, **et par le bouton « Position » de la barre** (un clic, sous le bouton : `menuAnchorUnder`), les flèches de la poignée un troisième canal (`nudge`). **L'astuce du premier usage** (« Astuce : glissez la poignée pour placer la barre où vous voulez », avec « OK ») est une bulle dans la page de la barre, au-dessus de la poignée : elle se montre à l'ouverture tant que le réglage `annotateBarHintSeen` (une mémoire, comme `suggestionsNoticeSeen`, sans interrupteur, classée dans `features.ts` et `NO_CONTROL_KEYS`) est faux ; `PageAnnotate` la tient (`hint` de `PageAnnotateState`, `BarContent.hint` qui agrandit la fenêtre de sa hauteur) jusqu'à « OK » ou Échap (canal `hint` ; Échap de la page de la barre ou de la page annotée ferme l'astuce avant de terminer l'annotation), jusqu'à un glissement qui a déplacé la barre (au lâcher, pour que la barre ne saute pas sous le pointeur), un choix du menu ou une flèche sur la poignée, et ne la retient comme vue qu'à ce moment-là (`deps.hintSeen`, `deps.setHintSeen`) : une barre fermée aussitôt la remontre. La géométrie est pure et testée (`src/shared/annotate-bar.ts` : `barSize` calcule la taille de la fenêtre pour chaque disposition, la rangée passant à la ligne par groupe comme `flex-wrap` (`wrapGroups`), `barBounds` la place dans la fenêtre et l'écran) ; la page reprend ses largeurs par des propriétés CSS (`--pa-*`, `barMetricVars`) qu'un test compare. **La rangée n'a jamais de barre de défilement** (`overflow: hidden`) : sa fenêtre a la taille de ses groupes, et une barre de défilement de 8 points faisait passer « Quitter » à une ligne invisible puis restait (une colonne, haute, dans une fenêtre qui venait d'avoir la taille d'une rangée, en faisait apparaître une, et le dernier groupe, sans marge, ne tenait plus avec elle) ; la colonne ne défile que dans une fenêtre plus basse qu'elle. Détails et mesures : `docs/design/annotation-partage-fenetre.md`.

**Commandes par adresse `lucium://`** (`urlAutomation`, id `applescript`). **Ce qu'Electron permet** (vérifié sur Electron 45.0.0 installé) : un dictionnaire AppleScript (`NSAppleScriptEnabled` + `OSAScriptingDefinition` dans `Info.plist`, un fichier `.sdef`) exige des classes Objective-C (`NSScriptCommand`, objets scriptables) dans le binaire ; l'`Info.plist` d'Electron n'a aucune de ces clés, `Electron Framework` et l'exécutable ne contiennent aucun symbole `NSScriptCommand` et l'archive ne livre aucun `.sdef`. Ajouter `extendInfo` ne suffirait donc pas : il faudrait un module natif Objective-C++ (chaîne de compilation, signature, mise à jour avec chaque Electron), ce qui contredit « mises à jour sans casse ». Ce n'est pas fait. L'app **Raccourcis** ne peut pas non plus recevoir d'actions natives de Lucium (les « actions d'app » demandent une extension App Intents en Swift). **La voie retenue** : un schéma d'URL, déclaré dans `Info.plist` (`electron-builder.yml`, `CFBundleURLTypes`, à côté de `http` et `https`), que macOS livre à l'app comme un lien d'une autre application (événement `open-url` sur macOS ; sous Windows et Linux, la ligne de commande du lancement ou du second lancement, `second-instance`, lue par `linksFromArgv`) : AppleScript `open location "lucium://…"`, l'action « Ouvrir des URL » de Raccourcis, `open "lucium://…"` dans le Terminal. Le schéma est déclaré que le réglage soit actif ou non (le système ne le sait pas) ; l'application refuse chaque adresse tant que le réglage est coupé, avec une ligne au journal.

| Adresse | Effet |
| --- | --- |
| `lucium://open?url=<adresse web encodée>` | ouvre l'adresse (`http` ou `https`, sans identifiant) dans un onglet, dans l'espace que désignent les règles de Réglages › Navigation (ouverture des liens), comme un lien venu d'une autre application |
| `lucium://new-tab` | met la fenêtre au premier plan avec la barre de commandes d'un nouvel onglet |
| `lucium://search?q=<texte encodé>` | lance la recherche du moteur du profil affiché, dans un onglet (500 caractères au plus) |

Exemples : `osascript -e 'open location "lucium://open?url=https%3A%2F%2Fexample.com%2F"'` ; dans Raccourcis, l'action « Ouvrir des URL » avec `lucium://search?q=lucium` ; `open "lucium://new-tab"`.

**Modèle de menace** (`src/shared/automation-url.ts`, `src/main/shell/automation.ts`). N'importe quelle application, script ou page d'un autre navigateur (qui demande d'abord à l'utilisateur) peut faire ouvrir une adresse. Donc : (1) désactivé par défaut, réglage relu à chaque adresse ; (2) liste blanche fixe de trois commandes, avec leurs paramètres exacts : commande inconnue, paramètre inconnu, absent ou répété, fragment, port, identifiant, chemin, caractère de contrôle, adresse de plus de 2 048 caractères (8 192 pour l'ensemble) sont refusés ; (3) **aucune commande ne lit ni n'efface quoi que ce soit** et aucune ne répond (ni retour, ni `x-callback-url`) : l'appelant n'apprend rien de l'état ; une commande qui lirait ou effacerait devrait d'abord demander à l'utilisateur dans une boîte native, et la liste (testée) n'en contient aucune ; (4) ce qui s'ouvre est une adresse web : jamais `file:`, `javascript:`, `data:`, `view-source:` ni une autre commande `lucium:` ; (5) au plus 20 commandes en 10 secondes, le reste est refusé (une feuille d'automatisation qui ouvre une liste de pages passe, une boucle non) ; (6) une application verrouillée (verrouillage de l'application) abandonne la commande au lieu de la garder pour le déverrouillage ; (7) un refus ne journalise que la raison et le nom de la commande, jamais les paramètres (une recherche peut être privée) ; (8) une fenêtre privée n'est jamais la cible : les commandes vont à la fenêtre principale, comme les liens d'autres applications.

## Notes : éditeur visuel, Markdown dessous

Le panneau « Notes » (`src/renderer/NotesPanel.tsx`) écrit chaque note dans un **éditeur visuel** (`src/renderer/NoteTextEditor.tsx`) : on voit le résultat (titres, gras, italique, barré, listes, cases à cocher, citations, code dans le texte et blocs de code, liens), pas les symboles. La note **reste du Markdown** : `notes.json` ne change pas de format, et une note seulement lue n'est jamais réécrite. Aucune bibliothèque : un `contenteditable="plaintext-only"` (le navigateur n'y écrit jamais d'élément à lui) redessiné depuis le Markdown après chaque modification.

- **Le modèle** (`src/shared/note-doc.ts`, pur) découpe la note en blocs (une ligne, ou un bloc de code entre deux lignes de trois accents graves) qui savent, caractère par caractère, où leur texte visible se trouve dans le Markdown. Une position à l'écran est une position dans le Markdown et inversement ; entre deux caractères séparés par des marques cachées, deux positions existent (dans le gras qui finit, ou après lui) et l'éditeur garde celle que le navigateur indique, pour que la frappe continue un gras ou non comme dans un traitement de texte. La lecture du Markdown (`src/shared/note-markdown.ts`) garde tout texte inconnu (tableaux, images, HTML, titres au-delà de `###`) comme du texte.
- **Les modifications** se font sur le Markdown, jamais par le navigateur : la frappe (`beforeinput` `insertText`) insère les caractères dans le Markdown à l'endroit du curseur, ce qui garde la **mise en forme pendant la frappe** (le second `*` de `*mot*` le met en italique, `# ` fait un titre, ```` ``` ```` puis Entrée ouvre un bloc de code) ; une frappe, une suppression ou un Entrée qui changerait l'aspect de ce qui existait (un `*` tapé dans un italique, la moitié d'une marque laissée par une suppression) réécrit les blocs touchés depuis ce qu'ils montrent (`writeBlock` : marques remises autour des caractères, une barre oblique inverse devant un signe qui serait lu comme une marque). Ce qui est écrit est relu et doit montrer la même chose ; sinon rien ne change, aucun caractère n'est perdu. Seule une méthode de saisie (accents, autres alphabets) écrit directement dans les éléments ; son résultat est relu par différence de texte à la fin de la composition. Le navigateur ne fournit pas de plage cible dans un champ en texte brut : les suppressions par mot (⌥⌫) et par ligne (⌘⌫) sont calculées ici (`Intl.Segmenter`).
- **La barre d'outils** (B, I, S | H1, H2 | •, 1., ☑ | ❝, `</>`, lien | « M↓ ») agit sur la sélection : marques posées ou retirées (avec un curseur seul, sur ce qui sera tapé ensuite), types de bloc (une seconde pression revient au paragraphe), code dans la ligne ou bloc de code selon la sélection, lien saisi dans un champ (adresse web ou mail seulement). « M↓ » montre le Markdown brut dans un champ texte, où les mêmes raccourcis écrivent les marques. Les raccourcis restent : ⌘B, ⌘I, ⌘K, ⇧⌘U ; ⇧⌘X (barré) et ⇧⌘S (télécharger) ne sont pas pris, déjà utilisés par l'application (effacer les données du site, enregistrer la page).
- **Sécurité** : aucun texte de note n'est jamais lu comme du HTML ; un lien n'ouvre qu'une page web (http, https, ⌘-clic, onglet derrière le panneau) ou une adresse mail (`mailto:` remis à l'application de messagerie par le processus principal, `externalLinkOf`). Le collage lit le HTML du presse-papiers dans un document à part (`DOMParser`, inerte : aucun script ne s'exécute, rien n'est chargé), puis `src/shared/note-paste.ts` n'en garde que le sous-ensemble connu (titres, gras, italique, barré, code, liens web ou mail, listes, cases, citations, blocs de code), avec des limites de taille et de profondeur ; scripts, styles, formulaires, cadres et images sont jetés avec leur texte, le reste réduit à son texte.
- **Hors du panneau** (`handleNoteFileRequest`, `src/main/shell/notes-ipc.ts`, canal `noteFiles`) : « Télécharger en .md » (dialogue d'enregistrement, nom tiré du titre par `noteFileName`), « Copier en Markdown », « Copier le texte mis en forme » (HTML et texte brut, `noteHtml`), « Partager » (feuille de partage du Mac, `ShareMenu`, avec le Markdown en texte et en fichier .md écrit dans un dossier temporaire propriétaire seul, effacé au partage suivant et à la fermeture), « Importer un fichier .md… » (dialogue d'ouverture, lecture bornée à `NOTE_FILE_MAX_BYTES`, refus d'un fichier non Markdown, trop long, vide ou qui n'est pas du texte) et le dépôt d'un fichier .md sur le panneau (lu dans le panneau, revérifié par le processus principal). Une note importée passe par la même création qu'une note écrite (`create`). Comme les notes, tout est refusé dans une fenêtre privée et quand la fonction est coupée, avant tout dialogue.

Tests : `note-doc.test.ts` (aller-retour Markdown → éditeur → Markdown pour chaque construction, positions, frappe, suppression, Entrée, boutons, copie), `note-paste.test.ts` (collage), `note-files.test.ts` (nom de fichier, import), `note-editor-dom.test.ts` (éléments), `notes-panel.test.ts` (barre d'outils, menu), `notes-ipc.test.ts` (fichiers, partage, presse-papiers).

## Distribution

`pnpm package` (electron-builder, `electron-builder.yml`) produit `dist/mac-arm64/Lucium.app`, **non signée** ; la variante DRM, elle, est signée avec un Developer ID et notarisée (`docs/drm.md`, section 8). L'`Info.plist` déclare les schémas `http`/`https` et les documents HTML, ce qui rend l'app proposable comme navigateur par défaut ; `app.setAsDefaultProtocolClient` ne fonctionne que depuis ce `.app`. Le test moteur ne tourne pas sur ce `.app` : le paquet n'embarque pas les suites, et l'application construite refuse `--smoke` (elle sort en code 1 avec une ligne `[launch] refused`). Ce qui n'existe que dans le paquet se contrôle avec `pnpm verify:app <chemin de Lucium.app>` (`src/main/verify-app.ts`), sans ouvrir de fenêtre : signature et exigence désignée, identifiant, version, schémas d'adresse de l'`Info.plist`, moteur et fusibles, `app.asar` (empreinte, fichiers dépaquetés, aucun fichier de test), textes de licence, droits de l'application et de ses auxiliaires, profil de provisionnement du service du trousseau, notarisation, puis le refus de `--smoke` et de `--remote-debugging-port` au lancement. Il est fait pour la variante DRM signée ; sur le `.app` non signé de `pnpm package`, il échoue sur la signature, le moteur et la notarisation, ce qui est attendu.

## Confidentialité : réglages réels et listes fixes

Chaque fonction de vie privée a un interrupteur dans `Settings` et **ne coûte rien tant qu'il est coupé** : le DNS chiffré (`dohCustom`) n'appelle jamais `configureHostResolver`, le proxy (`proxyEnabled`) n'appelle jamais `setProxy` (une session jamais touchée est déjà sur le proxy du système), l'historique (`historyOff`) est un simple test au moment d'une visite, la copie (`stripCopiedLinks`) un test au moment de copier. Le DNS et les proxys sont réglés par `Browser.configureNetwork` au démarrage et à chaque changement de réglage, seulement quand leur clé change.

- **Bloqueur : deux interrupteurs, une seule lecture** (`src/shared/blocker.ts` : `adsBlockingOn`, `adsBlockingPatch`, `blockerIsOn`). « Bloquer les publicités et les traqueurs » est `blockAds` **ou** son alias `blockTrackers` (l'interrupteur de Réglages écrit les deux, un ancien état peut n'avoir que l'alias) ; « Bloquer les bannières de cookies » est `blockCookieBanners`. Toute décision « le bloqueur filtre-t-il ? » passe par ces trois fonctions, jamais par `settings.blockAds` à la main : le filtre de requêtes (`requestFilter` de `browser-network.ts` = `blockerIsOn`), la configuration du service (`configureBlocker` donne `ads: adsBlockingOn(…)` à `BlockingService.configure`), le service lui-même (`judge`, `cosmeticCss`, `scriptletCalls`, `cspFor`, navigation nettoyée), le masquage dans les pages (`blocker-css.ts`), la garde de page (`page-guard.ts`), puis la ligne du panneau du site, les protections de Réglages et le tableau de bord. Avant, `requestFilter` et `configureBlocker` ne lisaient que `blockAds` : avec `blockAds` coupé et `blockTrackers` activé (le défaut met les deux à vrai), l'interrupteur affichait « activé » alors que le filtre était coupé. Chaque interrupteur filtre exactement ses listes (`ads` / `cookies` du catalogue ; les listes de traqueurs sont compilées avec celles des publicités, il n'y a pas de catégorie de traqueurs à part). Les réglages (`adsBlockingPatch(false)`) et les tests qui veulent « rien ne filtre » doivent couper les deux clés.
- **Paramètres de suivi** (liste fixe, `trackingParamList()` de `src/shared/privacy.ts` ; correspondance sur le nom entier, sans tenir compte de la casse, jamais sur une valeur) : `__hsfp`, `__hssc`, `__hstc`, `_bta_c`, `_bta_tid`, `_gl`, `_hsenc`, `_hsmi`, `_openstat`, `dclid`, `fb_action_ids`, `fb_action_types`, `fb_ref`, `fb_source`, `fbclid`, `gbraid`, `gclid`, `gclsrc`, `hsctatracking`, `igsh`, `igshid`, `li_fat_id`, `mc_cid`, `mc_eid`, `mkt_tok`, `msclkid`, `oly_anon_id`, `oly_enc_id`, `pk_campaign`, `pk_cid`, `pk_content`, `pk_keyword`, `pk_kwd`, `pk_medium`, `pk_source`, `pk_vid`, `rb_clickid`, `trk_contact`, `trk_module`, `trk_msg`, `trk_sid`, `ttclid`, `twclid`, `vero_conv`, `vero_id`, `wbraid`, `wickedid`, `yclid`, et la famille `utm_*`. Un paramètre qui choisit la page, l'élément ou la langue (`v`, `t`, `list`, `page`, `q`, `id`, `lang`, `ref`, `source`…) n'est jamais retiré. Le retrait sert deux réglages indépendants : à la navigation (`stripTrackingParams`) et à la copie (`stripCopiedLinks`, qui couvre ⇧⌘C et ses variantes, « Copier le lien » des menus, « Copier l'adresse du lien » du menu d'une page et la mini-fenêtre).
- **DNS chiffré** : modes Automatique / Activé (`secure`) / Désactivé (`off`) ; serveurs de la liste fixe de `DOH_PROVIDERS` (Cloudflare, Google, Quad9, Mullvad, OpenDNS : l'adresse publiée par chaque opérateur) ou adresse `https://` saisie (pas d'`http://`, pas d'identifiant, pas de fragment). « Activé » sans serveur utilisable est refusé : rien n'est appliqué, la raison est journalisée et affichée dans Réglages. Désactiver l'option remet les valeurs de Chromium (automatique, sans serveur) ; limite : Electron ne permet pas de relire ce qui était réglé avant.
- **Proxy** : `[http|https|socks4|socks5://]hôte:port`, jamais d'identifiant (une adresse qui en contient est refusée, et un fichier qui en contient retombe sur le proxy du système). Un proxy qui demande un identifiant (407) passe par l'invite de connexion de la fenêtre (`PageEvents.authenticate`) : ce qu'on y tape va à la requête et n'est stocké nulle part. Le proxy global s'applique aux sessions des profils sans proxy propre, aux sessions des fenêtres et onglets privés et aux requêtes de l'application (suggestions, listes de filtres, mises à jour, installation et mises à jour des extensions du Chrome Web Store : `web-store-transport.ts` passe par la pile réseau d'Electron dans la session par défaut, donc aussi par le DNS chiffré, et non par le `fetch` de Node, qui ignorerait les deux) ; une page créée pendant qu'un changement de proxy est en cours attend la fin avant sa première navigation. Si Chromium refuse un proxy, la session est mise sur un proxy qui ne mène nulle part (`CUT_OFF`, `network.ts`) : elle n'a plus de réseau jusqu'au prochain changement du réglage, au lieu de sortir par sa route précédente, et un message le dit. Les noms locaux (`<local>`) restent directs ; la liste « sans proxy » est bornée aux caractères d'un motif d'hôte. Le test de connexion ne joint que le serveur de proxy.
- **Onglet privé** (`TabItem.private`, réglage `privateTabs`) : la page vit dans une session en mémoire (`Browser.privateContext`, une `openEphemeral` partagée par les fenêtres normales, ouverte au premier onglet privé et effacée avec le dernier). L'état normalisé le représente (`state-clean.ts`) mais tout ce qui écrit passe par `persistableState` : fichier d'état, export, copies automatiques ; le reducer ne l'archive pas, ne l'épingle pas, ne le range pas en dossier, ne le met ni dans la liste de lecture ni dans une session ou un espace mis de côté, et n'apprend pas son adresse au classement de la barre de commandes. Hors du reducer : pas d'historique, permissions jamais mémorisées, zoom non enregistré, ni Retouche ni script utilisateur (hors ceux que l'utilisateur a autorisés en privé : la règle d'une fenêtre privée), ce qu'il ouvre (lien, aperçu, recherche) est privé. Limite : un fichier téléchargé reste sur le disque, comme dans la fenêtre privée.
- **Conteneurs d'onglets** (`TabItem.container`, réglage `tabContainers`, liste `Settings.containers` et règles `Settings.containerRules` ; `src/shared/containers.ts`, `container-id.ts`) : une identité à part par onglet. Ce n'est **pas** un profil : une session de profil charge les extensions (une `ElectronChromeExtensions` par session), ce qui serait trop lourd par conteneur ; c'est un **contexte persistant sur le modèle du contexte privé** (`ElectronEngine.openContainer`, partition `persist:container-<id>`, dossier `Partitions/container-<id>`, aucune extension, crochets propres : permissions, téléchargements, bloqueur, options de confidentialité), ouvert à la première page du conteneur et tenu par la fenêtre principale. L'id est un slug (`newContainerId` : nom + suffixe tiré de `ctx.newId()`, jamais réutilisé tant que l'effacement d'un conteneur supprimé court) ; il nomme un dossier : forme vérifiée à chaque frontière (`isContainerId`). Une page garde la session où elle est née : `Browser.sync` refait, dans chaque fenêtre, la page d'un onglet dont la session a changé (`pageSession` comparé à `sessionKeyOf` : conteneur entré, quitté ou supprimé, `tab/set-container`, ou espace passé à un autre profil, `space/update`). Règles : le conteneur d'un onglet privé est ignoré (la session jetable l'emporte) ; sans conteneur existant l'ouverture est refusée plutôt que de donner à la page les cookies du profil ; un lien ouvert depuis une page d'un conteneur y reste, sauf règle d'un site (`container/rule`, hôte et sous-domaines, le plus précis l'emporte, appliquée à l'ouverture d'un onglet et non à une navigation dans un onglet ouvert) ; une page d'extension n'entre jamais dans un conteneur. Les autorisations mémorisées sont celles du conteneur (`Container.permissions`, `container/permission`), jamais celles du profil ; aucune entrée d'historique, pas de surveillance de page (elle lit avec la session du profil), pas d'effacement « à la fermeture » (il ne touche que le profil). L'archive, les sessions et les espaces mis de côté gardent le conteneur de chaque onglet (`ArchivedTab.container`, `SessionTab.container`) ; `normalize` retire un conteneur qui n'existe plus (`pruneContainers`). **Suppression** (`container/delete`) : le reducer retire le conteneur, ses règles, ses onglets (fermés sans passer par l'archive) et ce qui garde leurs pages (archive, sessions, espaces de côté) ; `Browser.dispatch` détruit alors les pages et appelle `ElectronEngine.eraseContainer` (`container-store.ts` : données du site, stockage, cache, identifiants HTTP, DNS, connexions, puis écriture sur disque, chaque étape tentée quoi qu'il arrive aux autres ; ce qui reste est dit à l'utilisateur et journalisé). Le dossier lui-même ne peut pas être supprimé tant que la session vit : au lancement suivant, avec la fonction active, `sweepStoredContainers` retire les dossiers que la liste ne nomme plus (aussi après un plantage). Il laisse le dossier d'un conteneur qu'une copie de l'état faite avant Aide › Restaurer les données… nomme encore (`state.json.avant-restauration-*`, `containersNamedBeforeRestore`) : remettre cette copie doit retrouver ses cookies ; si une de ces copies est illisible, aucun dossier n'est retiré à ce lancement. Cette garde a une durée : un dossier ainsi gardé part quand rien n'y a été écrit depuis 30 jours (`containersKeptTooLong`, `containerFolderLastWrite` : la date d'écriture la plus récente du dossier et de son contenu, sur trois niveaux ; âge inconnu, le dossier reste), avec une ligne `[containers]` au journal qui le nomme et dit son âge. Fenêtre privée : aucune action de conteneur n'y passe (`privateAction`), sa liste est vide et n'est pas héritée ; l'interface ne peut pas modifier `containers` ni `containerRules` par `settings/update` (`ipc-policy.ts`). Fonction coupée : rien n'est lancé, plus de règle, plus d'entrée de menu ; les onglets déjà dans un conteneur y restent (leur identité ne change pas en silence) et les conteneurs restent supprimables. Limites : pas d'extensions dans un conteneur, pas de glisser vers un conteneur (aucune surface de dépôt sans nouveau bouton de la barre latérale), les cookies d'un conteneur ne sont pas dans « Cookies par site ».
- **Questions de permission d'une fenêtre privée, d'un onglet privé ou d'un conteneur** : le moteur connaît leurs pages sous l'identifiant de l'onglet préfixé par celui du contexte (`ephemeral:1/<onglet>`, `container:<id>/<onglet>`) ; le contexte donne à la politique de permissions de la fenêtre l'identifiant de l'onglet lui-même (`scopedPermissionPolicy`, `src/main/engine/ephemeral-scope.ts`), comme il le fait pour les téléchargements. La fenêtre privée retrouve ainsi ses onglets : la question s'ouvre dans son panneau, et la réponse peut être gardée dans sa mémoire (jamais sur disque). Sans cela, elle ne les reconnaissait pas et posait la question en feuille du système, jamais mémorisée. Test : `src/main/engine/private-permissions-wiring.test.ts`.
- **Fenêtres aux onglets indépendants** (`TabItem.windowKey`, réglage `independentWindows` ; `src/shared/window-tabs.ts`, `WindowView` de `src/main/store.ts`) : par défaut toutes les fenêtres normales sont des vues du même état (`window-selection.ts` : espace et onglet choisis propres à chaque fenêtre). Réglage actif, une fenêtre ouverte après la première porte une clé (`window-N`, l'id du gestionnaire de fenêtres) : sa vue (`project`) ne liste que les onglets épinglés et les siens, ses actions s'appliquent à cette vue, et `putBackOwnTabs` remet les onglets qu'elle ne voyait pas à leur place (un onglet qu'elle a ouvert ou désépinglé devient le sien ; ceux d'un espace qu'elle supprime disparaissent ; un `state/restore` ou `backup/restore` remplace tout). Les onglets sans clé sont ceux de la première fenêtre. La clé dure autant que la fenêtre : jamais écrite (`persistableState`, `parseSavedState`), et la fermeture de la fenêtre donne ses onglets à la première (`handOverTabs`). Une vue scindée dont les volets se retrouvent dans deux fenêtres (un volet glissé dans une autre fenêtre, un onglet épinglé désépinglé dans une fenêtre qui ne voyait pas la vue) ne serait dessinée par aucune : elle reste à la fenêtre qui en garde le plus de volets, avec ses épinglés, et se défait sous deux volets (`splitsOfOneWindow`, appelée par `putBackOwnTabs` et `giveTabs`). Mettre un espace de côté, supprimer un conteneur et un import agissent sur les onglets de toutes les fenêtres (`EVERY_TAB_ACTIONS`) ; « Exporter les données » et « Exporter les signets (HTML) » écrivent ceux de toutes les fenêtres (`store.root()`), et « Gérer les espaces » les compte (`UiSnapshot.spaceTabs`, absent quand la fenêtre liste tout ou qu'un verrou cache une partie de l'état). Réglage coupé, `project` est exactement ce qu'il était. Limites : à l'activation les onglets existants vont à la première fenêtre ; au redémarrage tout revient à la première ; les extensions (`chrome.tabs`) ne voient que les onglets de la première fenêtre.
- **Session de l'interface** (la session par défaut d'Electron : les pages de l'interface et les requêtes que l'application fait pour elle-même) : elle n'appartient à aucun profil. Les icônes des sites n'y passent plus (`src/shared/site-icon.ts`, téléchargées dans le profil de l'onglet) ; les requêtes de l'application n'y laissent ni cookie ni copie en cache (`credentials: 'omit'`, `cache: 'no-store'` : suggestions, listes du bloqueur, flux des versions, Chrome Web Store, catalogue et modèles de traduction), et ses images ne posent aucun cookie (`src/shared/interface-images.ts`). « Vider le cache » et « Effacer les données du profil » vident aussi son cache et ses cookies (`clearInterfaceTraces`). Reste : la liste des hôtes qui ont demandé une connexion sécurisée (HSTS, fichier `TransportSecurity` de Chromium, noms hachés) ; Electron n'a aucun appel qui la vide. Elle nomme les services que l'application a joints d'elle-même (moteur de suggestions, listes, mises à jour, traduction), pas les sites visités.
- **Cookies par site** : la valeur d'un cookie ne sort jamais du moteur (`engine/cookie-book.ts` ne rend que nom, domaine, chemin, taille). Un site gardé (`cookieKeepHosts`) couvre ses sous-domaines et les cookies de domaine parent qu'il reçoit ; « Supprimer » un site retire tout ce qu'il a posé, même gardé (l'utilisateur le demande), « Nettoyer » épargne la liste. `cookiesToClean` et `isCookieKept` (`src/shared/cookies.ts`) sont les fonctions à réutiliser par un effacement automatique.
- **Le sort de chaque permission** (`src/shared/permissions.ts`, `routePermission`) : un appareil (WebHID, WebUSB, Web Serial) va au service du matériel ; `GRANTED_PERMISSIONS` est accordé sans question (plein écran, verrou du pointeur, copie, écran gardé allumé, stockage conservé, envoi différé au retour du réseau) ; le verrou du clavier est refusé à toute page (`ALWAYS_REFUSED_PERMISSIONS`), pour qu'Échap quitte toujours le plein écran, comme le dit l'avis posé quelques secondes sur une page qui prend la fenêtre (`src/shared/fullscreen-notice.ts`, dessiné par `src/main/shell/fullscreen-notice.ts`) ; `REFUSED_PERMISSIONS` est refusé sans question à une page web, avec une ligne au journal (réalité virtuelle, NFC, et ce que seule une application web installée d'un autre système reçoit) ; tout le reste est une question, posée avec les mots de `PERMISSION_LABELS`. `src/main/permission-names.test.ts` lit la liste des permissions dans les types de l'Electron installé : un nom qu'une nouvelle version ajoute fait échouer ce test tant que son sort n'est pas choisi, au lieu de devenir une question qui affiche le nom technique.
- **Liens vers une autre application** (`src/shared/external-links.ts`, `ElectronPage.openAppLink`, `askAppLink` dans `electron-engine-permissions.ts`) : un lien `mailto:` ou `tel:` de la page part vers le système sur un clic, sans question. Un lien vers une autre application (`zoommtg:`, `msteams:`, `slack:`, `vscode:`…), suivi dans le cadre principal ou ouvert dans une nouvelle fenêtre, est arrêté, puis l'utilisateur reçoit la question de la permission `openExternal`, qui nomme le schéma ; l'adresse ne part que sur un oui. Avec un clic, la question est posée à chaque fois et propose la case « Toujours ouvrir les liens de ce type depuis ce site » ; sans clic (une page qui lance son application en se chargeant), une seule fois par document, sans la case, et jamais deux questions à la fois. La case cochée avec « Autoriser » garde un oui pour ce site **et** ce schéma, sous un nom à part (`openExternal:zoommtg:`, `appLinkPermission` dans `src/shared/permissions.ts`) : `openExternal` seul reste non mémorisable. Ce oui est rangé avec les autres réponses du site (`sitePermissions`, ou celles du conteneur), listé et retirable dans Réglages › Vie privée et sécurité (Autorisations des sites) et dans le panneau du site ; il répond ensuite sans question, une seule fois par document quand aucun clic n'explique le lien. Rien n'est gardé ni lu pour un onglet privé, ni pour un schéma qui ne part jamais. Les schémas de `NEVER_APP_SCHEMES` et ceux qui commencent par `x-apple` ne partent jamais (fichiers, volumes réseau, sessions distantes, Réglages Système, pages du navigateur). Un lien qui sort du navigateur (`mailto:`, `tel:` ou vers une autre application) demandé par un cadre d'un autre site que l'onglet (`linkAsker`) reçoit la question simple, sous le site de ce cadre : sans la case, et aucune réponse gardée n'est lue, ni celle de la page ni celle du cadre ; un `mailto:` ou un `tel:` y demande en plus un clic dans ce cadre, et une question sans clic de ce cadre ne prend pas celle de la page. Le cadre est nommé par la navigation : celui qui part, ou celui qui envoie l'onglet entier ailleurs (`target=_top`, l'`initiator` d'Electron). Une demande `window.open` ne dit pas quel cadre l'a faite (son référent est vide pour un tel lien) : un clic dans un cadre d'un autre site nomme ce cadre ; sinon la page n'est prise pour celle qui demande que si elle ne contient aucun cadre d'un autre site, et dans le cas contraire la question simple est posée sous le site de la page, sans réponse gardée (limite connue : un cadre qui demande sans clic ne peut pas être nommé). Dans un sous-cadre du même site et pour une redirection du serveur, c'est Chromium qui demande la même permission, et la même question s'affiche, sans la case : la réponse gardée n'y est pas lue. La fenêtre qu'une page ouvre (popup) garde l'ancienne règle : un tel lien y est arrêté sans question. **À mesurer** dans l'application : « Ouvrir dans l'application » de Zoom, Teams, Slack et VS Code, avec l'application installée puis absente.
- **Ce qu'une page lit d'une permission** (`src/main/engine/tab-answers.ts`, `src/preload/permission-state.ts`, `src/shared/permission-state.ts`) : Electron répond à une *vérification* (`Notification.permission`, `navigator.permissions.query`, l'affichage d'une notification) par oui ou non, depuis `setPermissionCheckHandler` seul. Deux conséquences reprises ici. Une réponse donnée sans « Se souvenir pour ce site » est gardée en mémoire pour l'onglet qui a demandé (une origine, une permission, un `webContents`), jusqu'à la fin de sa page : la vérification la lit, et un « oui » n'est pas redemandé dans cet onglet (un « non » l'est si la page redemande). Rien n'est gardé pour un contexte privé, ni pour `openExternal`, ni quand l'utilisateur a fait retenir la réponse (l'état répond alors). Et un site jamais interrogé lit « default » et « prompt » au lieu de « denied » : la précharge `chrome-app` (cadre principal des pages web) remplace les deux accesseurs dans le monde de la page et, quand Chromium dit « denied », demande au processus principal par un message synchrone si quelqu'un a répondu (un seul bit, pour `notifications`, `geolocation`, `camera`, `microphone` ; le canal ne répond qu'au cadre principal d'une page web d'une session du moteur).
- **Fenêtre demandée par un cadre d'un autre site** (`ElectronPage.windowOpenGesture`, `clickedFrameOpens` dans `src/shared/external-links.ts`) : `input-event` n'entend pas un clic dans un cadre que Chromium dessine dans un autre processus ; `before-mouse-event` l'entend, sans dire quel cadre l'a reçu. Deux témoins le désignent : le clic a donné le focus au cadre (`webContents.focusedFrame`), et la demande de fenêtre porte l'adresse du document qui la fait (`referrer`). La fenêtre s'ouvre quand les deux nomment le même site, dans les cinq secondes, une fois par clic. Refusé : une demande sans `referrer` (un cadre qui le masque), un cadre d'un autre site que celui qui a été cliqué. Non couvert : la touche Entrée ou Espace sur un bouton d'un tel cadre, et les cadres d'une fenêtre popup.
- **FedCM** (invites de connexion fédérée de certains fournisseurs de comptes) : non traité. `node_modules/electron/electron.d.ts` (45.0.0) n'a ni réglage ni permission FedCM (la liste des permissions de `setPermissionRequestHandler` n'en contient pas) ; un drapeau de ligne de commande Chromium ne serait pas une API d'Electron, et bloquer les adresses du fournisseur de comptes casserait son bouton de connexion.

## Sécurité

- Interface et pages : `sandbox`, `contextIsolation`, pas de `nodeIntegration`. `src/main/security-source.test.ts` échoue si un fichier livré écrit l'une de ces préférences (ou `webSecurity`, `webviewTag`, `allowRunningInsecureContent`) à sa valeur dangereuse, ou compile du texte en code (`eval`, `Function`) ailleurs que dans les deux fonctions que les pages exécutent aussi (`src/shared/find-replace.ts`, `src/shared/text-format.ts`).
- Le renderer n'est pas de confiance : le processus principal revalide tout (IPC limité aux deux surfaces d'interface, saisie recalculée côté main, `isNavigableUrl` appliqué par le reducer, donc aussi pour `window.open`, import et extensions).
- Permissions web (caméra, micro, géolocalisation, notifications…) : la page **demande**, l'utilisateur répond dans l'invite de Lucium, et rien n'est accordé sans sa réponse. Une courte liste sans danger (`GRANTED_PERMISSIONS` : plein écran, verrou du pointeur, copie…) est accordée sans question. Le sort de chaque permission est décrit plus haut (`routePermission`).
- **API matérielles du web** (WebHID, WebUSB, Web Serial) : réglage `webHardware`, désactivé par défaut, qui ne pose **rien** quand il est coupé. Electron laisse le navigateur choisir l'appareil (`select-hid-device`, `select-usb-device`, `select-serial-port`) mais `setDevicePermissionHandler` ne reçoit ni cadre ni onglet, et sa mémoire des appareils accordés n'a aucun appel de révocation (vérifié en 45.0.0 dans `electron.d.ts`). Le service `src/main/engine/web-hardware.ts` (règles pures dans `src/shared/web-hardware.ts`) pose donc, sur les sessions des profils seulement (jamais sur une session privée), les trois sélecteurs (menu natif qui nomme le site, cadre principal d'un onglet en origine sécurisée, après un clic) et un gestionnaire d'appareils qui répond **depuis le registre de Lucium** (`DeviceGrants`, en mémoire, une entrée par profil, origine et appareil précis, qui tombe avec l'onglet qui l'a reçue). `routePermission` envoie `hid`, `usb` et `serial` à ce service (jamais aux réponses mémorisées). Voir `docs/api-materielles.md` (modèle de menace, limites : une connexion déjà ouverte ne se ferme pas du dehors).
- **Partage d'écran** (`getDisplayMedia`) : Electron demande la permission `display-capture` pour tout appel de script, **sans exiger de geste de l'utilisateur** (vérifié en 45.0.0) ; le moteur refuse donc (`ElectronPage.takeShareGesture`, registre `GestureLedger` à part de celui de `window.open`) toute demande sans clic ni touche dans l'onglet, avant de lire une réponse mémorisée, puis passe par l'invite des permissions web (mémorisable, révocable depuis le centre de contrôle du site). Une page d'extension, une popup, un fichier local n'obtiennent jamais cette permission (`routePermission`), à **une seule exception, étroite, et ce n'est pas une page d'extension** : la page d'aide d'une capture du son d'un onglet (`chrome.tabCapture`, voir plus haut : fenêtre ordinaire cachée de Lucium, repérée par son identifiant de contenu web tant que la réclamation qu'elle sert n'a pas commencé) l'obtient pour sa demande de flux, dans le gestionnaire de permissions du moteur et pas dans `routePermission` (une autre permission, une page qui n'est pas une page d'aide, une page d'aide d'une autre session que celle de son profil, un autre cadre que son cadre principal, une réclamation déjà commencée : refus) ; le gestionnaire de `getDisplayMedia` répond alors le son de l'onglet et l'image de la page d'aide elle-même (que sa page retire), jamais une liste d'écrans ; une page d'extension n'obtient rien, pas même cette liste. Le choix de la source revient au menu natif de Lucium, sur tous les systèmes (`src/main/engine/display-media.ts`, règles pures dans `src/shared/display-media.ts`) : le sélecteur du système (`useSystemPicker`) n'est jamais demandé, il fait planter l'application dans Electron 45 (NSGenericException, ScreenCaptureKit). Le son du système n'est transmis que pour un écran entier sous Windows. Réglage `allowScreenShare` (activé par défaut, lu à chaque demande : `PermissionPolicy.screenShareAllowed`) : désactivé, toute demande est refusée sans question. Vérifié dans `src/main/smoke-runtime.ts` sans jamais capturer (un faux gestionnaire remplace le vrai sur toute session que la page peut atteindre).
- **Mémoire et processeur par onglet** : la carte de survol (`HoverCard.tsx`) interroge `tabResources` (canal `lucium:tab-resources`) tant qu'elle est ouverte seulement : une fois à l'ouverture, une seconde après (le processeur est une moyenne depuis la mesure précédente, la première n'en a pas), puis toutes les 3 s (`pollResources`). Le processus affiché est celui de la page de l'onglet, jamais un autre (`tabResourcesOf` applique la garde de `mayKillProcess`) ; « Mémoire libérée » pour un onglet endormi (il n'a plus de processus), « — » pour un onglet gelé. Réglage `showTabMemory`, désactivé par défaut : la carte reste la même et rien n'est mesuré.
- Navigation vers un schéma non web bloquée dans la page elle-même.
- **Fichiers locaux ouverts dans un onglet** (`src/main/engine/local-file-guard.ts`) : le fusible `grantFileProtocolExtraPrivileges` reste ouvert (l'interface est chargée en `file://` depuis `app.asar`, et EVS ne signe pas d'ensemble où il est fermé : `docs/drm.md`, section 5), et il donne à toute page `file://` le droit de lire n'importe quel fichier. Le crochet `onBeforeRequest` de chaque session de pages (profil, fenêtre privée, conteneur, posé à sa création et quels que soient les réglages) le reprend : une page locale ne lit aucun autre fichier, ni par `fetch`/`XMLHttpRequest`, ni par un cadre ou un objet, ni par un import JSON ou texte. Elle charge seulement le document lui-même (le lecteur PDF relit le fichier qu'il montre) et, par leur extension, les images, styles, scripts, polices, médias et PDF rangés dans son dossier ou dessous, sans fichier ni dossier caché, liens symboliques suivis ; posée directement dans un dossier large (la racine et ses dossiers, le dossier personnel et ses dossiers : Téléchargements, Bureau…), seulement le dossier `<nom>_files/` que son navigateur a enregistré à côté. L'interface, dans la session par défaut, n'a pas ce crochet. Reste permis, comme la règle le choisit : dessiner sur un canevas les images et vidéos de ce dossier.
- **Page locale et sites web** (même fichier, seconde moitié) : le même fusible fait sauter à Chromium la règle de même origine pour ce qu'un document `file://` demande au web. Sans reprise, son `fetch` et son `XMLHttpRequest` lisaient la réponse de n'importe quel site, d'un service de la machine ou du réseau local (mesuré par le test moteur `probes-web`). Lucium juge donc la réponse comme le fait un navigateur pour l'origine « null » : une lecture demandée par un cadre d'origine `file://` (`fetch`, `XMLHttpRequest`, module, police, image `crossorigin`, script d'un worker ; quel que soit le mode que la requête annonce dans `Sec-Fetch-Mode`, puisque la page le choisit et qu'avec l'accès universel un `fetch` en mode `same-origin` ou `no-cors` reçoit aussi la réponse) n'est rendue que si le serveur la partage (`Access-Control-Allow-Origin: *` ou `null` ; avec des cookies ou un identifiant HTTP, `null` et `Access-Control-Allow-Credentials: true`). Sinon la requête est annulée à l'arrivée des en-têtes. Ce qu'une page montre sans le lire (image, feuille de style, script classique, média demandés en `no-cors`, cadre, navigation, WebSocket) se charge comme avant, comme dans une page enregistrée. Une requête web sans cadre ni page, émise par un fichier local (`initiatorOrigin` en `file://` : un worker partagé d'une page locale), ne part pas, comme pour les fichiers du disque. Les deux crochets d'en-têtes (`onBeforeSendHeaders`, `onHeadersReceived`) ne sont posés sur les requêtes web d'une session qu'à l'ouverture de son premier fichier local, et y restent jusqu'à la fin du lancement : une session qui n'ouvre aucun fichier local ne paie rien. Limites connues : la requête part quand même (comme dans un navigateur pour une requête simple), mais sans la demande préalable (« preflight ») qu'un navigateur envoie pour une requête non simple ; et ce que Blink décide seul reste ouvert (lire les pixels d'une image d'un site dessinée sur un canevas, les règles d'une feuille de style d'un site).
- **Export chiffré, verrou, pages d'un onglet rouvert** : voir la section « Export chiffré, verrouillage, historique d'un onglet rouvert » ci-dessus (contenu d'un fichier traité comme hostile, coût `scrypt` borné avant tout calcul, phrase jamais enregistrée ni journalisée, verrou d'interface et non chiffrement).
- **Copies automatiques de la session** : fichiers du dossier des données (`session-backups/`, droits 0700 / 0600), jamais envoyés ; un fichier de copie est traité comme hostile (taille bornée avant lecture, format et version vérifiés, espaces, onglets et dossiers réparés comme ceux du fichier d'état, adresses non chargeables retirées) ; l'identifiant venu de l'interface n'est jamais joint à un chemin avant d'avoir la forme `copie-<13 chiffres>` ; `backup/restore` est une action réservée au processus principal, qui copie d'abord ce qu'elle remplace et ne remplace rien si cette copie échoue ; rien n'est copié depuis une fenêtre privée (le service ne voit que l'état partagé des fenêtres normales).
- **Scripts utilisateur** (`src/shared/userscript.ts`, `src/main/userscripts.ts`, `src/main/shell/userscripts-service.ts`) : un système à part des Retouches (un script vise des motifs `@match`, pas un site, et sa vie est autre : il arrive désactivé) qui en réutilise le véhicule, `Page.evaluate` à `dom-ready` (`Browser.applyUserScripts`, à côté d'`applyBoost`). Tout fichier ou texte importé est hostile : 200 ko au plus (octets), en-tête borné, **`@grant none` seulement** (pas de `GM_*` ni `unsafeWindow`), `@require` refusé, motifs web seulement ; le script est **ajouté désactivé** et l'utilisateur lit son code dans la feuille d'import puis l'active lui-même ; le même script réimporté remplace l'ancien et redevient désactivé. Il ne s'exécute pas sur une page de connexion, de paiement ou de gestionnaire de mots de passe que son adresse fait reconnaître (`isSensitiveUrl` : liste d'hôtes, premiers libellés `login.`, `secure.`, `pay.`… dès deux étiquettes et après un `www.`, `.bank`, et segments de chemin `/login`, `/signin`, `/signup`, `/auth`, `/oauth`, `/connexion`, `/password`, `/checkout`, `/pay`, `/payment`, `/billing`, lus décodés et sans leur paramètre `;…`). C'est une liste de mots, pas une preuve : une page de ce genre dont l'adresse ne dit rien est traitée comme les autres, jamais dans une fenêtre privée ni dans un onglet privé d'une fenêtre normale sauf choix par script, et seulement quand le réglage global `userScripts` est activé (désactivé par défaut : rien n'est lu, rien ne tourne). Le fichier `userscripts.json` du dossier des données ne garde que le texte, l'état activé et le choix « fenêtre privée » : le nom, les motifs et l'heure d'exécution sont relus du texte à chaque chargement, et une entrée que le lecteur n'accepte plus est écartée après copie du fichier. Les erreurs d'exécution s'écrivent dans la console de la page ; un script que la page refuse à l'analyse est journalisé et montré dans la liste. Limites : `@run-at document-start` s'exécute à `dom-ready` (un peu après les premiers scripts de la page), seule la fenêtre principale d'une page est visée (pas les cadres), pas de mise à jour automatique.
- **Fenêtres contextuelles** (`window.open` avec une liste de caractéristiques : connexion avec un compte tiers, PayPal, 3-D Secure) : une vraie fenêtre (`src/main/engine/popup-windows.ts`, décisions pures dans `src/shared/popup.ts`) pour que `window.opener`, `postMessage` et `window.close()` fonctionnent ; un ⇧-clic reste un Coup d'œil, un lien ou un `window.open` sans caractéristiques reste un onglet (une mini-fenêtre par défaut vers un autre site : réglage `littleArcNewTabLinks`, `src/shared/little-modifier.ts`). Une popup est une page web et rien de plus : même session que la page d'origine (profil, ou session en mémoire d'une fenêtre privée), `sandbox`, aucun préchargement, aucun accès à `window.lucium`, seulement `http(s)` et `about:blank`, un clic exigé, trois au plus par onglet (la popup d'une popup compte pour l'onglet), fermée avec son onglet, hors de l'état et des extensions. Elle passe par les mêmes crochets de session que les onglets (permissions, téléchargements, bloqueur, options de confidentialité) et reçoit les pages d'erreur et le HTTPS d'abord ; elle ne peut pas poser de question dans la fenêtre de l'onglet : une invite de permission y est une feuille du système posée sur la fenêtre de la popup (réponse non mémorisée), une authentification HTTP y est refusée, et les raccourcis du menu (⌘W, ⌘T…) ne s'y appliquent pas aux onglets.
- **`alert()`, `confirm()` et `prompt()` des pages** : Electron répond `null` à `prompt()` sans rien afficher, et montre `alert()` et `confirm()` dans une feuille de macOS qui ne nomme pas le site, a ses boutons en anglais et peut s'ouvrir depuis un onglet en arrière-plan par-dessus l'onglet affiché (`-run-dialog`, non contournable depuis le processus principal sans API privée). Donc `src/preload/dialog-bridge.ts` (préchargement de session, cadre principal seulement) remplace les trois fonctions dans le monde principal par un `Proxy` de la fonction native qui fait un `ipcRenderer.sendSync` sur le canal de la fonction (`PAGE_DIALOG`) : le script de la page est bloqué tant que le processus principal n'a pas affecté `event.returnValue` (affectation tardive permise), ce qui rend l'appel synchrone comme le veut la spécification. La page n'obtient ni `ipcRenderer` ni aucune API, chaque fonction reste une propriété ordinaire que la page peut réaffecter, et les sous-cadres gardent les fonctions d'Electron (`null` pour `prompt()`, sa feuille pour `alert()` et `confirm()` : décision du 12 novembre 2026, seul le cadre principal reçoit la boîte). Une page de bac à sable du web (origine opaque en `http(s)`) garde `alert()` et `confirm()` natifs, que Chromium filtre lui-même selon `allow-modals` (`bridgedDialogsOf`). Appelées depuis le gestionnaire d'un événement de départ de confiance (`beforeunload`, `pagehide`, `unload`, lu sur `window.event` par des accesseurs pris avant tout script de la page, sans écouteur qui priverait la page du cache de retour), les trois rendent aussitôt la réponse d'une annulation, comme Chromium. Le processus principal (`ElectronEngine.pageDialog`) n'écoute que le cadre principal d'une page d'**onglet** et revalide tout (`src/shared/page-dialog.ts` : le message seul pour `alert()` et `confirm()`, deux chaînes pour `prompt()`, bornés) ; une charge non conforme est refusée (la réponse d'une annulation, un journal sans le texte du message). Une page sans boîte de Lucium (ni l'interface, ni un Coup d'œil, ni une fenêtre contextuelle, ni une mini-fenêtre, ni une page qui n'est pas du web) reçoit `DIALOG_NATIVE` pour `alert()` et `confirm()`, et son pont appelle alors la fonction native, comme avant ; `prompt()` y reçoit `null`. L'hôte affiché vient de l'adresse que le navigateur tient pour le cadre, jamais du texte de la page ; le titre est « <hôte> demande : » pour `prompt()`, « <hôte> indique : » pour les deux autres ; le message est du texte brut (jamais du HTML), nettoyé des contrôles et des caractères d'inversion de sens, coupé à 1000 caractères. Chaque issue répond, y compris la fermeture de l'onglet, la navigation du cadre principal et la mort du moteur de rendu (la page reçoit la réponse d'une annulation : `null`, `false`, rien). Le panneau (`dialog`, `Browser.askPrompt`, `request.kind`) est modal, attend derrière un panneau en cours comme les invites de permission, et n'est pas remplaçable par un autre panneau tant qu'il est ouvert ; `confirm()` s'ouvre sur « OK » (Entrée), Échap ou « Annuler » rend `false` ; `alert()` n'a que « OK », qu'Entrée et Échap ferment ; la fermeture rend le clavier à la page. **Une question d'un onglet qui n'est pas à l'écran attend son onglet** (`whenOnScreen`, `src/main/shell/browser-dialogs.ts`) : les boîtes des pages, la connexion qu'un serveur demande et une permission ne s'ouvrent jamais par-dessus un autre onglet, et l'onglet qui demande n'est plus amené au premier plan par son propre appel (il prenait le clavier). Une notice dit quel site attend, avec « Afficher » ; la question s'ouvre quand l'onglet est affiché (`off-screen-questions.test.ts`). Une page qui n'est pas un onglet (Coup d'œil, panneau latéral) est interrogée aussitôt. Une page qui enchaîne les boîtes, des trois fonctions confondues (la suivante dans les 5 s qui suivent la fermeture de la précédente, à partir de la troisième), se voit offrir la case « Empêcher cette page de créer d'autres boîtes de dialogue » ; cochée, ses appels suivants rendent aussitôt la réponse d'une annulation sans rien afficher jusqu'au prochain document. La valeur saisie ne traverse que ce canal : elle n'est ni journalisée ni conservée.
- **Partage de Retouches et de thèmes** (fichier ou lien, sans compte ni serveur) : tout ce qui arrive est hostile. Les règles sont pures et testées dans `src/shared/` : `boost-css.ts` lit le CSS avec le découpage en jetons de la spécification (échappements décodés, chaînes et commentaires sautés) et refuse `@import`, tout `url()`, `image-set()`, `src()`, `image()`, `cross-fade()`, `attr(… type(<url>))`, `expression()`, `behavior`, `-moz-binding`, les caractères de contrôle, ceux qui changent le sens de lecture d'une ligne et les fins de ligne invisibles U+2028 et U+2029 (la règle des scripts utilisateur, `unreadableCode` ; un autre caractère invisible est accepté avec un avertissement) ; `boost-share.ts` borne la taille (512 Ko), valide chaque champ, reconstruit la Retouche champ par champ (rien d'inconnu n'est recopié, ni id, ni état) et fabrique les phrases de refus. Le processus principal (`src/main/shell/boost-share.ts`, environnement injectable `ShareEnvironment`) lit le fichier avec une borne (`bounded-file.ts` : fichier ordinaire, pas de tube ni de périphérique), refuse un site qui est un suffixe public (`boost-host.ts`, liste de `tldts-experimental` déjà livrée pour le bloqueur), montre une feuille (nom, site, contenu, début du CSS et du script) et ne distribue l'action `boost/import` (réservée au processus principal, refusée en fenêtre privée) qu'après accord ; le réducteur relit la Retouche avec les mêmes règles. **Un script importé n'est jamais exécuté sans que la personne l'ait lu** : il est rangé avec `jsEnabled: false`, `combineBoosts` l'ignore, un enregistrement qui ne dit pas `jsEnabled: true` ne le réveille jamais, et l'éditeur affiche le code avec le bouton « Activer le JavaScript ». Le réglage `boostScriptImport` (`ask` par défaut, `never` retire le script) ; l'interrupteur `boostSharing` (activé par défaut) masque toutes les entrées et fait refuser les demandes par le shell et par le réducteur. Le canal `boostShare` n'accepte que quatre demandes sans chemin ni texte (le shell ouvre lui-même la boîte de dialogue et lit le presse-papiers) et sert une demande à la fois par fenêtre.
- **Lecture automatique** : Electron laisse par défaut démarrer seul tout média (`no-user-gesture-required`), ce que Chromium ne fait pas. Chaque page est créée avec une politique explicite (`src/main/engine/autoplay.ts` : Chromium, `document-user-activation-required`, sauf choix contraire de l'utilisateur) ; Electron ne permet pas de la changer ensuite, donc `Browser.ensurePage` choisit le mode d'après l'adresse de l'onglet et `rebuildForAutoplay` refait la page (historique repris par `navigationHistory.restore`, au plus une fois toutes les 5 s) quand l'onglet arrive sur un site d'un autre mode. Mesuré dans Electron 45 avec de vrais clics : `document-user-activation-required` reproduit les quatre cas de la politique de Chromium (page atteinte par un lien de même origine : joue, `AudioContext` en marche ; atteinte depuis une autre origine : `NotAllowedError`, `AudioContext` suspendu ; après un clic : joue ; après un rechargement : refusé de nouveau), `no-user-gesture-required` laisse tout jouer, `user-gesture-required` refuse même le lien de même origine et laisse tourner l'`AudioContext` (donc non proposé). Une vidéo muette d'un onglet affiché peut toujours démarrer seule (aucune valeur d'Electron ne l'empêche).
- **Listes de filtres personnalisées** : le contenu d'un fichier ou d'un texte collé est une entrée hostile. Il est relu ligne par ligne (`src/shared/custom-filter-lists.ts`) et seules les règles applicables sont gardées : jamais de script (`##+js(...)`), pas d'expression régulière (une règle de 8 caractères fige le processus principal sur une adresse de 24 : mesuré), au plus deux jokers (trois : 89 s sur une adresse de 8 000 caractères), pas de sélecteur contenant `{`, `}` ou `/*` (il fermerait la règle de style où le moteur l'écrit). Le fichier est choisi par le processus principal (l'interface ne donne jamais de chemin) et borné (8 Mo, 1 000 000 de caractères collés, 20 listes). Rien n'est téléchargé depuis une adresse. Les options d'une règle sont coupées là où le moteur les coupe (au dernier `$` non échappé qui n'est pas suivi d'un `/`), pour qu'une expression suivie de `$3p` soit vue comme une expression.
- **Coût d'une règle du bloqueur, toutes listes confondues** (`src/shared/filter-lists.ts` : `FILTER_ADDRESS_MAX`, `filterRuleHazard` ; `src/main/blocking/ghostery-engine.ts` : `withoutCostlyRules`). Le moteur compare chaque requête dans le processus principal, et transforme chaque `*` d'une règle en `.*` : une règle à plusieurs jokers coûte une puissance de la longueur de l'adresse, que la page choisit. Deux bornes : le moteur ne reçoit que les 2 048 premiers caractères d'une adresse (une adresse coupée n'est jamais réécrite par `$removeparam`), et à la compilation les règles dont l'expression peut dépasser un budget d'étapes sur cette longueur sont écartées, avec leur nombre dans le journal (garde commune aux règles des extensions, `src/shared/regex-guard.ts`). Restent : un joker n'importe où, deux après un nom d'hôte, les expressions lues en un passage. Mesuré le 11 novembre 2026 sur les huit listes du catalogue : 183 règles réseau écartées sur 130 196, dont 35 pour une assertion avant ou arrière que la garde refuse sans la juger. L'identifiant du moteur porte un numéro de révision, pour qu'un moteur compilé avant ce tri ne revienne pas du cache.
- **Identité des pages** : les pages de toutes les sessions de pages (profils et fenêtres privées) et les fenêtres qu'elles ouvrent se présentent comme un navigateur ordinaire basé sur Chromium, de la même version majeure que le Chromium embarqué (`Chrome/<majeure>.0.0.0`, sans `Electron/…` ni nom d'application, ce que certains services de comptes prennent pour un navigateur intégré), **sauf sur les deux hôtes de connexion de Google, qui voient Electron tel qu'il est** (point suivant) ; les pages de l'interface et les requêtes que l'application fait pour elle-même (listes du bloqueur, mises à jour, suggestions) gardent l'identité d'Electron et de l'application (`src/shared/user-agent.ts`, `ElectronEngine.presentPagesAsChrome`). **`window.chrome.app`** : l'identité (*user agent*) seule ne suffit pas à un grand service de comptes. Un navigateur basé sur Chromium donne à toute page web `window.chrome.app` ; celui d'Electron est un objet vide, et ce service refuse alors le navigateur dès la saisie d'une adresse (« Impossible de vous connecter… ce navigateur ou cette application ne sont peut-être pas sécurisés », vu avec Gmail et Slack). Mesuré dans des instances jetables avec une fausse adresse (`@example.com`, ni mot de passe ni compte réel), un profil neuf à chaque essai et l'identité changée par DevTools : sans rien → refusé ; `chrome.app` seul → accepté (« Impossible de trouver ce compte ») ; `csi` + `loadTimes` sans `app` → refusé ; avec ou sans `Sec-CH-UA` (marques de navigateur ajoutées) → même résultat, et les mêmes fonctions simples suffisent (pas besoin de masquer `toString`). Donc `src/preload/chrome-app.ts` définit `chrome.app` (la valeur qu'un navigateur basé sur Chromium donne à une page qui n'est pas une application installée) avant les scripts de la page, dans les pages http(s) seulement (le `chrome` d'une page d'extension est le vrai). Reste non mesuré : les écrans qui suivent l'adresse (mot de passe, vérifications) et les pages de connexion de ce service dans un cadre intégré. **Indices du client** (*Client Hints*) : Electron ne donne aucun moyen de régler les marques que Chromium annonce ; seul le *user agent* est remplacé. **Mesuré le 13 novembre 2026** (suite `client-hints`, Electron 45.2.1, Chromium 156.0.8078.75, macOS), à l'identique dans un onglet du profil normal (protection Standard et Renforcée), une fenêtre privée et une fenêtre d'un second profil : Chromium met `Sec-CH-UA: "Not:A-Brand";v="8", "Chromium";v="156"`, `Sec-CH-UA-Mobile: ?0` et `Sec-CH-UA-Platform: "macOS"` sur les requêtes que fait une page (image, script, image d'un autre site) et **aucun** sur la requête de la page elle-même (la navigation) : Electron ne donne pas à Chromium de quoi décider les indices d'une navigation (ce n'est pas le *user agent* remplacé, comme on le croyait). Les indices qu'un site demande par `Accept-CH` (version complète, version du système, architecture, modèle) ne partent jamais. `navigator.userAgentData` donne les mêmes marques, dans le même ordre (« Not:A-Brand », « Chromium » : ni « Electron », ni « Lucium », ni « Google Chrome », ce que `smoke-popups.ts` vérifie aussi), et `getHighEntropyValues` répond. Un Chromium ordinaire met les trois indices sur la navigation aussi : un site qui comparait la requête de sa page à celles qui suivent voyait un navigateur qu'aucun Chromium n'est. **Décidé le 13 novembre** : le moteur ajoute exactement ces trois en-têtes aux navigations des pages web (cadre principal et sous-cadres), avec les valeurs que Chromium met sur le reste. Ces valeurs ne sont pas calculées par Lucium : elles sont lues du moteur, une fois par lancement, dans la page de la fenêtre principale, un Chromium identique à celui des pages (`navigator.userAgentData` : marques dans leur ordre, indicateur mobile, système ; `src/main/engine/engine-client-hints.ts`, appelé par `ElectronEngine.learnClientHints` dès que cette page est validée, puis de nouveau à son document si la première lecture vient trop tôt), puis seulement écrites sous la forme des en-têtes, en champs structurés de HTTP (`clientHintsOf`, `src/shared/client-hints.ts`) ; aucune marque nouvelle. Au lancement, les onglets restaurés commencent à charger pendant que la page de l'interface arrive (`browser.start()` suit de peu le chargement de la fenêtre dans `src/main/index.ts`) : dès que la fenêtre principale a donné sa page, une navigation attend la lecture, au plus `HINTS_WAIT_MS` (2 s) comptées depuis ce moment et une seule fois par lancement, pour que la première page porte les indices comme les autres. Si la lecture n'arrive pas dans ce délai, ou échoue, une navigation part sans indice, comme Chromium l'envoie, plutôt qu'avec une valeur devinée, et le journal le dit une fois (un échec de lecture est écrit avec sa raison). Ils sont posés dans le crochet `onBeforeSendHeaders` de chaque session de pages, celui qui pose déjà `Sec-GPC` (`installPrivacyHeaders`, `src/main/engine/electron-engine-network.ts`) : profils, conteneurs, fenêtres privées et invitées. Seulement vers une adresse à laquelle Chromium envoie des indices (https, ou http vers cette machine : `localhost`, `*.localhost`, 127.0.0.0/8, `[::1]`), et jamais à la place d'un en-tête `Sec-CH-UA…` déjà présent. Ordre dans le crochet : les indices d'abord, comme Chromium les ajoute avant qu'une extension voie la requête (une extension peut les lire, les changer ou les retirer, comme dans Chrome), puis les règles et les écouteurs des extensions, puis `Sec-GPC` en dernier. Jamais pour les requêtes de l'application elle-même ni pour ses pages : la session de l'interface et les sessions des recherches de l'application ont leur propre crochet (`own-requests.ts`), une requête faite par l'application dans une session de profil n'est jamais une navigation, et les adresses `lucium:`, `chrome-extension:`, `file:` et `data:` sont hors du filtre. La boutique d'extensions : ses pages reçoivent les mêmes trois indices (Chromium les met déjà sur leurs autres requêtes, et les extensions n'y touchent pas : `keptFromExtensions`) ; aucun code n'ajoute de marque pour elle : `versionForStore` (`src/shared/web-store.ts`) ne change que la version que `chrome.webstorePrivate.getFullChromeVersion` répond à sa page, et `src/preload/chrome-app.ts` ne définit que `window.chrome.app` ; les deux ne croisent donc pas ces en-têtes. Coût : le crochet est toujours là sur une session de pages, mais avec tous les réglages coupés il ne voit que les navigations (`types: ['mainFrame', 'subFrame']`) ; les images et les scripts ne passent pas par lui, tant qu'aucun onglet de la session n'a été sur une page de connexion de Google (point suivant). Une lecture de `navigator.userAgentData` par lancement, dans la page de l'interface. Au lancement, la requête des premières pages (onglets restaurés) part au plus tard quand cette lecture est faite : le temps entre le début du chargement des onglets et la validation de la page de l'interface, plus un aller-retour vers elle ; non mesuré (attendu : de l'ordre d'une à quelques centaines de millisecondes, en grande partie avant que la fenêtre ne s'affiche ; 2 s au plus si la lecture n'arrive pas). Les navigations suivantes n'attendent rien. Un site voit toujours qu'il ne parle pas à Google Chrome, comme pour les autres navigateurs basés sur Chromium, qui annoncent leur propre marque ; il ne peut pas lire le nom de Lucium ; annoncer « Google Chrome » serait une fausse déclaration. Limites : les valeurs viennent de la page de l'interface, pas d'une page web ; il faut qu'Electron donne aux deux les mêmes données de *user agent* (l'interface garde son propre *user agent*, celui de l'application), ce que la suite `client-hints` contrôle désormais en comparant la navigation aux autres requêtes et à `navigator.userAgentData` de la page ; son premier passage (13 novembre, 41 sur 44) a confirmé les mêmes valeurs partout et montré la seule limite d'alors : la toute première navigation du lancement partait sans indice, avant la lecture ; d'où l'attente bornée ci-dessus (pas encore repassée). Non mesuré : l'ordre des en-têtes sur le fil (les indices sont mis en tête de ce que rend le crochet, là où Chromium les écrit sur une navigation), une redirection vers une adresse http d'une autre machine (attendu : pas d'indice, le crochet décide à chaque étape), une page qui refuse `ch-ua` à ses cadres par `Permissions-Policy` (Chromium ne leur enverrait pas les indices ; Lucium les ajoute à la navigation du cadre).
- **Pages de connexion de Google** (`accounts.google.com` et `accounts.youtube.com`, en https, avec le port par défaut ; `src/shared/google-sign-in.ts`, `src/main/engine/google-sign-in-agent.ts`) : sur ces deux hôtes, et dans l'onglet qui y est, Lucium montre Electron tel qu'il est, pas le Chrome des autres pages. **Pourquoi** : Google refusait la connexion de certains comptes (« Ce navigateur ou cette application ne sont peut-être pas sécurisés », au plus tard après le mot de passe) à un navigateur qui se dit Chrome (*user agent* `Chrome/<majeure>.0.0.0`, `window.chrome.app`, trois indices `Sec-CH-UA`) alors que le reste de ses signaux est celui d'Electron : un mélange qu'aucun vrai Chrome ne produit (cause probable, non prouvée par le code : Google ne la publie pas). **Mesuré le 16 novembre 2026** par le mainteneur, sur une build d'essai et un profil neuf, avec un compte réel que Google refusait : avec l'identité d'Electron sur ces deux hôtes, la connexion aboutit ; ni la version de Lucium, ni le profil, ni les cookies, ni l'ajout des indices `Sec-CH-UA` n'expliquaient le refus. Précédent public cité par le mainteneur : le navigateur Orca (pull request n° 36519). La règle que Google publie pour sa connexion va dans le même sens (un navigateur ne doit pas prendre le *user agent* d'un autre navigateur sur `accounts.google.com`, ni réécrire les en-têtes ; blog des développeurs de Google, 28 août 2020). **Ce qui change**, dans l'onglet qui est sur ces hôtes et lui seul : (1) `navigator.userAgent` et l'en-tête `User-Agent` de toutes ses requêtes sont ceux d'Electron (nom de l'application, `Chrome/<version complète>`, `Electron/<version>`) : `webContents.setUserAgent` quand le cadre principal va vers ces hôtes (une fois) et pour rendre l'identité des autres pages quand il en sort, **depuis `did-start-navigation` et nulle part ailleurs** : appelé pendant qu'une navigation charge, `setUserAgent` fait recharger l'onglet par Chromium (`WebContentsImpl::SetUserAgentOverride`, puis `NavigationControllerImpl::Reload`, qui recharge la **dernière entrée validée**, pas la navigation en cours), sauf pendant `did-start-navigation` ; c'est ce rechargement, appelé depuis `will-redirect` et `did-redirect-navigation` dans la 1.1.1, qui perdait la navigation (page blanche, roue qui tourne) quand Gmail redirigeait vers `accounts.google.com`. Une redirection ne s'annonce pas par `did-start-navigation` : celle du cadre principal qui **entre** dans ces hôtes ou en **sort** est donc annulée (`will-redirect`, `event.preventDefault()`, qui annule la navigation et non la seule redirection) et l'onglet est envoyé à l'adresse où la redirection allait par `loadURL`, lancé juste après (`setImmediate` : `loadURL` est refusé pendant qu'une redirection est retenue, crbug 347742) ; cette navigation s'annonce par `did-start-navigation`, qui règle l'*user agent* avant la requête. **Limites voulues** : (a) seule une redirection qui suit une requête **GET** est reprise : Electron ne dit ni la méthode ni le code d'une redirection, et une redirection 307/308 d'un POST doit rester un POST ; le crochet `onBeforeSendHeaders` de la session dit au module la méthode de chaque requête du cadre principal (`noteRequest`), et une redirection qui suit autre chose qu'un GET, ou une requête dont le module n'a pas été informé, n'est pas touchée (l'onglet garde alors l'identité qu'il avait jusqu'à sa navigation suivante ; l'en-tête de la requête elle-même reste juste par le crochet) ; (b) la nouvelle navigation ne porte pas de *referrer* : Electron ne donne pas celui de la navigation annulée, et en recomposer un d'après la page où est l'onglet enverrait ce que la page a demandé de ne pas envoyer (elle en envoie moins, jamais plus ; la connexion de Google ne le lit pas) ; (c) au plus 5 redirections de suite reprises sans qu'une navigation valide (`did-navigate`) : au-delà, la redirection est laissée à Chromium, pour qu'un onglet ne se relance jamais sans fin (l'*user agent* refusé par Chromium, un serveur qui renvoie d'un hôte à l'autre) ; l'en-tête est aussi réécrit dans le crochet `onBeforeSendHeaders` de la session (`signInRequestHeaders`), pour la requête qui part avant que le changement n'agisse et pour celles de l'onglet ; (2) Lucium n'ajoute aucun indice `Sec-CH-UA*` à ces requêtes (les trois de la navigation décrits plus haut) ; (3) aucun préchargement de Lucium qui écrit dans la page n'y tourne : `excludeMatches` d'Electron sur `window.chrome.app` et l'état des permissions, le remplacement de `alert`/`confirm`/`prompt`, le pont média, la garde de page et son pendant dans les *service workers* (le pont des mots de passe reste dans le monde isolé de la page, invisible d'elle, et ne change pas). **Ce qui ne change pas** : les autres hôtes de Google (`mail.google.com`, `myaccount.google.com`, `www.google.com`), un sous-domaine, un nom qui ressemble (`accounts.google.com.example`), http, un cadre de Google dans la page d'un autre site, et tout autre onglet, gardent l'identité ordinaire ; quitter ces hôtes rend à l'onglet celle des autres pages. La mesure de `chrome.app` ci-dessus (identité Chrome sans `chrome.app` : refusée dès l'adresse) vaut pour un navigateur qui se dit Chrome ; avec l'identité d'Electron la même page passe l'adresse (essai du mainteneur). **Coût** : un écouteur par onglet sur trois évènements (`did-start-navigation`, `will-redirect`, `did-navigate`), qui compare l'hôte d'une navigation, et une ligne de plus dans le crochet `onBeforeSendHeaders` (la méthode des requêtes du cadre principal) ; le crochet `onBeforeSendHeaders` d'une session ne voit toutes les requêtes web qu'à partir de la première visite d'un de ces hôtes dans cette session, jusqu'à la fin du lancement (`watchSignInPages`, comme pour les fichiers locaux) : une session qui n'y va jamais ne paie rien de plus. **Non mesuré** : un seul compte refusé a été essayé, sur macOS ; les autres comptes et écrans (vérification en deux étapes, clés d'accès, « Se connecter avec Google » depuis un autre site, YouTube) ; l'ordre des en-têtes sur le fil (`User-Agent` est mis en fin de liste) ; ce que Google décide demain (c'est son choix, pas une règle qu'on peut contrôler : si l'identité d'Electron est refusée un jour, ce point est à revoir) ; ce que fait Chromium dans une fenêtre : le rechargement quand le *user agent* change pendant un chargement est établi par la lecture du code de Chromium 156 (non observé ici), et la reprise d'une redirection (annulation puis `loadURL`) n'a été jouée que sur des doublures d'Electron, pas dans une fenêtre (à vérifier : Gmail → « Se connecter », puis la sortie de la connexion vers Gmail, sur un onglet neuf et sur un onglet déjà ouvert ; une redirection d'un POST 307/308 vers ces hôtes garde son *user agent* d'avant, sans reprise). Les tests (`google-sign-in*.test.ts`, `client-hints-wiring.test.ts`) tournent sur des doublures d'Electron : la réponse de Google n'est vérifiable que dans une fenêtre.
- **Ce que les outils de Lucium laissent dans une page** : rien qui porte le nom du navigateur. Les repères de liens des touches Vim sont un `div` à racine fermée ; la fonction qui arrête la Gomme de l'extérieur a un nom tiré au hasard à chaque usage (`zapStopName`, `src/shared/boost.ts`) ; la vidéo flottante ne marque ses éléments d'aucun attribut ; un refus d'« Image dans l'image » est écrit dans le journal de l'application, pas dans la console de la page ; un script utilisateur en échec et la garde de page écrivent dans cette console sans nommer le navigateur, et l'erreur qui arrête un script bloqué a pour message des lettres tirées au hasard. Ce qui reste visible et qu'une page peut observer : la présence de ces éléments pendant qu'un outil sert (un `div`, un `canvas`, une feuille adoptée de « Contraste de la page » et son attribut `data-r…` tiré au hasard), la police « Lucium Inter » qu'une Retouche ajoute à `document.fonts`, et, à mesurer dans l'application, les noms `lucium-find` du registre `CSS.highlights` pendant une recherche par expression régulière.

## Limites connues, à garder en tête

Rien à corriger aujourd'hui ; ces points sont écrits pour qu'une modification voisine ne les rende pas faux sans qu'on le voie. Les cinq derniers sont des choix : chacun dit ce qu'il laisse et pourquoi la correction n'a pas été faite.

**Le préchargement *service worker* de la bibliothèque d'extensions tourne aussi dans les workers des sites web.** Lucium ne limite par adresse que le script de préchargement des cadres de la bibliothèque (`LIBRARY_FRAME_MATCHES`, `src/main/engine/extension-runtime.ts` : les pages `chrome-extension://`) ; son script de *service worker* est enregistré sans limite. Dès qu'une extension est chargée dans une session (`ExtensionPreloads.activate`), `crx-mv3-preload` s'exécute donc aussi dans les service workers des sites ouverts dans cette session. Le limiter à `chrome-extension://*/*` (le champ `matches` de l'enregistrement, que le type d'Electron 45 n'interdit pas pour ce type de contexte) est une piste, non essayée : il faudrait vérifier qu'il laisse les workers d'extensions MV3 intacts. Ce n'est pas exploitable, parce que le préchargement n'accorde rien par lui-même : tout ce qu'il envoie arrive au processus principal, qui ne croit pas l'identité que le message annonce mais lit l'adresse réelle de l'expéditeur (`extensionOfSender` : le `scope` d'un worker, l'adresse d'une page). Un worker de site web n'est pas en `chrome-extension://` : `callerRefusal` refuse l'appel (« a page that is not an extension »), et les gestionnaires réservés à l'interface de l'application ne répondent qu'à la session par défaut (`INTERFACE_ONLY`). `restrictLibraryApis` enveloppe en dernier tous les gestionnaires que la bibliothèque a déjà enregistrés, et `ece-router.test.ts` vérifie qu'un worker ou une page d'un site, un expéditeur détruit ou absent sont traités en étrangers. Ce qui reste à relire à chaque montée de version de `electron-chrome-extensions` : un gestionnaire que la bibliothèque enregistrerait après cet enveloppement ne serait pas gardé, et un appel qui ne nomme aucune extension n'est pas refusé par `callerRefusal` (il est servi par les gestionnaires qui n'en exigent pas). Exception relevée le 9 novembre 2026, **non vérifiée dans Electron** : le retrait d'un écouteur (`crx-remove-listener`) ne garde, pour un worker, aucun expéditeur à comparer, et la bibliothèque retire l'écoute du worker de l'extension que le message nomme. La bibliothèque n'écoute ce canal sur `serviceWorker.ipc` que pour les workers d'extension ; si Electron remet aussi à `ipcMain`, où elle l'écoute également, le message d'un worker de site, un site pourrait désinscrire le worker d'une extension d'un événement : des événements perdus pour elle, rien de lu. Piste : la même limite par adresse pour le script de worker, ou un correctif de la bibliothèque qui compare `event.serviceWorker.scope` à l'extension nommée, vérifiés par le test moteur.

**« Geler » passe par `debugger.attach`, et un service worker du site n'est peut-être pas gelé.** Geler un onglet envoie `Page.setWebLifecycleState('frozen')` par le protocole de débogage de la page : `debugger.attach('1.3')`, la commande, puis `detach` (`ElectronPage.setLifecycleState`, `src/main/engine/electron-page.ts`). Détacher laisse la page gelée, seule la commande la gèle ; si une extension a déjà attaché son débogueur à la page, c'est sa session qui sert et Lucium ne la détache pas. Ce que le README mesure (une page lourde de 5 % de CPU visible à 0 %) est la page. Un service worker du site est une autre cible de Chromium : qu'il ne soit pas gelé avec la page est **supposé, non mesuré**. Un site gelé peut donc garder un peu d'activité (CPU, réseau) dans son worker. « CPU à zéro » dit le README pour la page, pas pour ses workers.

**Le plan de la garde de page est celui de l'adresse que la page annonce.** Le préchargement de la garde (`src/preload/page-guard.ts`) demande son plan par un message synchrone, avec l'adresse du document qui démarre (`location.href`, qu'aucun script de la page n'a encore pu toucher). Le processus principal le sert pour cette adresse dès qu'elle est une adresse web (`guardPageUrl`, `src/shared/page-guard.ts`), sans la comparer à celle qu'il connaît pour le cadre : pendant qu'une navigation s'engage, celle-ci peut encore être l'adresse de la page précédente. Seul un processus de page déjà pris (du code exécuté hors du monde isolé du préchargement) peut annoncer une autre adresse ; il obtient le plan de ce site (les scriptlets des listes, publiques, et le niveau de protection contre l'empreinte retenu pour lui, donc l'existence d'une exception) et la politique WebRTC qui va avec, pour son propre onglet. Il n'agit sur aucune autre page. Comparer l'adresse annoncée à la navigation en cours demanderait de suivre chaque navigation du cadre principal (début, redirections, restauration, fenêtres ouvertes par une page), et un écart refusé laisserait la page sans protection dans tout cas que ce suivi manquerait, ce que seule la chaîne moteur peut montrer. La correction coûterait plus qu'elle ne protège : elle n'est pas faite.

**Un seul préchargement pour toutes les surfaces de l'interface.** `src/preload/index.ts` donne `window.lucium` (157 appels) à toutes les surfaces faites par Lucium : la fenêtre principale et son calque, les Réglages, la page des extensions, À propos, le gestionnaire de tâches, la barre de la vidéo flottante, les mini-fenêtres et le cadre des fenêtres d'application. Leur garde (`registerIpc`) vérifie que l'expéditeur est une de ces surfaces, pas laquelle : une surface dont le processus serait pris aurait les droits de la fenêtre principale. Ce qui les tient aujourd'hui : chacune est un fichier de l'application (`app.asar`), sous une politique `default-src 'self'`, dans un processus isolé (`sandbox`, `contextIsolation`), et ne peut naviguer ailleurs (`lockSurface`). L'annotation et le partage ont déjà leur propre préchargement. Découper le préchargement par rôle toucherait chaque page de l'interface et les contrôles moteur qui lisent ses gestionnaires : c'est un chantier à part, pour après la 1.0.

**Champs d'une version plus récente et restauration.** Les champs de `state.json` que cette version ne connaît pas (écrits par une version plus récente) sont gardés et réécrits à chaque enregistrement (`foreignFieldsOf`, `withForeignFields`, `src/shared/state-clean.ts`), y compris après Aide › Restaurer les données… ; ceux du fichier restauré ne sont pas repris. C'est voulu : un fichier venu d'ailleurs ne décide pas de ce que cette version ne sait pas vérifier, de la même façon que la restauration garde les réglages propres à l'installation (dossiers, proxy, flux des mises à jour). Au-delà de 256 Kio (`FOREIGN_FIELDS_MAX_BYTES`), ces champs ne sont pas gardés et le journal le dit.

**Un état de plus de 64 Mio n'est plus écrit.** Un fichier d'état plus gros que ce que le lancement suivant lit (`DATA_FILE_MAX_BYTES`) serait mis de côté comme abîmé. L'écriture recommence alors sans les icônes `data:` des onglets ; si l'état dépasse encore 64 Mio, le fichier en place est gardé, l'utilisateur en est averti une fois (« Enregistrement impossible »), et l'écriture est réessayée toutes les 5 secondes et à la fermeture : ce qui a changé depuis le dépassement est perdu si l'état ne redescend pas sous la borne avant la fermeture. Aucun état réel n'en approche (il faudrait des centaines de Retouches de 1 Mo de JavaScript ou des sessions de dizaines de milliers de pages) ; plafonner le nombre de Retouches ou les sessions refuserait des données qui existent déjà, pour un cas qui n'a pas été mesuré.

**Le journal du processus principal est la console.** Le processus principal écrit son journal avec `console.error`, `console.warn` et, plus rarement, `console.info` ou `console.log` (plus de 600 lignes), chaque ligne précédée du nom de son domaine entre crochets (`[store]`, `[webstore]`, `[guard]`…). Il n'y a ni niveau réglable ni module central. Les 50 dernières erreurs sont aussi gardées en mémoire, expurgées, pour « État de Lucium… » du menu Aide (`src/main/error-log.ts`) ; rien n'est écrit sur le disque ni envoyé. Un module de journal ne changerait rien de ce que voit l'utilisateur et toucherait chacune de ces lignes : il n'est pas fait.

## Image dans l'image de Lucium

« Image dans l'image » demandé à Lucium (Fichier › Image dans l'image, bouton du lecteur multimédia) ouvre **la fenêtre flottante de Lucium** (`src/main/shell/floating-video.ts`) ; le bouton d'image dans l'image du site garde la fenêtre du système, et l'image dans l'image automatique en quittant un onglet aussi (`auto-pip`).

- **Document Picture-in-Picture, repris derrière une fonction.** Le moteur de page de Chromium 156 expose bien `documentPictureInPicture`, mais Electron 45.2.1 ne montre jamais la fenêtre : la demande arrive au processus principal avec la disposition `NEW_PICTURE_IN_PICTURE`, que le convertisseur d'Electron rend `"other"`, et `lib/browser/api/web-contents.ts` (`-add-new-contents`) annule toute disposition autre que `foreground-tab`, `new-window`, `background-tab` et `save-to-disk`, après quoi `WebContents::AddNewContents` détruit le contenu ; seul `EnterVideoPictureInPicture` est câblé (`electron_api_web_contents.cc`). Ticket ouvert depuis 2023 : electron/electron#39633. La build castLabs est le même code. Écartée jusqu'au 12 novembre, la reprise par l'événement interne est faite derrière la fonction `document-pip`, coupée par défaut (`src/main/engine/document-pip-windows.ts`, décisions dans `src/shared/document-pip.ts`, détail dans [fonctions.md](fonctions.md)) : l'écouteur d'Electron est remplacé, sur la page qui a eu un « oui », par le nôtre, qui prend la seule fenêtre acceptée et rappelle celui d'Electron pour tout le reste ; sans cet écouteur (une mise à jour), rien n'est accepté. Le contrôle moteur `src/main/smoke-docpip.ts` en est la preuve et la sonde.
- **La vue de l'onglet prêtée.** `Page.lendView(windowId, ended)` (`ElectronPage`) sort la vue de la fenêtre de l'onglet et la pose dans la fenêtre flottante, telle quelle : ni rechargement ni capture d'images, la protection Widevine suit la page. Contrairement à `moveToWindow`, rien n'est dit au moteur d'extensions (l'onglet reste dans sa fenêtre pour `chrome.tabs`) et les popups et boîtes de la page restent attachées à sa fenêtre. Tant que la vue est prêtée, `show`, `hide`, `raise`, `focus` et `moveToWindow` de la page ne font rien : la mise en page de la fenêtre de l'onglet ne peut pas la reprendre. Le prêt finit quand la page se ferme, que son rendu meurt ou qu'elle change de document (`destroyed`, `render-process-gone`, `did-navigate`) ; la fenêtre se ferme alors sans rien montrer. Un onglet emmené dans une autre fenêtre est d'abord rendu (`adoptPage`).
- **La vidéo remplit la page, sur place** (`src/main/engine/floating-video-scripts.ts`, monde isolé `FLOATING_WORLD`) : rien n'est déplacé dans le document. Le lecteur (l'ancêtre de la vidéo au plus 1,25 fois sa taille, où le site dessine ses sous-titres en texte) passe dans la couche supérieure (`popover="manual"` + `showPopover()`), à la taille de la vue, la vidéo en `object-fit: contain` ; les styles sont posés sur les éléments avec `!important` et les valeurs de la page gardées pour être rendues. Un `MutationObserver` remet les styles si la page les écrase, rouvre la couche si elle la ferme, et fait flotter la vidéo qui remplace l'ancienne (un lecteur React redessiné) ; il se coupe pendant ses propres changements. Limites : un sous-titre dessiné hors du lecteur (plus grand que 1,25 fois la vidéo) n'est pas montré ; les commandes du site, dans le lecteur, restent sous la barre (la page ne reçoit jamais la souris, elles se cachent d'elles-mêmes pendant la lecture, mais restent visibles sur une vidéo en pause).
- **Vidéo dans un cadre** (un lecteur intégré d'un autre site) : `findFloatingVideo` répond `frame`, et la vidéo flotte dans la fenêtre du système (`floatFrameVideo`, avec un geste dans ce cadre) ; une notice le dit.
- **La fenêtre** : sans cadre, au-dessus des autres (`setAlwaysOnTop(…, 'floating')`), sur tous les bureaux (sans `visibleOnFullScreen`, qui ferait disparaître et revenir l'icône du Dock), aux proportions de la vidéo (`setAspectRatio`), ouverte sans prendre le focus (le clavier va à la barre quand on clique dans la fenêtre). Première fois : 480 px de large en bas à droite de l'écran de la fenêtre de l'onglet ; ensuite la place et la taille de la dernière (en mémoire, le temps de la session). Une seule vidéo flotte à la fois pour tout le groupe de fenêtres.
- **La barre** (`FloatingVideoBar.tsx`, règles pures dans `src/shared/floating-video.ts`) : apparaît au mouvement du pointeur, disparaît 2 s après (sans fondu avec « Réduire les animations »), reste tant que le clavier est dedans. Espace, M, ↑/↓, ←/→ ; ⌘W ferme la fenêtre (intercepté avant la barre de menus, qui fermerait l'onglet de la fenêtre derrière). La vidéo n'est lue (toutes les 0,5 s) que pendant que la barre est affichée. −10 s / +10 s ne sont proposés ni pour un direct (`duration === Infinity`) ni pour une vidéo protégée (`mediaKeys`), et le processus principal comme le script les refusent quoi qu'on demande. Le son coupé ici est celui de l'onglet (`toggleMute`, la barre latérale suit) ; le rendre rend aussi le sien à une vidéo muette. Un message de la barre n'est écouté que de sa propre vue, par son cadre principal, et revalidé (`parseFloatingCommand`).
- **Fin** : « Revenir à l'onglet » rend la page telle qu'elle était, ramène la vue dans sa fenêtre et y montre l'onglet, sélectionné, fenêtre au premier plan ; le bouton de fermeture et ⌘W font de même en mettant la vidéo en pause et sans passer la fenêtre devant. La rangée de l'onglet porte une marque tant qu'il flotte (un clic sur la marque ou le choix de l'onglet ramènent la fenêtre flottante devant, sans le focus) et la place de sa page le dit, avec « Ramener la vidéo ici » (`TabRuntime.floating`).
- **Veille** : un onglet dont la page est dans la fenêtre flottante n'est jamais mis en veille ni gelé, même à la main (`SleepFacts.floating`, lu dans l'état du processus principal : la page, elle, ne sait pas qu'elle flotte).

## Surfaces d'interface

Quatre surfaces web que nous possédons (plus les mini-fenêtres), plus les pages :
- **Fenêtre** (`index.html`) : sidebar et fond.
- **Règles étendues du bloqueur et protection contre l'empreinte** (réglages `blockScriptlets`, `reduceFingerprint`, `fingerprintStrict`, `fingerprintExceptions` ; désactivés par défaut ; détail, limites et mesures dans `docs/fonctions.md`). Trois pièces. *Moteur de filtres* : `FilterEngine.decide()` (verdict `pass`/`block`/`redirect`/`rewrite`), `scriptlets()` (nom et arguments, jamais du code) et `cspFor()` ; `BlockingService.verdict()` les applique quand le réglage est actif (`filter()` reste le « annule ou laisse passer » d'avant), `scriptletCalls()` revérifie chaque règle contre la bibliothèque (`shared/scriptlets.ts`), `cspFor()` filtre les directives (`shared/extended-rules.ts`). Le crochet `onBeforeRequest` du moteur Electron accepte un verdict `{ redirect }` (adresse `http(s)` ou exactement une de nos ressources, `safeRedirectTarget` ; une ressource est servie par la session sous le schéma `lucium-stand-in://<mot du lancement>/<nom>`, `syncStandIns`, parce que Chromium abandonne une redirection vers un `data:`), un crochet `onHeadersReceived` (documents principaux seulement) ajoute la politique CSP. *Garde de page* : `PageGuard` (`shell/page-guard.ts`, un par fenêtre et un pour le contexte privé) configure le moteur (`setPageGuard`, `setResponsePolicy`) seulement quand un des réglages est actif ; le moteur enregistre alors, par session, le préchargement `preload/page-guard.ts` (`registerPreloadScript`, retiré par `unregisterPreloadScript` quand tout est coupé, avec le canal `lucium:page-guard:plan`). Le préchargement demande son plan de façon synchrone (la page ne doit pas courir avant d'être protégée), ne reçoit que des noms et des nombres (`shared/page-guard.ts`, relus), et passe `preload/guard-world.ts` au monde principal (`contextBridge.executeInMainWorld`, fonction autonome) : bibliothèque de scriptlets et bruit stable par site. Les graines viennent d'une clé tirée au hasard, gardée en mémoire (`SiteSeeds`). La politique WebRTC est celle de la page (`Page.setWebRtcPolicy`). Les cadres et les workers d'une page, que ce préchargement n'atteint pas, reçoivent la même protection contre l'empreinte par une session du protocole DevTools gardée sur la page (`engine/inner-guard.ts`, `setInnerGuard` ; session partagée avec l'apparence des sites, `engine/own-session.ts`), et les service workers par le même préchargement enregistré pour eux. *Moteur compilé sur disque* : `ListStore.readEngine/writeEngine` (en-tête JSON `format`, `key`, `size`, `crc32`, droits 0600).
- **Téléchargements : options avancées** (désactivées par défaut ; réglages `downloadPause`, `downloadAskWhere`, `openWithMemory` + `openWithApps`, `openUnsaved`, `pdfWithSource`, `useReadLaterFolders`). Le moteur lit une `DownloadPolicy` (`setDownloadPolicy`, propre à chaque fenêtre privée) : `ask` (la boîte « Enregistrer sous », une couture `setDownloadUi` que le test moteur remplace) et `openUnsaved`. Un fichier dont on demande l'emplacement, ou ouvert sans être gardé, est écrit dans le dossier temporaire de l'application (`download-staging.ts` : `tmp/lucium-<empreinte du dossier de données>/dl-N/`, jamais une écriture hors de ce dossier, balayé au démarrage et à la sortie, une racine qui serait un lien est refusée) ; il est déplacé à l'endroit choisi à la fin du téléchargement (copie puis suppression entre deux disques). Le nom proposé vient de `shared/file-names.ts` (dernier segment, caractères de contrôle et de renversement du texte retirés, 240 octets au plus). La pause et la reprise passent par `DownloadItem.pause()/resume()` ; une interruption de réseau que Chromium ne reprend pas seul (cinq tentatives) se reprend par une requête `Range`. Reprise après redémarrage (réglage `downloadResume`, désactivé par défaut, détail dans `docs/telechargements-reprise.md`) : Electron ne garde aucun historique, l'application écrit donc dans `download-resume.json` (droits 0600, dossier des données, hors de l'état et des exportations) l'adresse et le chemin du fichier partiel de chaque téléchargement en cours, avec l'empreinte de son premier et de son dernier mégaoctet (`download-resume.ts`). Jamais pour une fenêtre ou un onglet privé, jamais pour un fichier du dossier temporaire ; 20 enregistrements, 72 h. « Reprendre » juge de nouveau l'enregistrement et le fichier (sous le dossier de téléchargement du profil, sans lien ni `..`, mêmes empreintes), demande au serveur un octet avec `Range` et `If-Range` (206, même `ETag`, même `Last-Modified`, même longueur, sinon refus avec un message), coupe le fichier à l'offset et ne demande alors à Chromium (`session.createInterruptedDownload`, puis `item.resume()` dans `will-download`) de continuer. Le fichier de reprise sert aussi de signe au démarrage suivant pour télécharger en un seul flux (`single-stream.ts` : `ParallelDownloading` désactivée), sans quoi l'octet compté ne serait pas un préfixe continu du fichier. « Ouvrir avec… » (`shared/open-with.ts`, `shell/open-with.ts`) appelle `/usr/bin/open -a <application.app> <fichier>` sans interpréteur, après avoir revérifié l'application (un `.app` avec `Contents/Info.plist`) et le fichier (fichier ordinaire, sans lien, sans bit d'exécution, type absent de `EXECUTABLE_TYPES`, type MIME annoncé qui n'est pas un programme) ; l'interface ne peut que retirer des entrées de `openWithApps` (`interfaceMayDispatch`), une restauration d'état garde la liste locale, une fenêtre privée n'en mémorise rien. L'impression en PDF (`shared/pdf-source.ts`) met l'adresse (sans identifiants ni fragment, échappée) et la date en pied de page par `webContents.printToPDF`. Les dossiers de « Lire plus tard » sont `readLaterFolders` (au plus 50) et `folderId` sur chaque page, normalisés par `state-clean.ts` ; les actions `readlater-folder/*` et `readlater/move` ne font rien tant que le réglage est désactivé, et les pages gardent leur dossier dans le fichier.
- **Calque** (`overlay.html`) : une seule vue, au-dessus de tout, qui affiche *un* panneau à la fois : barre de commandes, recherche dans la page, téléchargements, éditeur d'espace, **éditeur de thème** (posé à côté de la sidebar, qui montre le thème en direct), invite de permission, **feuille de revue des permissions d'une extension** (Chrome Web Store), connexion HTTP, boîte du `prompt()` d'une page. Les panneaux modaux couvrent la fenêtre ; recherche et permission n'occupent qu'un rectangle pour que la page reste utilisable. Une invite de permission, une connexion HTTP ou une boîte de `prompt()` n'écrase jamais un panneau en cours : elle attend sa fermeture ; la boîte d'un `prompt()`, elle, ne se laisse pas remplacer (une page est bloquée dessus).
- **Page Extensions** (`extensions.html`) : ce n'est plus une fenêtre : le même bundle, servi à un onglet sous `lucium-ui://extensions/` et affiché `chrome://extensions` (voir « La page Extensions en onglet »). Elle ne reçoit pas les instantanés de la fenêtre : un instantané réduit, par ses canaux à elle.
- **Fenêtre Réglages** (`settings.html`) : une vraie fenêtre, créée à la demande et réutilisée ; elle reçoit les mêmes instantanés d'état que la fenêtre principale et n'est une surface de confiance que tant qu'elle existe. ⌘W la ferme sans toucher aux onglets.
- **Sidebar flottante** (`index.html#float`) : la même sidebar, glissée par-dessus la page quand la sidebar est masquée et que le pointeur touche le bord gauche.
- **Barre de la fenêtre d'image dans l'image** (`floating-video.html`) : la barre de commandes de la fenêtre flottante de Lucium (voir « Image dans l'image de Lucium » plus bas), une vue transparente posée sur la page prêtée ; surface de confiance tant que la fenêtre existe, et seule à pouvoir la piloter (canal `lucium:floating-video-action`).

Si le processus de rendu d'une surface meurt (plantage, mémoire reprise par le système), `load` la recharge au lieu de la laisser blanche : même `WebContents`, donc même identifiant de confiance pour l'IPC, et l'état, qui vit dans le processus principal, revient par l'instantané. Trois rechargements par minute au plus, puis la surface reste telle quelle et le journal le dit (`src/main/shell/ui-crash-reload.ts`).

**Taille des fenêtres et des panneaux** (Réglages › Apparence ; `src/shared/panel-scale.ts`). Les panneaux du calque et les fenêtres à part sont dessinés en pixels CSS : petits sur un écran 3440 × 1440, grands sur un petit portable. Un seul facteur les règle, calculé à un seul endroit pour l'écran où se trouve la fenêtre : le choix retenu pour cet écran, ou « Automatique » (d'après la taille de l'écran en points : 100 % pour 1512 × 982, 105 % pour 1920 × 1080, 120 % pour 2560 × 1440, 125 % pour 3440 × 1440, 95 % pour 1280 × 800), ramené à ce que la fenêtre peut contenir (au-delà de 100 %, jamais plus que ne tient la fenêtre : `fitLimit`). Il se pose de deux façons, jamais panneau par panneau : (1) le **zoom du `WebContents`** qui dessine (`setZoomFactor`, le texte suit comme avec la taille de l'interface, jamais le zoom des pages) : pour le calque, `Browser.overlayZoom` = zoom de l'interface × facteur des panneaux tant qu'un panneau posé au milieu de la fenêtre est ouvert (`PANEL_PLACEMENT` : `centred`), et le zoom de l'interface seul pour ce qui est accroché à la barre latérale ou à la barre d'outils, que le processus principal place en pixels CSS de l'interface (barre de commandes, recherche, panneaux de la barre latérale, thème, Glance, ⌃Tab, voile du glisser, invite de permission, bulles ancrées) ; `syncUiZoom` le pose à chaque disposition ; (2) la **taille des fenêtres à part**, multipliée dans le processus principal (`PanelScaling.open` : taille et minimum × facteur, bornés à la zone utile de l'écran, centrée sur l'écran de la fenêtre où l'on travaille) et suivie tant qu'elles sont ouvertes. Le choix est retenu **par écran** dans `Settings.panelSizes`, sous une clé faite du nom du moniteur, de sa taille en points et de sa densité (`LG UltraWide|3440x1440@1` ; l'écran intégré est `built-in|1512x982@2` : le nom que le système lui donne change avec la langue) : l'`id` d'un `Display` d'Electron change quand on débranche et rebranche un moniteur et ne sert donc pas ; deux moniteurs identiques partagent un choix, ce qui convient (même taille). 12 écrans au plus (le plus ancien part), chaque entrée relue et nettoyée (clé recalculée depuis ses champs, pourcentage borné à 80-160, entrée sans choix ni notice écartée). Une fenêtre privée suit les choix de la fenêtre principale ; une fenêtre d'invité les ignore (Automatique). Notice : `ScreenWatch` regarde l'écran d'une fenêtre normale peu après son affichage, à la prise du focus et après un déplacement (jamais en fenêtre privée ni en test moteur), sans rien écouter d'autre ; un écran d'au moins 2560 points de large ou de rapport 2,2 reçoit « trop petits », un écran de moins de 1366 points « trop grands », une fois par écran (`noticed` retenu avant la notice). **Non vérifié sur écran** (le code a été écrit sans ouvrir de fenêtre) : Chromium retient un zoom par adresse de page, et le code compte sur le fait que les pages de l'application construite sont des fichiers, chacune avec son zoom (même hypothèse que `syncUiZoom` pour la taille de l'interface) ; en développement (`pnpm dev`), toutes les surfaces sont servies par `localhost`, un seul zoom y est retenu pour l'hôte, et le zoom des panneaux y entraînerait celui de la fenêtre. Les fenêtres à part reposent leur zoom à chaque navigation (`did-navigate`, `did-navigate-in-page`, `did-finish-load`, puis 100 ms plus tard : l'ordre dans lequel les observateurs de Chromium apprennent une navigation n'est pas fixé) pour la même raison. Le calque de toutes les fenêtres est la même page, donc la même adresse : deux fenêtres d'écrans différents qui montrent un panneau en même temps se partagent son zoom, et le dernier panneau ouvert l'emporte ; chaque ouverture relit le zoom réel du calque (`layerZoom` remis à zéro dans `openOverlay`) au lieu de se fier à ce que la fenêtre lui a donné la dernière fois.

Ordre d'empilement : interface → page → sidebar flottante → calque (`Browser.layout`). Le processus principal ne fait confiance à aucune de ces surfaces : chaque message IPC est revalidé (`shell/ipc.ts`), et seul le processus principal peut ouvrir une invite de permission.

## Fenêtre des Réglages

Une fenêtre de 780 × 760 points (la taille des fenêtres à part la multiplie, voir plus haut) : une barre latérale de 204 px et la page. La barre latérale porte la recherche, « Pour commencer », les huit catégories, puis « Fonctions en option » et « À propos et mises à jour » sous un filet, et, à son pied, « Réglages modifiés ». La page montre en haut ses réglages principaux, puis un seul repli, « Plus de réglages », dont la ligne nomme les groupes qu'il contient, puis « Rétablir les valeurs par défaut » de la page. Une liste ou un éditeur est sur une sous-page, à l'adresse `#<page>/<sous-page>` (`#protection/filterlists`), qu'ouvre une rangée de sa page et que referment son lien de retour ou Échap. Le guide d'utilisation est [reglages.md](reglages.md).

Ce qui décide de quoi (logique pure dans `src/shared/`, sans Electron) :

| Fichier | Rôle |
|---|---|
| `settings-catalog.ts` | La carte : les pages et leur ordre (`SETTINGS_CATEGORIES`, le même que `SETTINGS_PAGES` de `ipc.ts`), la page de chaque clé de `Settings` (`SETTINGS_KEYS`), les clés sans rangée et pourquoi (`NO_CONTROL_KEYS`), les rangées que « Pour commencer » redessine (`HOME_MIRROR_KEYS`), les thèmes de « Fonctions en option » (`FEATURE_THEMES`), ce que « Rétablir » ne touche pas (`KEPT_ON_RESET`), les anciennes adresses et leur page d'aujourd'hui (`resolveSettingsTarget`). |
| `settings-placement.ts` | Le haut de la page ou « Plus de réglages » : une clé de `PAGE_KEYS` est en haut, toute autre dans le repli ; un réglage d'une sous-page suit la rangée qui l'ouvre. |
| `settings-subpages.ts` | Les 17 sous-pages (`SUBPAGES`) : leur page, leur titre, leur ligne d'intro, les réglages qu'elles tiennent, et l'état que dit la rangée qui les ouvre (`subpageSummary`). |
| `settings-presets.ts` | Les quatre préréglages (`PRESETS`) : chaque option est une réponse de « Régler en quelques questions » (`settings-guide.ts`), les valeurs n'existent qu'une fois. |
| `settings-search.ts`, `settings-synonyms.ts` | La recherche : mots courants écartés, pluriels et terminaisons, poids selon l'endroit où un mot est trouvé (libellé, synonyme, choix d'un menu, groupe, aide), meilleur résultat ; les synonymes ajoutent les mots qui ne sont pas à l'écran. |
| `settings-answers.ts` | Ce que la recherche répond quand la requête nomme une commande de menu ou ce que Lucium n'a pas (une page d'accueil, une police), avec le menu et le raccourci en vigueur. |
| `settings-path.ts` | Les chemins que donnent les textes (`settingsPath`), écrits d'après la carte. |

Ce qui dessine (`src/renderer/`) : `SettingsWindow.tsx` (la barre latérale, l'adresse, la recherche, « Réglages modifiés », les sous-pages, le clavier), `SettingsCategories.tsx` (ce que chaque page tient, dans l'ordre de ses groupes ; `CategoryContent` dessine une page en trois passes : son haut, son repli ou une sous-page, `FoldPassContext` de `settings-context.ts`), `SettingsHome.tsx` (« Pour commencer »), `SettingsMore.tsx` (le repli et sa ligne, lue sur les rangées qu'il dessine), `FeaturesPage.tsx` (« Fonctions en option »), `PresetSettings.tsx` et `CategoryRows.tsx` (les préréglages), `SettingsSearchHead.tsx` (la réponse et le meilleur résultat), `GuideSettings.tsx` (les questions), `settings-parts.tsx` (`Row`, `Check`, `Group`, `SubpageEntry`, `Subpage`, `MoreText`), `settings-filter.ts` (la recherche appliquée aux rangées dessinées et le surlignage), `settings-modified-view.ts`, `settings-anchor.ts` (l'arrivée sur un groupe ou une rangée) et `settings-icons.tsx`. Les volets `*Settings.tsx` sont ceux d'avant, rangés à leur nouvelle place.

**Ajouter un réglage** : chacun a sa page, sa place et son texte court.

1. **Sa page** : la clé dans `SETTINGS_KEYS` de la page qui la dessine, et sa rangée dans le volet de cette page, marquée par sa clé (`settingKey` de `Row` ou `Check`, qui pose `data-setting`). Une clé sans rangée va dans `NO_CONTROL_KEYS` avec sa raison. Une fonction à ajouter (« voulez-vous cette chose ? ») va dans `FEATURE_THEMES` et dans le registre (`docs/fonctions.md`, « Marche à suivre »).
2. **Sa place** : en haut de la page seulement si on le change dans les premières semaines (`PAGE_KEYS`) ; sinon il attend dans « Plus de réglages », sans autre geste. Une liste ou un éditeur va sur une sous-page (`SUBPAGES`), avec l'état que dit sa rangée.
3. **Son texte court** : un libellé et une aide d'une ligne, dans les deux catalogues ; le détail derrière « En savoir plus » (section suivante). Un texte qui envoie vers les Réglages dit `{settingsPath}` et ajoute son lieu à `SETTINGS_PLACES`.
4. Si les mots que l'on tape pour le trouver ne sont pas à l'écran, une entrée dans `settings-synonyms.ts`. Si « Rétablir » ne doit pas le toucher (ce qu'on a saisi ou construit), `KEPT_ON_RESET` avec la raison.

Ce qui le vérifie : `src/renderer/settings-structure.test.ts` dessine chaque page et échoue pour une clé qu'aucune page ne dessine ou une rangée que la carte ne connaît pas ; `settings-more.test.ts` mesure qu'aucun réglage n'est caché sans que la page le dise ; `settings-subpages.test.ts` ouvre chaque sous-page à son adresse ; `settings-texts.test.ts` compte les mots des aides ; `settings-paths.test.ts` vérifie chaque chemin ; `settings-search-queries.test.ts` trouve chaque rangée par son nom, dans les deux langues ; `src/main/features-docs.test.ts` relit `docs/fonctions.md` ; `src/main/docs-settings-paths.test.ts` et `settings-paths.test.ts` relisent les chemins vers les Réglages écrits dans les documents.

## Textes des Réglages : une ligne, et « En savoir plus »

Chaque rangée des Réglages dit son aide en une ligne, qui décrit ce que la personne verra ou ce que la fonction coûte. Le mécanisme, les seuils et les cas à part passent derrière « En savoir plus » (`MoreText` dans `src/renderer/settings-parts.tsx`, la prop `more` de `Row`, `Check` et `Group`), qui garde le texte entier. Une phrase courte a sa propre clé, placée à côté de la clé longue dans les deux catalogues. Les fonctions ont une ligne courte dans le registre (`featureSummary`, `featureLine` dans `src/shared/features.ts`). `src/renderer/settings-texts.test.ts` dessine chaque page dans les deux langues et refuse une aide visible de plus de 30 mots, une moyenne au-dessus de 18 mots, et une note de groupe de plus de 30 mots.

Aucun texte n'écrit à la main un chemin vers les Réglages. Il dit `{settingsPath}`, et le code lui donne `settingsPath('<lieu>')` (`src/shared/settings-path.ts`). Le chemin est écrit d'après la carte de la fenêtre : le nom de la page, « Plus de réglages » quand le réglage y attend, la sous-page, le groupe. `src/renderer/settings-paths.test.ts` vérifie chaque lieu dans la fenêtre dessinée, trouve un appel qui ne donne pas le chemin, et refuse un chemin écrit à la main qui ne mène nulle part.

## Clavier et extensions : touches de type Vim, groupes d'onglets en dossiers, mots-clés d'extension

Trois fonctions du registre (`vim-keys`, `tab-groups-ext`, `omnibox-keywords`), désactivées par défaut, leurs réglages dans `src/shared/key-ext-settings.ts` et leurs interrupteurs à la place de chacune (`src/renderer/KeyExtSettings.tsx` : touches Vim dans Clavier et souris › Plus de réglages, mots-clés d'extension dans Navigation › Plus de réglages, groupes d'onglets dans « Fonctions en option »). Détail de ce qu'Electron ne permet pas (accès d'une extension aux sites) : `docs/compat-extension-claude.md`.

**Touches de type Vim** (`vimKeys`, `vimKeysExcludedHosts` ; `src/shared/vim-keys.ts`). C'est un **outil de page** comme le défilement automatique et les gestes (`src/shared/page-tools.ts`) : un script du monde isolé `TOOLS_WORLD` (4 200 031) du **cadre principal** seulement, jamais d'une surface de l'interface ni d'un cadre incorporé, installé au `dom-ready` d'une page dont le site n'est pas dans la liste des sites exclus, retiré quand le réglage ou la liste change (`Browser.toolsFor` / `refreshPageTools`). La table des touches et les étiquettes des liens sont des fonctions pures que le script emporte comme source (testées en Node). Touches (hors champ de saisie, sans ⌘ ⌃ ⌥, jamais une touche que la page a fabriquée) : `j k h l` (60 px), `d u` (demi-page), `gg G`, `f` / `F` (étiquettes sur les liens visibles, en nouvel onglet avec `F` ; étiquettes dans un élément `lucium-vim-hints` à racine fermée, au-dessus de tout), `H L` (retour, avance), `J K` (onglet précédent, suivant), `r`, `/` (la recherche de Lucium), Échap. Ce que la page ne peut pas faire seule passe par la ligne de console signée du secret de la page (`{ tool: 'vim', action }`, adresse d'un lien ≤ 1800 caractères, http(s) seulement, revérifiée) ; le processus principal n'obéit qu'à la page affichée (`Browser.runVimKey`). Un lien ouvert avec `F` suit le réglage du ⌘-clic (derrière, par défaut). Le défilement vise la boîte qui a le focus, sinon la page, sinon la plus grande boîte défilante (applications web). **Coût désactivé** : aucun script injecté. **Coût activé** : un écouteur de touches par page ; `f` lit au plus 5 000 éléments et étiquette 400 liens. Limites : ni compteur (`5j`), ni `n` / `N`, ni touches dans les cadres incorporés ; les raccourcis propres d'un site (messagerie, forge) sont masqués par les lettres : à mettre dans la liste des sites exclus ; seuls les éléments de la liste de `HINT_SELECTOR` et les éléments visibles non recouverts sont étiquetés (un `div` à écouteur JavaScript sans `onclick`, `tabindex` ni rôle ne l'est pas).

**Groupes d'onglets d'extension en dossiers** (`tabGroupFolders` ; `src/shared/group-folders.ts`, `extension-shims.ts`, portail `tab-groups-ext`). Un dossier de la barre latérale ne contient que des onglets épinglés : les onglets du groupe y sont épinglés tant que le groupe vit et remis à leur place d'origine (épinglé ou non, dossier, rang) ensuite. `persistableState` écrit l'état **sans** ces dossiers (le fichier ne garde jamais un dossier pour un groupe qui n'existera plus). Voir `docs/compat-extension-claude.md`.

**Mots-clés d'extension** (`omniboxKeywords` ; `src/shared/omnibox.ts`, `command-bar.ts` `omniboxFor`, canal `omniboxEnter`). Mot-clé, espace, texte, Entrée : le processus principal démarre le worker de l'extension si besoin et lui livre `onInputStarted` puis `onInputEntered` (`engine.deliverToWorker`). Sans suggestions. Voir `docs/compat-extension-claude.md`.
